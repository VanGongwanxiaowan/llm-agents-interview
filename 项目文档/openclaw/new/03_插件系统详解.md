# 03_插件系统详解

## 1. 什么是 Plugin？

**Plugin（插件）** 是 OpenClaw 的扩展机制，允许你：
- 添加新的消息渠道（Channel）
- 添加新的 AI 模型提供商（Provider）
- 添加新的工具（Tool）
- 在消息处理的各个环节进行干预（Hook）
- 添加 CLI 命令

**类比理解**：Plugin 就像是一个**插件式软件模块**，可以随时插拔，不需要修改核心代码。

---

## 2. 插件结构

一个典型插件的目录结构：

```
extensions/telegram/          # 插件根目录
├── openclaw.plugin.json     # 【重要】插件清单文件
├── package.json             # npm 包配置
├── src/
│   ├── index.ts            # 【重要】插件入口点
│   ├── api.ts              # 公共 API 导出
│   ├── runtime-api.ts      # 运行时 API
│   ├── config-api.ts       # 配置 API
│   ├── setup-entry.ts      # 安装入口
│   └── src/               # 实际实现
│       ├── channel.ts      # 渠道实现
│       ├── bot.ts         # Bot 实现
│       └── ...
└── tsconfig.json
```

---

## 3. openclaw.plugin.json - 插件清单

这是插件的**身份证**，必须在插件根目录下。

```json
{
  "id": "telegram",           // 唯一标识符
  "name": "Telegram",         // 可读名称
  "description": "...",       // 描述

  // 插件激活方式
  "activation": {
    "onStartup": false        // 是否在启动时激活
  },

  // 声明这个插件提供的渠道
  "channels": ["telegram"],

  // 渠道相关的环境变量
  "channelEnvVars": {
    "telegram": ["TELEGRAM_BOT_TOKEN"]
  },

  // 配置验证 schema
  "configSchema": {
    "type": "object",
    "properties": {
      "pollingInterval": { "type": "number" }
    }
  }
}
```

**为什么需要清单文件？**
- 在加载插件代码**之前**就可以验证配置
- 不需要执行插件就能知道插件的能力
- 用于插件市场、搜索、权限控制

**不这样做的后果**：
- 配置错误会导致插件加载失败
- 无法在启动前验证配置有效性
- 插件管理变得非常困难

## 4. index.ts - 插件入口点

```typescript
// extensions/telegram/src/index.ts
import type { ChannelPluginContract } from "openclaw/plugin-sdk/channel-contract";

export function createPlugin(): ChannelPluginContract {
  return {
    id: "telegram",
    channel: { /* 渠道运行时 */ },
    config: { /* 配置验证 */ },
    setup: { /* 安装逻辑 */ },
  };
}
```

**Plugin Contract 的类型**：
- `ChannelPluginContract` - 渠道插件（如 Telegram）
- `ProviderPluginContract` - 模型提供商插件（如 OpenAI）
- `ToolPluginContract` - 工具插件
- `HookPluginContract` - 钩子插件

## 5. 插件类型

### 5.1 Channel Plugin（渠道插件）

负责与具体的消息渠道集成：

```
User ---> Telegram API ---> Channel Plugin ---> Gateway
                         (telegram)           (统一格式)
```

**Telegram Channel 工作流程**：

```
1. bot-handlers.runtime.ts
   - 接收 Telegram webhook/polling
   - 解析消息格式

2. bot-message-context.ts
   - 构建统一的会话上下文
   - 处理回复策略

3. bot-message-dispatch.ts
   - 消息路由到 Agent
   - 处理命令、自然语言消息
```

### 5.2 Provider Plugin（提供商插件）

负责与 AI 模型提供商通信：

```typescript
// 示例：OpenAI Provider Plugin
{
  id: "openai",
  providers: ["openai"],
  providerEndpoints: [
    { endpointClass: "openai", hostSuffixes: ["api.openai.com"] }
  ],
  providerAuthEnvVars: {
    "openai": ["OPENAI_API_KEY"]
  },
  // ...
}
```

### 5.3 Hook Plugin（钩子插件）

在消息处理生命周期中干预行为：

```typescript
// Hook 类型（来自 src/plugins/hook-types.ts）
export type PluginHookName =
  | "before_agent_start"      // Agent 启动前
  | "before_agent_reply"      // Agent 回复前
  | "before_tool_call"        // Tool 调用前
  | "after_tool_call"         // Tool 调用后
  | "before_prompt_build"     // 构建提示前
  | "llm_input"               // LLM 输入时
  | "llm_output"              // LLM 输出时
  | "session_start"           // 会话开始
  | "session_end"             // 会话结束
  | ... // 30+ 种钩子
```

## 6. Hook 系统详解

Hook 是插件最重要的能力之一。它允许你在消息处理的**各个环节**干预：

```
用户消息
    │
    ▼
┌─────────────────────────┐
│    message_received     │ ◄── Hook: 可以修改/拦截消息
└────────────┬────────────┘
             │
             ▼
┌─────────────────────────┐
│      inbound_claim      │ ◄── Hook: 决定是否处理这条消息
└────────────┬────────────┘
             │
             ▼
┌─────────────────────────┐
│   before_agent_start    │ ◄── Hook: Agent 启动前的准备工作
└────────────┬────────────┘
             │
             ▼
┌─────────────────────────┐
│   before_prompt_build   │ ◄── Hook: 构建 AI 提示词之前
└────────────┬────────────┘
             │
             ▼
┌─────────────────────────┐
│   llm_input             │ ◄── Hook: 输入到 LLM 之前
└────────────┬────────────┘
             │
             ▼
         [AI 模型调用]
             │
             ▼
┌─────────────────────────┐
│   llm_output           │ ◄── Hook: LLM 输出之后
└────────────┬────────────┘
             │
             ▼
┌─────────────────────────┐
│   before_tool_call      │ ◄── Hook: 调用工具之前
└────────────┬────────────┘
             │
             ▼
         [Tool 执行]
             │
             ▼
┌─────────────────────────┐
│   after_tool_call       │ ◄── Hook: 工具执行之后
└────────────┬────────────┘
             │
             ▼
┌─────────────────────────┐
│   before_agent_reply    │ ◄── Hook: AI 回复用户之前
└────────────┬────────────┘
             │
             ▼
         回复用户
```

## 7. Hook 执行机制

### 7.1 优先级

Hook 有优先级，数字越小越先执行：

```typescript
// Hook 配置示例
{
  hooks: [
    { name: "before_agent_start", priority: 100, handler: myHook },
    { name: "before_agent_start", priority: 50, handler: anotherHook },
  ]
}
```

### 7.2 错误处理

Hook 可能失败，需要优雅处理：

```typescript
// 来自 hooks.ts
import { formatHookErrorForLog } from "../hooks/fire-and-forget.js";
import { formatErrorMessage } from "../infra/errors.js";

// Hook 错误不会导致整个消息处理失败
// 只记录错误并继续执行
```

### 7.3 异步支持

Hook 支持异步操作：

```typescript
interface PluginHookBeforeAgentStartEvent {
  agentId: string;
  sessionId: string;
  context: PluginHookAgentContext;
}

interface PluginHookBeforeAgentStartResult {
  // 可以返回修改后的配置
  override?: {
    systemPrompt?: string;
    tools?: string[];
  };
  // 或者返回一个延迟执行的 async 操作
}
```

## 8. 插件加载流程

```
配置文件 (openclaw.yaml)
    │
    ▼
┌─────────────────────────────────────┐
│  1. 发现插件 (Discovery)            │
│     - 扫描 plugins/entries         │
│     - 读取 manifest.json5          │
│     - 验证配置                      │
└─────────────┬───────────────────────┘
              │
              ▼
┌─────────────────────────────────────┐
│  2. 激活插件 (Activation)           │
│     - 解析依赖关系                  │
│     - 确定加载顺序                  │
│     - 按需加载（Lazy Loading）       │
└─────────────┬───────────────────────┘
              │
              ▼
┌─────────────────────────────────────┐
│  3. 执行插件 (Execution)            │
│     - 初始化运行时                  │
│     - 挂载 Hooks                    │
│     - 启动服务（如 Channel 监听）    │
└─────────────────────────────────────┘
```

## 9. 插件注册表 (Plugin Registry)

OpenClaw 维护一个插件注册表：

```typescript
// src/plugins/registry.ts (概念)
interface PluginRegistry {
  plugins: Map<string, PluginMetadata>;
  hooks: Map<string, HookHandler[]>;
  channels: Map<string, ChannelRuntime>;
  providers: Map<string, ProviderRuntime>;
}
```

**注册表操作**：
- `register(plugin)` - 注册插件
- `unregister(pluginId)` - 注销插件
- `find(channelId)` - 查找渠道插件
- `listHooks(hookName)` - 列出所有钩子

## 10. 插件示例：Telegram

让我们用 Telegram 插件来理解整个系统：

```typescript
// extensions/telegram/src/channel.ts
export function createTelegramChannelRuntime(): ChannelPluginRuntime {
  return {
    // 消息接收
    async start(bot: TelegramBot) {
      // 设置 webhook 或开始 polling
      await bot.startPolling();
    },

    // 消息处理
    async onUpdate(update: TelegramUpdate) {
      const context = await buildMessageContext(update);
      await dispatchToAgent(context);
    },

    // 消息发送
    async sendMessage(chatId: string, text: string) {
      await bot.api.sendMessage(chatId, text);
    }
  };
}
```

## 11. 插件生命周期

```
安装 (Install)
    │
    ▼
配置 (Configure)
    │
    ▼
启用 (Enable)
    │
    ▼
运行 (Running)
    │         │
    ▼         ▼
  更新      禁用
    │         │
    └────┬────┘
         ▼
    卸载 (Uninstall)
```

**关键方法**：
- `setup()` - 首次安装时调用
- `activate()` - 启用插件
- `deactivate()` - 禁用插件
- `update()` - 更新插件

## 14. 缺点与不足

| 缺点 | 说明 |
|------|------|
| **Hook 版本兼容性** | Hook 签名在不同版本间可能有 Breaking Changes |
| **单点故障** | 一个插件崩溃可能影响整个系统 |
| **调试困难** | 插件在运行时加载，出错难定位 |
| **版本管理复杂** | 插件依赖关系复杂，更新容易出问题 |
| **文档缺失** | 虽然有 docs/ 目录，但实际开发指南不够详细 |

---

## 15. 总结

**插件系统核心概念**：
1. **Manifest-first** - 先读清单，再加载代码
2. **Lazy Loading** - 按需加载，不浪费资源
3. **Hook 机制** - 在生命周期各点干预
4. **Contract-based** - 基于契约的接口定义

**设计亮点**：
- 清单文件使配置验证在代码加载前完成
- 30+ 种 Hook 覆盖了完整生命周期
- 分层架构让插件互不干扰

**设计不足**：
- 插件间通信机制不够清晰
- Hook 的优先级控制略显复杂
- 缺少官方的插件开发调试工具
