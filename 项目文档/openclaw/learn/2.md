  核心知识点详解

  1. Provider 层：为什么要先写 Mock？

  ┌──────────┬─────────────────────────────────────────────────────────┐
  │   考虑   │                          说明                           │
  ├──────────┼─────────────────────────────────────────────────────────┤
  │ 测试成本 │ 真实 API 按 token 收费，调试时反复调用会产生费用        │
  ├──────────┼─────────────────────────────────────────────────────────┤
  │ 开发效率 │ Mock 延迟 100ms，真实 API 可能 2-5 秒，调试节奏差 50 倍 │
  ├──────────┼─────────────────────────────────────────────────────────┤
  │ 确定性   │ Mock 对 "你好" 永远返回固定响应，测试可以精确断言       │
  ├──────────┼─────────────────────────────────────────────────────────┤
  │ 离线开发 │ 没有 API Key 的新成员也能立即运行项目                   │
  └──────────┴─────────────────────────────────────────────────────────┘

  工程细节：MockProvider 也实现了 LLMProvider 接口，这保证了"替换成本极低"——从 Mock
  切到 Anthropic 只需要改工厂函数里的一行代码。

  2. 工厂模式 vs 直接 new

  // ❌ 反面教材：散落在各处的 if-else
  if (config.provider === "anthropic") provider = new AnthropicProvider(...)
  else if (config.provider === "openai") provider = new OpenAIProvider(...)

  // ✅ 工厂模式：集中管理，一处修改
  const provider = createProvider(config.provider, config);

  为什么这很重要？ OpenClaw 原始项目支持 20+ 个
  Provider（Anthropic、OpenAI、Google、Cohere、本地模型等）。如果没有工厂，新增一个
  Provider 要改 N 个文件，必然漏改。

  3. 工具安全设计

  Bash 工具的三层防护：

  ┌────────────┬──────────────────────┬───────────────────────┐
  │    层级    │         机制         │         示例          │
  ├────────────┼──────────────────────┼───────────────────────┤
  │ 黑名单拦截 │ 正则匹配危险命令     │ rm -rf / → blocked    │
  ├────────────┼──────────────────────┼───────────────────────┤
  │ 超时控制   │ exec 的 timeout 选项 │ 防止命令无限挂起      │
  ├────────────┼──────────────────────┼───────────────────────┤
  │ 输出截断   │ maxBuffer + 长度限制 │ 防止 1GB 日志撑爆内存 │
  └────────────┴──────────────────────┴───────────────────────┘

  Read 工具的三层防护：

  ┌────────────────┬──────────────────────┬───────────────────────────────┐
  │      层级      │         机制         │             示例              │
  ├────────────────┼──────────────────────┼───────────────────────────────┤
  │ 工作目录限制   │ resolve() 后比较路径 │ ../../../etc/passwd → blocked │
  ├────────────────┼──────────────────────┼───────────────────────────────┤
  │ 敏感路径黑名单 │ 正则匹配             │ .env、.ssh/ → blocked         │
  ├────────────────┼──────────────────────┼───────────────────────────────┤
  │ 文件大小限制   │ stat() 检查 size     │ > 1MB 的文件 → rejected       │
  └────────────────┴──────────────────────┴───────────────────────────────┘

  为什么不直接依赖操作系统权限？
  - 操作系统权限是"最后一道防线"，不是"唯一防线"
  - 深度防御（Defense in Depth）：每层都检查，一层失效还有其他层
  - AI 工具的错误模式不同于人类用户，需要专门设计规则

  4. 工具注册表（Registry Pattern）

  const registry = new Map<string, ToolFactory>();
  registry.set("bash", createBashTool);
  registry.set("read", createReadTool);

  // 调用方完全解耦
  const tool = getTool("bash"); // 不需要知道 bash 工具是怎么创建的

  为什么用 Map 而不是 Object 或数组？
  - Object：有原型链污染风险，hasOwnProperty 等继承属性会干扰
  - 数组：查找是 O(n)，Map 是 O(1)。工具多了以后差距明显
  - Map：API 语义明确（get/set/has），类型安全更好

  5. 错误处理策略：返回结果 vs 抛异常

  我们的工具都返回 ToolResult（{ success, output?, error? }），而不是抛异常。

  为什么？
  场景：AI 让用户执行 "cat /root/secret.txt"，权限不足。

  如果抛异常：
    → 异常被 catch 后变成 "Unknown error"
    → AI 不知道发生了什么，无法告诉用户"权限不够"
    → 用户体验差

  如果返回 ToolResult：
    → AI 看到 { success: false, error: "Permission denied" }
    → AI 可以在回复中说："我没有权限读取这个文件，你可以用 sudo
  或者把文件复制到工作目录"
    → 用户得到有用的反馈

  这是"错误作为值"（Error as Value）的设计哲学，在 Rust、Go 中很常见。JavaScript
  中虽然用异常更普遍，但在 Agent 系统里，让 LLM 知道错误细节 是核心需求。

  目前设计的缺点

  ┌─────────────────┬────────────────────────────────────────────────────────────┐
  │      缺点       │                            说明                            │
  ├─────────────────┼────────────────────────────────────────────────────────────┤
  │ MockProvider    │ 没有真正的"推理"能力，只是关键词匹配。真实 LLM             │
  │ 太简单          │ 通过数十亿参数理解语义。                                   │
  ├─────────────────┼────────────────────────────────────────────────────────────┤
  │ Bash 安全策略不 │ 黑名单容易被绕过（如 sh -c 'rm -rf /'）。原始 OpenClaw     │
  │ 够精细          │ 用了进程级沙箱（nsjail）。                                 │
  ├─────────────────┼────────────────────────────────────────────────────────────┤
  │ Read 不支持二进 │ 图片、PDF 等二进制文件读取会乱码。原始项目有文件类型检测和 │
  │ 制文件          │ 二进制处理。                                               │
  ├─────────────────┼────────────────────────────────────────────────────────────┤
  │ 工具没有版本控  │ 如果 Tool 的 schema                                        │
  │ 制              │ 变了，已有配置可能不兼容。原始项目有工具契约（Tool         │
  │                 │ Contract）系统。                                           │
  ├─────────────────┼────────────────────────────────────────────────────────────┤
  │ 没有工具调用格  │ 现在的代码只定义了 Tool 接口，但 LLM                       │
  │ 式              │ 还不知道"怎么调用"工具。下一节会讲如何把 Tool schema       │
  │                 │ 转换成 LLM 能理解的格式（JSON Schema / XML）。             │
  ├─────────────────┼────────────────────────────────────────────────────────────┤
  │ 缺少超时测试    │ 没有验证 bash 工具的 timeout 是否真正生效（需要 mock exec  │
  │                 │ 或启动慢命令）。                                           │
  └─────────────────┴────────────────────────────────────────────────────────────┘
