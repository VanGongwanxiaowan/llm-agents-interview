  ---
  第一步：项目骨架搭建                                                               
                                                                  
  一个 TypeScript 项目最基础需要三个东西：
  - package.json — 项目元数据和依赖
  - tsconfig.json — TypeScript 编译配置
  - src/ 目录 — 源代码

  为什么这样设计目录结构？

  OpenClaw 的核心架构是分层设计，所以源码目录也要体现这种分层：
  src/
    types/       — 所有接口定义放这里，解耦各层之间的依赖
    provider/    — AI 模型提供商抽象
    agent/       — AI 对话核心
    channel/     — 消息渠道接入
    gateway/     — 消息路由中心
    plugin/      — 扩展机制
    tools/       — 内置工具实现
    entry.ts     — 程序入口

  工程细节：把 types/ 单独放一个目录，而不是散落在各个模块里。这样做的好处是：
  - 任何模块想引用类型，只需要 import { ... } from '../types'
  - 避免循环依赖（如果 A 模块的类型定义在 A 里，B 引用 A 的类型，A 又引用 B
  的代码，就会循环依赖）
  - 新成员看代码时，先看 types/ 就能理解整个系统的数据结构

  如果不这样做会怎样？
  - 类型散落在各个文件里，找起来困难
  - 很容易出现循环 import，导致编译失败或运行时异常
  - 重构时牵一发而动全身

  第二步：核心类型定义

  类型定义是整个系统的契约。所有模块都基于这些类型来协作。先写类型的好处是：
  - 强制你思考清楚数据结构和边界
  - 编译器帮你检查各模块是否遵守契约
  - 后续改实现时，只要类型不变，就不会破坏其他模块

  为什么先写类型，而不是先写 Gateway？

  这是很多新手会困惑的地方。答案是：类型是设计文档。如果你先写 Gateway，写到一半发现
  "哦，原来 Session 需要这个字段"，就得回头改
  Gateway。先定义类型，相当于先画好蓝图再施工。

  另一个工程上的原因是：TypeScript
  的接口可以跨文件引用，但不会引入运行时依赖。你可以在 types/index.ts 里定义一万个接
  口，编译后这些代码会完全消失（被擦除），不会影响包体积。所以大胆地把类型写清楚。

  2. 类型设计的核心思路

  我们把 OpenClaw 的所有数据契约抽象成了 10 组类型：

  1. Message — 统一消息格式（解决多渠道格式差异问题）
  2. Session — 保存对话历史（解决 LLM 无状态问题）
  3. AgentConfig — 静态配置（可序列化，可存配置文件）
  4. Tool / ToolResult / ToolContext — 工具的三件套
  5. LLMProvider — 策略模式，解耦具体 AI 模型
  6. ChannelRuntime — 渠道的统一接口
  7. PluginManifest / PluginRuntime — Manifest-first 设计
  8. HookName / HookEvent / HookHandler — 生命周期干预
  9. GatewayConfig — 顶层配置聚合
  10. 工具函数 — generateId()、createMessage() 工厂函数

  3. 关键工程细节

  为什么用工厂函数 createMessage() 而不是直接构造对象？

  想象三个月后，你给 Message 加了一个必填字段
  channelId。如果你之前在所有代码里都是直接写 { id, role, content, timestamp
  }，现在得改几十处。但如果你一直用 createMessage(role,
  content)，只需要在工厂函数里加参数默认值，其他代码自动生效。

  原始 OpenClaw 的真实做法：实际上原始项目很少用工厂函数，而是直接构造对象。这在小范
  围迭代时没问题，但项目大了以后确实会增加重构成本。我们这里展示的是更工程化的做法。

  为什么 AgentConfig.tools 是 string[] 而不是 Tool[]？

  因为 Tool 接口里包含 handler 函数，而函数是不可序列化的。配置应该能存成
  JSON、能写进 YAML 文件、能通过环境变量传递。如果 tools 是
  Tool[]，就没法做这些了。用名称引用，启动时再查找对应的实现，这是配置与实现的分离。
