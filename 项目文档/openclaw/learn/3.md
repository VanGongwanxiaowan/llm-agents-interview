  核心知识点详解

  1. Agent 的核心流程：工具调用循环

  这是 Agent 和普通 LLM 聊天的根本区别：

  用户: "列出当前目录"
    │
    ▼
  Agent.processMessage()
    │
    ├── 1. 添加用户消息到历史
    │
    ├── 2. 构建 System Prompt（角色定义 + 工具说明）
    │
    ├── 3. 调用 LLM.generate()
    │      LLM 返回: "```tool_call\n{"name":"bash","params":{"command":"ls
  -la"}}\n```"
    │
    ├── 4. 检测到工具调用
    │      ├── 解析 JSON → { name: "bash", params: { command: "ls -la" } }
    │      ├── 查找 Tool 实现
    │      ├── 执行 tool.handler() → { success: true, output: "total 32..." }
    │      └── 把结果加入历史
    │
    ├── 5. 再次调用 LLM.generate()（循环）
    │      这次历史包含了工具结果
    │      LLM 返回: "根据命令执行结果，我已经看到了目录/文件列表..."
    │
    ├── 6. 没有工具调用 → 返回最终回复
    │
    └── 7. 添加助手回复到历史

  为什么要循环调用 LLM？

  因为 LLM 本身不能"记住"它之前调用了什么工具。每次 API 调用都是独立的。要让 LLM
  知道工具执行了什么、结果是什么，必须把结果作为新的消息加入历史，再次调用 LLM。

  ▎ 工程细节：原始 OpenClaw 把这个循环叫做 "Turn"（轮次），每一轮包括 LLM 调用 +
  可能的工具执行。复杂任务可能有 5-10 轮。

  2. SessionManager 的裁剪策略

  当对话历史越来越长时，LLM 的上下文窗口会不够用（还要花钱）。SessionManager
  自动裁剪：

  ┌────────────┬────────────────────────────────┬───────────────────────────────┐
  │    策略    │            触发条件            │             操作              │
  ├────────────┼────────────────────────────────┼───────────────────────────────┤
  │ 消息数限制 │ > maxHistoryMessages (默认 50) │ 成对删除最早的消息            │
  ├────────────┼────────────────────────────────┼───────────────────────────────┤
  │ Token 限制 │ > maxContextTokens (默认 4000) │ 估算 token 数，超限时成对删除 │
  └────────────┴────────────────────────────────┴───────────────────────────────┘

  为什么"成对删除"？

  消息是对话的基本单位：用户问 → 助手答。如果删了用户的问题但保留了助手的回答，LLM
  看到 "Assistant: 答案是 42" 却不知道问题是什么，会困惑。

  Token 估算公式

  // 保守估计：每个 token 约 2 个字符（混合中英文）
  estimatedTokens = Math.ceil(totalChars / 2);

  为什么不引入 tiktoken（OpenAI 的官方 token 计数库）？
  - tiktoken 是原生模块（Rust 编译），安装可能失败
  - 我们的目标是学习核心概念，不是精确计费
  - 估算够用，留 20% 余量即可

  原始 OpenClaw 实际怎么做？
  - 也做粗略估算，但会处理 API 返回的 "context length exceeded" 错误
  - 有消息摘要（summarization）功能：把旧消息压缩成一段摘要，而不是直接删除

  3. ToolFormatter：文本格式的工具调用

  我们没有对接真实的 Claude/GPT API（它们有原生的 Function
  Calling），而是用了文本格式：

  System Prompt 中的工具说明：
  你可以使用以下工具来完成任务。如果需要使用工具，请按以下格式输出：

  ```tool_call
  {"name": "工具名称", "params": {"参数名": "参数值"}}

  可用工具列表：

  bash

  描述：Execute a bash shell command...
  参数：
  - command (string, required): The shell command to execute
  - timeout (number, optional): Maximum execution time...

  **LLM 的输出：**
  好的，我来帮你查看。

  {"name": "bash", "params": {"command": "ls -la"}}

  **解析方式：**
  ```typescript
  const regex = /```tool_call\n([\s\S]*?)\n```/g;

  为什么不直接用原生 Function Calling API？

  ┌───────────────────────┬──────────────────────────┬───────────────────────────┐
  │         方案          │           优点           │           缺点            │
  ├───────────────────────┼──────────────────────────┼───────────────────────────┤
  │ 文本格式（我们的方案  │ 任何 LLM 都能用；不依赖  │ 可靠性稍低；消耗更多      │
  │ ）                    │ Provider API；易于调试   │ token                     │
  ├───────────────────────┼──────────────────────────┼───────────────────────────┤
  │ 原生 Function Calling │ 可靠性高；格式严格；toke │ 每个 Provider 格式不同；  │
  │                       │ n 效率好                 │ 本地小模型不支持          │
  └───────────────────────┴──────────────────────────┴───────────────────────────┘

  对于学习项目，文本格式更合适。原始 OpenClaw 实际用了 Provider 插件来适配不同 API
  的原生格式。

  4. Agent 类的依赖注入设计

  const agent = new Agent({
    config: { ... },      // 静态配置
    provider: provider,   // LLM 实例
    tools: [bash, read],  // 工具实例数组
  });

  为什么用依赖注入而不是在 Agent 内部硬编码？

  1. 测试友好：测试时可以传入 MockProvider，不用真的调用 API
  2. 灵活替换：今天用 Claude，明天换 GPT，只改 provider 参数
  3. 工具动态加载：插件系统可以在运行时添加/移除工具
  4. 配置与实现分离：config 是纯数据（可序列化），provider 和 tools 是运行时对象

  原始 OpenClaw 的复杂度：实际项目中 Agent 不直接持有 Provider，而是通过
  ProviderRuntime 插件动态解析。还有模型回退（model fallback）：Claude 失败时自动切
  GPT。

  5. MockProvider 的工具模拟

  这是测试的关键创新。MockProvider 能"假装"理解工具：

  用户说"列出文件" → MockProvider 返回工具调用格式
  Agent 执行工具 → 把结果加入历史
  再次调用 LLM → MockProvider 看到历史中有工具结果 → 返回总结回复

  为什么这样设计？
  - 不连接真实 API，就能验证完整的工具调用循环
  - 测试速度快（没有网络延迟）
  - 确定性高（每次测试结果一致）

  目前设计的缺点

  ┌───────────────────────┬──────────────────────────────────────────────────────┐
  │         缺点          │                         说明                         │
  ├───────────────────────┼──────────────────────────────────────────────────────┤
  │ 文本格式工具调用不够  │ LLM 可能输出格式错误的                               │
  │ 可靠                  │ JSON，或把工具调用和普通文本混在一起。真实项目用     │
  │                       │ Provider 的原生 API 更可靠。                         │
  ├───────────────────────┼──────────────────────────────────────────────────────┤
  │ 没有错误恢复          │ 如果 LLM API 调用失败（网络错误、超时），Agent       │
  │                       │ 直接抛异常。原始 OpenClaw 有重试策略和模型回退。     │
  ├───────────────────────┼──────────────────────────────────────────────────────┤
  │ 工具结果角色处理简化  │ 我们把工具结果当作 assistant 消息，但真实 API（如    │
  │                       │ Anthropic）有专门的 tool_result 角色。               │
  ├───────────────────────┼──────────────────────────────────────────────────────┤
  │                       │ Agent 的 processMessage()                            │
  │ 没有流式输出          │ 只返回最终结果。用户要等全部生成完才能看到回复。原始 │
  │                       │  OpenClaw 支持流式传输，让用户看到"打字机效果"。     │
  ├───────────────────────┼──────────────────────────────────────────────────────┤
  │ System Prompt         │ 没有动态上下文注入（如当前工作目录、最近修改的文件） │
  │ 构建太简单            │ 。Claude Code 的 system prompt                       │
  │                       │ 有几百行，包含详细的操作指南。                       │
  ├───────────────────────┼──────────────────────────────────────────────────────┤
  │ SessionManager        │ 重启程序后对话历史丢失。原始项目会保存到 SQLite      │
  │ 没有持久化            │ 或文件。                                             │
  ├───────────────────────┼──────────────────────────────────────────────────────┤
  │ 没有并发控制          │ 同一个 Session 如果同时收到多条消息，可能产生竞态条  │
  │                       │ 件（消息顺序错乱）。                                 │
  ├───────────────────────┼──────────────────────────────────────────────────────┤
  │ 单进程架构限制        │ 所有 Agent                                           │
  │                       │ 运行在同一个进程，一个工具卡死会影响整个系统。       │
  └───────────────────────┴──────────────────────────────────────────────────────┘
