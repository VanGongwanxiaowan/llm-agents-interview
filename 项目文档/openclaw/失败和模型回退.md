# 失败恢复与模型回退机制详解

## 概述

OpenClaw 的 Agent 在真实线上场景中面对的错误是多元化的：API Key 失效、Rate Limit、上下文溢出、模型不支持当前 Thinking Level 等。该项目设计了一套**三层恢复策略**，逐层尝试修复或绕过错误，只有当前层无法恢复时才会进入下一层。

```
LLM 调用失败
    │
    ▼
[第一层] Thinking 降级 —— 模型不支持当前思考级别
    │
    ▼
[第二层] Auth Profile 轮换 —— 换一个 API Key / 凭证
    │
    ▼
[第三层] 模型级 Fallback —— 换到另一个模型
```

---

## 一、错误分类：一切判断的起点

在三层恢复之前，系统需要先**判断错误类型**，这是整个恢复链路的决策依据。

### 核心文件

- `src/agents/pi-embedded-helpers/errors.ts` — 上下文溢出判断
- `src/agents/pi-embedded-helpers/failover-matches.ts` — 速率限制/认证/计费等模式匹配

### 1.1 上下文溢出（Context Overflow）检测

**为什么重要？** 上下文溢出不应该尝试模型切换，因为另一个模型可能上下文窗口更小，反而失败更严重。系统会直接暴露错误给用户，而不是浪费一次 Fallback 机会。

```typescript
// src/agents/pi-embedded-helpers/errors.ts:74-119

export function isContextOverflowError(errorMessage?: string): boolean {
  if (!errorMessage) return false;
  const lower = errorMessage.toLowerCase();

  // Groq 用 413 代表 TPM（每分钟 Token 数）限制，这是速率限制，不是上下文溢出
  if (hasRateLimitTpmHint(errorMessage)) return false;

  if (isReasoningConstraintErrorMessage(errorMessage)) return false;

  const hasRequestSizeExceeds = lower.includes("request size exceeds");
  const hasContextWindow =
    lower.includes("context window") ||
    lower.includes("context length") ||
    lower.includes("maximum context length");

  return (
    lower.includes("request_too_large") ||
    lower.includes("request exceeds the maximum size") ||
    lower.includes("context length exceeded") ||
    lower.includes("maximum context length") ||
    lower.includes("prompt is too long") ||
    lower.includes("exceeds model context window") ||
    lower.includes("model token limit") ||              // 新增
    (hasRequestSizeExceeds && hasContextWindow) ||      // 组合判断
    lower.includes("context overflow:") ||
    lower.includes("exceed context limit") ||
    lower.includes("exceeds the model's maximum context") ||
    (lower.includes("max_tokens") && lower.includes("exceed") && lower.includes("context")) ||
    (lower.includes("input length") && lower.includes("exceed") && lower.includes("context")) ||
    (lower.includes("413") && lower.includes("too large")) ||
    lower.includes("context_window_exceeded") ||         // Anthropic / OpenAI 兼容接口
    // 中文代理错误消息
    errorMessage.includes("上下文过长") ||
    errorMessage.includes("上下文超出") ||
    errorMessage.includes("上下文长度超") ||
    errorMessage.includes("超出最大上下文") ||
    errorMessage.includes("请压缩上下文")
  );
}
```

**处理细节：**

1. **TPM Hint 排除**：Groq 的 413 是 Rate Limit 不是 Context Overflow，需要通过 `hasRateLimitTpmHint` 排除
2. **中文支持**：国内代理常见中文错误消息，需要显式匹配
3. **组合判断**：`request size exceeds` + `context window` 同时出现才算（避免单独出现时的误判）
4. **宽松版本** `isLikelyContextOverflowError`：额外使用正则兜底，但会先排除 Billing、Rate Limit、Context Window 太小的模型

### 1.2 其他错误类型模式匹配

`failover-matches.ts` 使用**正则 + 字符串包含**的混合模式：

```typescript
// src/agents/pi-embedded-helpers/failover-matches.ts:6-103

const ERROR_PATTERNS = {
  rateLimit: [
    /rate[_ ]limit|too many requests|429/,
    "model_cooldown",
    "exceeded your current quota",
    "resource_exhausted",
    /\btpm\b/i,                           // 避免和 context overflow 混淆
    "tokens per minute",
  ],
  overloaded: [
    /overloaded_error/i,
    "overloaded",
    /service[_ ]unavailable.*(?:overload|capacity|high[_ ]demand)/i,  // 需要组合
  ],
  timeout: [
    "timeout", "timed out",
    /\betimedout\b/i, /\beconnrefused\b/i, /\besockettimedout\b/i,
  ],
  billing: [
    /["']?(?:status|code)["']?\s*[:=]\s*402\b/,  // HTTP 402
    "insufficient credits",
    "credit balance",
  ],
  auth: [
    /invalid[_ ]?api[_ ]?key/,
    "incorrect api key",
    "unauthorized", "forbidden",
  ],
};
```

**设计意图**：每个错误类型对应一种 `FailoverReason`，不同 Reason 在恢复时有不同的处理策略。

### 1.3 FailoverReason 类型

```typescript
// src/agents/failover-error.ts:46-69

type FailoverReason =
  | "auth"              // 认证失败（401）
  | "auth_permanent"    // API Key 被撤销/禁用（403）
  | "rate_limit"        // 速率限制（429）
  | "billing"           // 计费/余额问题（402）
  | "overloaded"        // 服务过载（503）
  | "timeout"           // 请求超时
  | "format"            // 请求格式错误（400/422）
  | "model_not_found"   // 模型不存在
  | "session_expired"   // 会话过期
  | "unknown";
```

**关键决策规则**：

- `timeout` → **不触发 Auth Profile 轮换**（因为超时是网络问题，不是认证问题；而且标记超时会导致同一 provider 的其他模型也无法使用该 profile）
- `context_overflow` → **不触发模型 fallback**（其他模型可能更小）
- `auth` / `billing` / `rate_limit` / `overloaded` → 可以触发 Auth Profile 轮换

## 二、第一层恢复：Thinking Level 降级

### 核心文件

- `src/agents/pi-embedded-helpers/thinking.ts`

### 2.1 问题场景

某些模型（如 Claude Opus）支持 `thinking` 参数（允许低/中/高思考级别），但换到另一个不支持该级别的模型时，API 会直接拒绝请求，返回类似：

```
supported values are: none, low, medium
```

### 2.2 从错误消息中提取支持的级别

```typescript
// src/agents/pi-embedded-helpers/thinking.ts:3-20

function extractSupportedValues(raw: string): string[] {
  const match =
    raw.match(/supported values are:\s*([^\n.]+)/i) ??
    raw.match(/supported values:\s*([^\n.]+)/i);
  if (!match?.[1]) return [];

  const fragment = match[1];

  // 优先提取被引号包裹的值（更精确）
  const quoted = Array.from(fragment.matchAll(/['"]([^'"]+)['"]/g))
    .map((entry) => entry[1]?.trim());
  if (quoted.length > 0) {
    return quoted.filter(Boolean);
  }

  // 否则按逗号或 "and" 分割
  return fragment
    .split(/,|\band\b/gi)
    .map((entry) => entry.replace(/^[^a-zA-Z]+|[^a-zA-Z]+$/g, "").trim())
    .filter(Boolean);
}
```

**解析示例**：

| 错误消息 | 提取结果 |
|---------|---------|
| `supported values: "none", "low", "medium"` | `["none", "low", "medium"]` |
| `supported values are: none, low and medium` | `["none", "low", "medium"]` |
| `think value "low" is not supported` | `[]`（进入兜底逻辑） |

### 2.3 选择降级目标

```typescript
// src/agents/pi-embedded-helpers/thinking.ts:22-53

export function pickFallbackThinkingLevel(params: {
  message?: string;
  attempted: Set<ThinkLevel>;  // 已尝试过的级别
}): ThinkLevel | undefined {
  const raw = params.message?.trim();
  if (!raw) return undefined;

  const supported = extractSupportedValues(raw);
  if (supported.length === 0) {
    // 当错误消息明确说"不支持"但没有列出支持列表时的兜底
    // 典型场景：从 Anthropic（有 thinking level）换到不支持的 provider
    if (/not supported/i.test(raw) && !params.attempted.has("off")) {
      return "off";  // 降级到关闭思考
    }
    return undefined;
  }

  for (const entry of supported) {
    const normalized = normalizeThinkLevel(entry);
    if (!normalized) continue;
    if (params.attempted.has(normalized)) continue;  // 跳过已尝试的
    return normalized;
  }
  return undefined;
}
```

### 2.4 调用位置（在 run.ts 的重试循环中）

```typescript
// src/agents/pi-embedded-runner/run.ts:1402-1411（prompt 阶段）
// src/agents/pi-embedded-runner/run.ts:1437-1446（assistant 阶段）

// 在 Auth Profile 轮换之后
const fallbackThinking = pickFallbackThinkingLevel({
  message: errorText,
  attempted: attemptedThinking,
});
if (fallbackThinking) {
  log.warn(`unsupported thinking level for ${provider}/${modelId}; retrying with ${fallbackThinking}`);
  thinkLevel = fallbackThinking;
  continue;   // 同一模型，重试
}
```

**工作流程**：

1. 错误发生 → 调用 `pickFallbackThinkingLevel` 从错误消息解析支持的级别
2. 如果有未尝试的级别 → 降级该级别，`continue` 重试（同模型，同 profile）
3. 如果没有可降级级别 → 退出 thinking 降级，进入下一层（Auth Profile 轮换）

**设计要点**：Thinking 降级是**最轻量的恢复手段**，发生在最内层循环，不涉及网络请求或 API Key 切换，只改变请求参数。

## 三、第二层恢复：Auth Profile 轮换

### 核心文件

- `src/agents/pi-embedded-runner/run.ts` — `advanceAuthProfile` 函数
- `src/agents/auth-profiles.ts` — Profile 冷却期管理

### 3.1 问题场景

一个 API Key 遇到 Rate Limit / Auth 错误 / Billing 问题，不代表所有 Key 都有问题。用户可能配置了多个 API Key（多个 Profile），系统应该尝试换一个 Key 重试。

### 3.2 advanceAuthProfile 实现

```typescript
// src/agents/pi-embedded-runner/run.ts:710-735

const advanceAuthProfile = async (): Promise<boolean> => {
  if (lockedProfileId) {
    return false;  // 锁定的 profile 不允许切换（如 prompt 中已使用过的）
  }

  let nextIndex = profileIndex + 1;
  while (nextIndex < profileCandidates.length) {
    const candidate = profileCandidates[nextIndex];
    // 跳过在冷却中的 profile
    if (candidate && isProfileInCooldown(authStore, candidate)) {
      nextIndex += 1;
      continue;
    }
    try {
      await applyApiKeyInfo(candidate);  // 应用新 Key
      profileIndex = nextIndex;
      thinkLevel = initialThinkLevel;     // 重置 thinking 级别
      attemptedThinking.clear();          // 清空已尝试的 thinking 记录
      return true;
    } catch (err) {
      if (candidate && candidate === lockedProfileId) {
        throw err;  // 锁定 profile 失败，直接抛错
      }
      nextIndex += 1;  // 尝试下一个
    }
  }
  return false;  // 没有更多可用 profile
};
```

### 3.3 冷却期（Cooldown）机制

Profile 失败后不会被立即重新选择，而是进入**指数退避冷却期**：

```typescript
// Profile 失败后标记
await markAuthProfileFailure({
  profileId: lastProfileId,
  reason: promptProfileFailureReason,
});

// 判断所有 profile 是否都在冷却中
const allAutoProfilesInCooldown = autoProfileCandidates.every(
  (candidate) => isProfileInCooldown(authStore, candidate)
);
```

冷却期的好处：
- **Auth 失败**：Key 可能已被撤销，短期内重试无意义
- **Rate Limit**：等待 provider 的时间窗口
- **Billing**：余额问题不会在短时间内自行恢复

### 3.4 调用条件（在 run.ts 的错误决策树中）

```typescript
// src/agents/pi-embedded-runner/run.ts:1393-1401（prompt 阶段）
// src/agents/pi-embedded-runner/run.ts:1508-1532（assistant 阶段）

const promptFailoverReason =
  promptErrorDetails.reason ?? classifyFailoverReason(errorText);

const promptFailoverFailure =
  promptFailoverReason !== null || isFailoverErrorMessage(errorText);

// 条件：可 failover 的错误 + 非超时 + 还有可用 profile

  promptFailoverFailure &&
  promptFailoverReason !== "timeout" &&  // ← 超时不轮换 profile

```

### 3.5 throwAuthProfileFailover — 轮换失败时

```typescript
// src/agents/pi-embedded-runner/run.ts:613-641

const throwAuthProfileFailover = (params: {
  allInCooldown: boolean;
  message?: string;
  error?: unknown;
}): never => {
  const reason = resolveAuthProfileFailoverReason({
    allInCooldown: params.allInCooldown,
    message,
    profileIds: profileCandidates,
  });

  if (fallbackConfigured) {
    throw new FailoverError(message, {
      reason,
      provider,
      model: modelId,
      status: resolveFailoverStatus(reason),
      cause: params.error,
    });
  }
  // 无 fallback 配置时直接抛原始错误
  if (params.error instanceof Error) throw params.error;
  throw new Error(message);
};
```

**关键逻辑**：

1. 如果配置了模型 fallback → 抛出 `FailoverError`，交给外层 `runWithModelFallback` 处理
2. 如果没有配置 fallback → 直接抛出原始错误（用户需要看到具体错误）

### 3.6 冷却探测（Cooldown Probe）

当**所有 Profile 都在冷却中**时，系统仍可能在特定条件下**探测性尝试**：

```typescript
// src/agents/model-fallback.ts:384-407

function shouldProbePrimaryDuringCooldown(params: {
  isPrimary: boolean;
  hasFallbackCandidates: boolean;
  now: number;
  throttleKey: string;
  authStore: ...;
  profileIds: string[];
}): boolean {
  if (!params.isPrimary || !params.hasFallbackCandidates) return false;
  if (!isProbeThrottleOpen(params.now, params.throttleKey)) return false;  // 30s 最小间隔

  const soonest = getSoonestCooldownExpiry(params.authStore, params.profileIds);
  if (soonest === null) return true;  // 无已知过期时间，探测

  // 冷却即将过期时探测（给用户一个快速恢复的机会）
  return params.now >= soonest - PROBE_MARGIN_MS;  // 2分钟 margin
}
```

这实现了"**不白等**"策略：冷却期快要结束时，主动探测一次看是否已恢复，避免用户等待完整的冷却时间。

### 核心文件

- `src/agents/model-fallback.ts`

### 4.1 runWithModelFallback 函数签名

```typescript
// src/agents/model-fallback.ts:511-521

export async function runWithModelFallback<T>(params: {
  cfg: OpenClawConfig | undefined;
  provider: string;
  model: string;
  agentDir?: string;

   * 显式 fallback 列表；提供时（即使为空）替换 agents.defaults.model.fallbacks
   * - undefined：使用 config 中的 fallback
   * - []（空数组）：禁用 fallback（只尝试主模型）
```

### 4.2 候选模型列表构建

```typescript
// src/agents/model-fallback.ts:258-333

function resolveFallbackCandidates(params: {
  cfg: OpenClawConfig | undefined;
  provider: string;
  model: string;
  fallbacksOverride?: string[];
}): ModelCandidate[] {
  // 1. 加入主模型
  addExplicitCandidate(normalizedPrimary);

  // 2. 确定 fallback 列表来源
  const modelFallbacks = (() => {
    if (params.fallbacksOverride !== undefined) {
      return params.fallbacksOverride;  // override 完全替换
    }
    return resolveAgentModelFallbackValues(params.cfg?.agents?.defaults?.model);
  })();

  // 3. 解析每个 fallback 字符串（支持 "gpt-4" → "openai/gpt-4" 的自动补全）
  for (const raw of modelFallbacks) {
    const resolved = resolveModelRefFromString({ raw, defaultProvider, aliasIndex });
    if (!resolved) continue;
    addExplicitCandidate(resolved.ref);
  }

  return candidates;  // [主模型, fallback1, fallback2, ...]
}
```

**fallbacksOverride 的精确语义**（易错点）：

| 值 | 行为 |
|----|------|
| `undefined` | 使用 `config.agents.defaults.model.fallbacks` |
| `[]`（空数组） | **禁用 fallback**，只尝试主模型 |
| `["openai/gpt-4.1"]` | 用这个列表**完全替换** config 中的 fallback |

### 4.3 循环尝试候选模型

```typescript
// src/agents/model-fallback.ts:537-762（核心循环）

for (let i = 0; i < candidates.length; i += 1) {
  const candidate = candidates[i];
  const isPrimary = i === 0;
  const requestedModel = params.provider === candidate.provider && params.model === candidate.model;

  // 检查冷却状态（上面已详述）
  // ...

  const attemptRun = await runFallbackAttempt({
    run: params.run,
    provider: candidate.provider,
    model: candidate.model,
    attempts,
    options: runOptions,
  });

  if ("success" in attemptRun) {
    // 成功：记录日志，返回结果
    return attemptRun.success;
  }

  // 失败：分类处理
  const err = attemptRun.error;

  // [关键] 上下文溢出错误不尝试下一个模型，直接上抛
  if (isLikelyContextOverflowError(errMessage)) {
    throw err;
  }

  // 标准化为 FailoverError
  const normalized = coerceToFailoverError(err, {...}) ?? err;

  // 非 FailoverError：不重试，直接抛（业务逻辑错误，如用户 query 格式问题）
  if (!isFailoverError(normalized)) {
    if (i === candidates.length - 1) throw err;  // 最后一个候选也失败才抛
    continue;  // 实际上这里永远不会到，因为最后一个候选失败时会 throw
  }

  // 记录失败尝试，继续下一个候选
  lastError = normalized;
  attempts.push({
    provider: candidate.provider,
    model: candidate.model,
    error: described.message,
    reason: described.reason,
    status: described.status,
    code: described.code,
  });
  await params.onError?.({...});
}

// 所有候选都失败
throwFallbackFailureSummary({ attempts, candidates, lastError, ... });
```

### 4.4 为什么只有 FailoverError 才触发 Fallback？

这是**设计决策**，不是 bug：

- **业务逻辑错误**（如用户 query 格式问题、权限不足）：应该立即返回给用户，不应该被 fallback 消化。用户换一个模型也无法解决格式错误。
- **可恢复错误**（Rate Limit、Auth 过期、Billing）：换一个模型/Key 可能解决。

如果你的 `run` 函数抛出非 `FailoverError`，fallback 链会在第一个模型失败时直接终止。要触发 fallback，需要先转换为 `FailoverError`：

```typescript
// 自定义 run 函数中
if (isRateLimited(err)) {
  throw new FailoverError(err.message, {
    reason: "rate_limit",
    provider,
    model,
  });
}
```

### 4.5 FallbackAttempt 记录

每次失败都记录到 `attempts` 数组，供最终错误汇总：

最终失败时的错误消息格式：

```

```

## 五、三层恢复完整决策树

```
LLM 调用失败
    │
    ▼
classifyFailoverReason(errorText)  ──→ 判断是否可 failover
    │
    ├─ 不是 failover 错误 → 直接抛给用户
    │
    └─ 是 failover 错误
            │
            ▼
    [第一层] Thinking 降级（同一模型，同一 profile）
            pickFallbackThinkingLevel(errorText, attemptedThinking)
            │
            ├─ 有可降级 level → thinkLevel = 新级别，continue 重试
            │                         ✓ 成功 → 返回结果
            │                         ✗ 失败 → 回到决策树顶部
            │
            └─ 无可降级 level
                    │
                    ▼
            [第二层] Auth Profile 轮换（同一模型）
                    advanceAuthProfile()
                    │
                    ├─ 有可用 profile → applyApiKeyInfo，continue 重试
                    │                         ✓ 成功 → 返回结果
                    │                         ✗ 失败 → 回到决策树顶部
                    │
                    └─ 全部冷却
                            │
                            ▼
                    throwAuthProfileFailover()
                            │
                            ├─ fallbackConfigured = true → throw FailoverError
                            │                                    │
                            ▼                                    ▼
                    [第三层] 模型级 Fallback               [外层 runWithModelFallback]
                    runWithModelFallback                           │
                    candidates = [主模型, ...fallbacks]            │
                    for each candidate:                            │
                      run(candidate)                               │
                      │
                      ├─ 成功 → 返回 result + attempts            │
                      │                                            │
                      └─ FailoverError → 记录 attempts，继续下一个│
                                                            │
                                                    全部失败 → throw 汇总错误
```

## 六、run.ts 内部的重试循环结构

`run.ts` 中的**主重试循环**是两层嵌套的：

```typescript
// src/agents/pi-embedded-runner/run.ts:816-818

const MAX_OVERFLOW_COMPACTION_ATTEMPTS = 3;
const MAX_RUN_LOOP_ITERATIONS = resolveMaxRunRetryIterations(profileCandidates.length);
let overflowCompactionAttempts = 0;
let toolResultTruncationAttempted = false;

// 外层大循环（处理 profile 轮换、thinking 降级后的重试）
while (true) {
  // ... 初始化 ...

  try {
    // 内层：真正的 LLM 调用
    attempt = await runPiAssistant({...});
    break;  // 成功，退出循环
  } catch (err) {
    // 根据错误类型走三层恢复
    if (shouldFallbackToModel(err)) {
      throw new FailoverError(...);  // 进入 runWithModelFallback
    }

    const shouldRetry = await maybeHandleError(err);
    if (!shouldRetry) throw err;
    // 否则 continue 继续循环（可能是 thinking 降级或 profile 轮换后重试）
  }
}
```

## 八、开发避坑指南

### 1. 自定义 run 函数要正确抛出 FailoverError

```typescript
// ❌ 错误：抛普通 Error，fallback 不会触发
if (isRateLimited(err)) throw new Error("rate limited");

// ✅ 正确：抛 FailoverError，fallback 会尝试下一个模型
if (isRateLimited(err)) {
  throw new FailoverError("rate limited", {
    reason: "rate_limit",
    provider,
    model,
  });
}
```

### 2. `fallbacksOverride = []` 和 `undefined` 含义不同

```typescript
// 使用 config 中的 fallback
runWithModelFallback({ ... });

// 禁用 fallback，只尝试主模型
runWithModelFallback({ fallbacksOverride: [], ... });
```

### 3. Timeout 不触发 Auth Profile 轮换

```typescript
// 在 run.ts 中的判断
if (
  promptFailoverFailure &&
  promptFailoverReason !== "timeout" &&  // ← 必须条件
  (await advanceAuthProfile())
) { ... }
```

**原因**：Timeout 是网络问题，不是认证问题。标记 Timeout 会导致同一 provider 下其他模型也无法使用该 profile（因为它在冷却中），而它实际上只是网络慢。

### 4. Context Overflow 不触发模型切换

```typescript
// 在 model-fallback.ts 中
if (isLikelyContextOverflowError(errMessage)) {
  throw err;  // 直接上抛，不尝试下一个模型
}
```

**原因**：换一个模型可能上下文窗口更小。如果主模型就溢出了，fallback 模型大概率也溢出。

### 5. Auth Profile 冷却期是指数退避的

```typescript
// Profile 失败后
await markAuthProfileFailure({ profileId, reason });

// 再次失败时，冷却期 = base * 2^failures
```

短时间内多次失败会导致冷却期越来越长，但同一个 provider 的**其他 profile** 可以继续使用。

## 九、关键设计原则总结

| 原则 | 实现 |
|------|------|
| **先轻后重** | Thinking 降级（改参数）→ Profile 轮换（换 Key）→ 模型切换（换 provider） |
| **避免级联失败** | Timeout 不标记 profile，避免影响同 provider 的其他模型 |
| **精确归因** | 同一个错误可能是多种原因（402 是 billing 还是 rate_limit？需要上下文判断） |
| **用户可见性** | 所有失败尝试记录在 `attempts` 中，最终错误消息包含完整失败链 |
| **冷却探测** | 所有 Profile 冷却时不白等，在冷却期快结束时主动探测 |
| **安全失败** | 非 FailoverError 不被 fallback 消化，业务错误立即暴露给用户 |
