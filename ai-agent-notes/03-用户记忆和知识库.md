# 03 · 用户记忆和知识库

> 来源：《深入理解 AI Agent》第 3 章
> 从单次会话的上下文管理，扩展到跨会话的持久化知识体系。

---

## 3.0 总览

- **用户记忆（个体尺度）**：针对单个用户的个性化记忆，让 Agent 成为"懂你的助手"。
- **知识库（群体尺度）**：面向所有用户共享的集体知识，让 Agent 成为"领域专家"。
- 两者共用底层技术（向量检索、知识压缩），面临同样麻烦（信息冲突、知识过期、检索不准）。
- **两条线索汇合于「双层记忆架构」**：Advanced JSON Cards 常驻概览 + 上下文感知检索按需取细节。

---

## 3.1 用户记忆系统

- 记忆系统**不保存每句对话**，而是用额外 LLM 调用提取、压缩并审查对未来有用的事实。
- 提取结果满足三规则：**选择性**（丢弃短期细节）、**抽象化**（归纳长期偏好）、**结构化**（可检索字段保存）。

### 3.1.1 记忆能力评估：三层次框架（贯穿全章）

| 层次 | 能力 | 示例 |
|------|------|------|
| **第一层：基础回忆** | 准确存取用户直接提供的、结构化、无歧义信息 | "会员号是 12345"，需要时精确返回 |
| **第二层：多会话检索** | 面对不同对象、不同时期的多段会话，检索全部相关信息并推理判断 | 两辆车用户要"预约保养"，主动问哪辆车；忽略已失效报价；取消旅行主动关联机票+酒店 |
| **第三层：主动服务** | 综合多会话、很久以前的信息，提供预见性主动帮助 | 订国际航班时关联数月前护照信息预警过期；手机损坏整合所有保障方案；报税季整合全年税务文件 |

- 综合 LoCoMo 等基准归纳的八项记忆能力：个人信息保留、偏好追踪、上下文切换、记忆更新、多会话连续性、复杂思考、时间感知、冲突解决。

### 3.1.2 记忆的层次结构（"放哪里"）

| 层次 | 定义 | 特性 |
|------|------|------|
| **轨迹（Trajectory）** | 一次运行的完整历史记录（用户消息+模型回复+工具结果） | 按时间追加、只增不改（append-only），流水账 |
| **用户长期记忆** | 跨会话、跨实例的持久化存储（键值对绑用户 ID） | 反复改写、合并、淘汰，档案；Agent 通过工具显式读取/更新 |
| **业务状态** | 开发者定义的高层状态抽象（"需要澄清"、"处理请求中"、"等待付款"、"请求完成"） | 事件驱动架构尤其重要 |

> 轨迹是不可变完整事件序列；长期记忆是跨会话提炼的稳定信息。为控制长度，每轮发给模型的运行时 Context 可压缩/重组/摘要替换，原始记录是否保留取决于数据保留与审计要求。

### 3.1.3 用户记忆的四种存储格式（"怎么存"）

| 格式 | 特点 | 优点 | 缺点 |
|------|------|------|------|
| **Simple Notes** | 最小不可分事实（"用户邮箱：john@x.com"） | 开销极低、O(1) 操作 | 关联性丢失，需重新拼凑碎片 |
| **Enhanced Notes** | 整段叙事（含完整上下文段落） | 语义完整 | 存储冗余、难更新、长文难检索 |
| **JSON Cards** | 三层嵌套（类别→子类别→键值对） | 支持部分更新、可预测可扩展 | 刚性分类，多维信息强制归一类丢多维性 |
| **Advanced JSON Cards** | 加 backstory（来源背景）、person（主体身份）、relationship（关系）、时间戳 | 消歧、知识管理、带来源与关系 | 生成维护成本高 |

- **实践选择标准**：关键且少量数据（用户偏好、关键人物关系）用 Advanced JSON Cards；大量非关键对话事实用 Simple Notes；多数生产系统用**混合模式**（不同类别信息走不同路径）。
- Advanced JSON Cards 核心思想：同一条信息在不同场景含义不同（"张医生"可能是用户自己的牙医或父亲的心脏科医生）；通过 backstory 提供"为什么"存，person/relationship 提供"为谁"存。

### 3.1.4 进阶知识表示形态：可执行代码（User as Code）

- 四种格式本质都是文本：擅长召回单条事实，却要把聚合、冲突检测、约束执行交给 LLM"心算"。
- **User as Code**：把用户状态改成带类型的可执行对象，规则写成普通函数，"表示"和"推理"用同一种可验证介质。
- 借鉴"预写日志 + 检查点"机制：会话结束先追加事实到只增日志，再定期从完整日志重建带类型状态。
- 示例：`count(trip for trip in state.trips if trip.is_international ...)`（聚合）、`check_drug_allergy`（冲突发现交叉比对用药与过敏史）、`check()`（约束执行，护照有效期检查，状态更新后自动触发）。

### 3.1.5 用户记忆的认知科学基础（"存什么"）

| 认知类型 | 人类例子 | Agent 对应 |
|----------|----------|-----------|
| **情景记忆（Episodic）** | 上周三和同事吃晚餐 | "用户订了下周五去东京的 ANA 航班" |
| **语义记忆（Semantic）** | 意大利首都是罗马 | "用户是素食者"、"偏好靠窗座位" |
| **程序记忆（Procedural）** | 骑自行车的能力 | "先搜直飞→确认座位→用常旅客号→订餐" |

**三套分类体系（正交，可自由组合）**：
- 记忆层次（放哪里）：轨迹 / 长期记忆 / 业务状态。
- 存储格式（怎么存）：四种 Notes/Cards。
- 认知类型（存什么）：情景 / 语义 / 程序。

> 工作记忆（Working Memory）对应上下文窗口（轨迹是核心内容，还可含从长期记忆激活加载的信息）。工作记忆是"筛选和激活的动态子集"（按相关性裁剪），轨迹是"不可变完整事件序列"。

### 3.1.6 记忆框架案例

**Mem0（从写入时消歧到检索时推理）**：
- **v2（2025）**：对话 → LLM 提取候选事实 → 向量检索已有记忆 → LLM 决定 ADD/UPDATE/DELETE/NOOP（写入时消除冲突）。优点记忆库简洁一致；风险：一次错误更新/删除不可逆丢失历史，每条候选事实都需二次 LLM 判断。
- **v3（2026.4）**：一次 LLM 调用提取事实 + **只做 ADD**（仅追加写入）；"住北京"和"搬到上海"作为带时间信息的两条事实并存。查询时融合语义相似度 + BM25 + 实体匹配 + 时间排序。**LoCoMo 71.4→92.5（+21.1），LongMemEval 67.8→94.4（+26.6）**。避免错误 UPDATE/DELETE 丢失历史，减少 LLM 调用，用多种检索信号 + 时间排序找当前事实。

**Memobase（用户画像 + 事件记忆）**：
- 聚焦"用户画像"具体形态。**用户画像（Profile）**：开发者可配置槽位（主题—子主题两级，如 basic_info→姓名、interest→游戏偏好）。**事件记忆（Event Memory）**：按时间线记录事件，回答"上次讨论预算是什么时候"。
- 工程：缓冲批处理策略（对话累积到一定规模/时限再统一触发记忆提取，摊薄 LLM 成本），查询侧低延迟。

### 3.1.7 记忆压缩与整理机制（三层）

1. **重要性评分筛选**：综合四因素——访问频率（经常检索更重要）、时间衰减（越久远越易忘）、情感强度（强情感更易保留）、信息独特性（重复信息重要性降低）。低于阈值标记可压缩/删除。
2. **聚类**：相似记忆分组，每组生成代表性摘要；原始详细记忆归档二级存储。
3. **抽象与泛化**：从具体情景记忆提取一般规律，转化为语义/程序记忆（如从多次购物对话学到"偏好性价比高、重视评价"）。

### 3.1.8 隐私保护：日志脱敏

- 核心挑战：利用用户信息提供个性化服务，又不让敏感数据暴露在 LLM 上下文和系统日志。
- 用**本地小模型**（Ollama + Qwen3 0.6B）做 PII 检测与脱敏（本地部署而非云端，因日志本身敏感）。
- 识别结构化（身份证号、银行卡号）、半结构化（地址）、自然语言（"我的密码是 abc123"）；JSON Schema 结构化输出（类型、位置、置信度）。
- LLM 脱敏召回率 95%+，显著降低假阳性；超高吞吐用混合策略（正则快速过滤 + LLM 深度分析）。

## 3.2 RAG 基础：知识获取管道

- RAG = 检索器（找相关片段）+ 生成器（LLM 拿片段作上下文生成答案）。
- 核心流程：检索相关片段 → 注入上下文 → LLM 生成。

### 3.2.1 文档分块（Chunking）

**为什么必须分块**：① 嵌入模型输入长度有限，整篇压成一个向量主题混杂；② 片段太大连带引入无关内容浪费窗口。

**三类策略**：
| 策略 | 做法 | 特点 |
|------|------|------|
| **固定大小切分** | 按固定 token（如 512）切，相邻块重叠 50-100 token | 简单可预测，无视结构 |
| **递归/结构感知切分** | 按自然边界（标题、段落、句子）递归切，超长降级更小边界 | 生产系统最常用默认 |
| **语义切分** | 计算相邻句嵌入相似度，在语义"断崖"处下刀 | 质量更高，需额外嵌入计算 |

- 块大小权衡：块太小信息不完整（"该公司收入增长 3%"——哪家？哪季度？）；块太大主题混杂、嵌入稀释。
- 常见起点：每块 256-1024 token、相邻重叠 10%-20%，按检索质量实测调优。
- **固有缺陷**：分块切断片段与原始上下文联系（"该公司"指代谁、出自哪份报告留在块外）→ 后文"上下文感知检索"解决。

### 3.2.2 稠密嵌入

- 嵌入 = 把词/句子转成向量，语义相近向量也相近；"稠密"指每个维度都有数值（对比稀疏嵌入大部分为零）。
- **余弦相似度**：衡量向量夹角余弦值（接近 1 = 语义相似）。用夹角不用距离（关心方向而非长度）。
- 技术演进：Word2Vec（静态词向量，一词一向量，无法处理一词多义）→ BERT（上下文感知，自注意力）→ Sentence-BERT（句子级）→ BGE-M3（多语言长文本、同时输出稠密/稀疏/多向量）。

**ANN 索引算法（实验 3-4）**：
| 特性 | ANNOY（树） | HNSW（图） |
|------|------------|------------|
| 构建速度 | 快 | 较慢 |
| 内存占用 | 低 | 较高 |
| 增量更新 | 不支持（需完全重建） | 支持（长期插入后建议定期重建） |
| 查询精度 | 较高 | 极高 |
| 适用 | 静态数据集 | 实时索引新信息的动态场景 |

### 3.2.3 稀疏嵌入（精确关键词匹配）

- 词袋模型（BoW）：只关心哪些词出现、出现几次，忽略词序。
- **TF-IDF**：一个词在当前文档出现越多、在整个语料越少见，对检索越重要。局限：词频线性增长无饱和、无长度校正。
- **BM25**：保留 IDF 稀有词加权，引入**词频饱和**（k1）与**长度归一化**（b）。公式：Score = Σ IDF(qi) × [TF(qi,D)(k1+1)] / [TF(qi,D) + k1(1−b+b·|D|/avgdl)]。
  - k1 控制词频饱和速度（重复出现边际贡献递减，出现 10 次不会比 5 次贡献整整两倍）。
  - b 控制长度归一化强度（长文档不因字数多而高分）。
  - IDF_BM25 = ln((N−DF+0.5)/(DF+0.5))，DF>N/2 时取负值需设下限。
- **倒排索引**：从词到文档的反向映射（"给定词，立刻找到所有含它的文档"），像书后术语索引。
- 稀疏检索优点：精确关键词匹配（技术代码、人名极佳）；缺点：读不懂同义表达（查"kitty"找不到只写"cat"的文档）。

### 3.2.4 混合检索（两全其美）

- 稠密检索懂语义但漏关键词；稀疏检索精确但不懂同义词。
- **三阶段流水线**：
  1. **并行检索**：同时向稠密、稀疏两引擎发查询，各自召回候选。
  2. **结果融合（RRF 倒数排名融合）**：抛开原始得分只看排名，综合得分 = Σ 1/(k+rank)，k 常取 60。简单稳健，但只用排名信息。
  3. **神经重排序（Neural Reranking）**：跨编码器对查询和文档深度交互匹配，对前 N（如 50）候选精确打分。**重排序不是补救 RRF，而是换更强的匹配范式**。
- **双编码器（Bi-Encoder）** vs **跨编码器（Cross-Encoder）**：前者独立生成向量算相似度（快、适合初筛），后者拼接查询+文档逐词比对（慢、准）。常用重排序模型 BAAI/bge-reranker-v2-m3。
- 类比：双编码器 = 猎头快速筛选简历；跨编码器 = 面试官深谈。

**检索质量三指标**：
| 指标 | 回答 | 说明 |
|------|------|------|
| **recall@k**（本书口径 = hit rate） | 该找的找到了吗 | 正确答案出现在前 k 结果的查询比例，最贴近 RAG 需求 |
| **MRR** | 找到得够不够靠前 | 第一个相关文档排名倒数的平均 |
| **nDCG** | 整个排序列表质量如何 | 考虑所有相关文档排名与相关程度 |

> 工业界还有"检索失败率"（正确信息未出现在 top-20 的查询比例）。

## 3.3 超越扁平文本：知识的组织与检索

### 3.3.0 为什么不能只平铺原始案例

两个案例：
1. **黑猫白猫计数**：100 个独立案例文档（90 黑 10 白），top-k=20 只能看到不完整样本 → 错误结论。预先生成摘要"共 100 只猫：90 黑 10 白"并索引，一次检索就准确。
2. **Xfinity 优惠边界**：几百条工单各写个案，无一条写资格范围本身。三重障碍：最近邻偏置（"护士"与"医生"语义最近，排前就顺势推断护士也可以）、边界语义缺失（"仅限…其他不适用"不存在于任何单条）、完整性信号缺失（模型无从判断是否看全，不追问自信作答）。

> **结论**：把原始案例不加处理直接放进知识库远远不够，必须在**索引阶段**投入计算资源，主动提炼、抽象、结构化——把"100 个案例"压缩为统计摘要，把"散落工单"提炼为带边界的规则。

### 3.3.1 结构化索引：RAPTOR 与 GraphRAG

**RAPTOR（树状层次）**：自下而上递归抽象。叶子节点（文本块）→ 聚类 → LLM 生成父节点摘要 → 递归 → 根（全局摘要）。适合"从概念逐步钻进细节"的查询（宏观→微观）。

**GraphRAG（实体关系图）**：实体-关系-实体三元组构建知识图谱。两大核心优势：
1. **多跳关系推理**：沿关系边遍历（"用户→医生→医院→地址"）。
2. **实体消歧**：区分两个同名"张医生"是图结构原生能力（不同节点靠关系边区分），无需额外推理。
- 流程：LLM 提取实体和关系 → 社区发现算法找语义紧密集群生成摘要。
- **局限**：自然语言转三元组导致语义降级（"如果下周还下雨就取消海滩计划改博物馆"的条件逻辑和时间依赖在分解后丢失）；三元组提取准确性依赖 LLM，错误提取导致知识污染。

**何时需要结构化索引**：查询主要是"找到包含某信息的片段"→ 混合检索够用；查询经常需要跨文档综合或多层次导航 → 值得投入（代价：索引构建和查询需更多 LLM 调用）。

### 3.3.2 文件系统范式（OpenViking）

- 把上下文映射为虚拟文件系统（目录+文件，每个条目唯一 URI：`viking://resources/`、`viking://user/memories/`、`viking://agent/skills/`）。
- **L0/L1/L2 三层按需加载**：
  - L0（摘要）：~100 tokens 一句话概述，快速判断目录相关性。
  - L1（概览）：~2000 tokens 核心信息与使用场景，供规划决策。
  - L2（全文）：完整原始内容，需深入时按需加载。
- 每目录自动生成 `.abstract`（L0）和 `.overview`（L1）文件。大部分查询加载到 L1 即可完成决策，Token 大幅降低。
- **用 Markdown 纯文本而非专用数据库**：用户可直接阅读编辑修正；Git 版本控制回滚；Agent 用 write_file 自主记录知识，经审核流程合入主库。
- **关键前提（易被忽视）**：文件之间必须建立**链接与索引**——组织得像 Wikipedia（条目互相链接 + 入口页 + 索引页），否则零散文件越难检索。
- **实践差异**：不同模型主动建立链接的意愿不同，写入知识的提示词必须明确要求"每新增条目先检索并链接到相关已有条目、更新索引页"。

### 3.3.3 知识应该如何更新

**两条路径**：事件触发增量更新 + 周期触发全量整理。

#### 增量更新（把知识库当代码库，PR 流程）

沿用提议者—审核者模式：
1. **Proposer Agent 提交 PR**：从原始证据发现新事实/冲突/过期内容，工作分支上提最小完整 diff（先检索相关已有知识，再增删改对应条目，维护链接、索引、时间元数据、证据引用）。
2. **Reviewer Agent 独立审核**：拿到变更前知识 + diff + 原始证据，检查断言是否有证据支持、是否漏限定条件、是否冲突、删除改写是否过度；审核不通过返回指向具体证据和行号的可执行意见。
3. **双方迭代至收敛**：设置最大迭代次数/成本预算，超限转人工审核，不能默认放行。
4. **合入后再发布**：CI 检查格式/链接/元数据/权限标签，代码型知识运行类型检查测试；通过后增量重建受影响的分块、摘要、向量索引。

**三层分层**：原始证据层（只增不改）→ 知识层（可修订 Markdown/代码）→ 服务层（检索索引，可重建的派生物）。

**关键要求**：
- Proposer 和 Reviewer 都是 **Agent**（非两次固定 LLM 调用），需拥有文件搜索、版本比较、测试执行、证据检索工具。
- **异源互审**：两 Agent 用能力相近但不同家族的模型（Proposer Claude/Reviewer GPT），降低同处犯同类错误概率；能力不宜悬殊。
- **权限强制分工**：Proposer 只能写工作分支，Reviewer 只读证据提交审核，只有合并流程更新主分支和线上索引。
- PR 记录证据标识、知识库版本、审核意见、决定 → 每条知识可回答"从哪来、谁何时批准"。

#### 定期整理（全量）

- 增量更新只看到局部，多次局部正确修改仍累积全局问题（同一事实散落多处、新旧说法并存、摘要偏离证据）。
- 三项核心工作：
  1. **去重、去旧、合并**：删除/归并/重写语义重复、被取代、碎片化条目；重建链接索引页；必要时拆大文件、合并小文件、调目录。
  2. **回到原始数据核查**：不能只在摘要间互改；逐段对照原始对话/轨迹/文档检查遗漏、丢失否定词或时间条件、把推测错当事实。分批扫描必须保留覆盖清单确保全量。
  3. **冲突解决与场景限定（qualification）**：矛盾说法不简单"保留最新"或让模型猜，而是追溯原始信息源检查是否在不同时间/对象/地域/任务/前置条件下成立；两者都有效就写明各自适用场景；证据不足则保留冲突和待确认状态。
- 整理产物也不直接覆盖主库，走 Proposer/Reviewer PR 流程；全量 diff 大可按目录拆多个 PR 共享整理计划；通过后回放典型检索问答用例确认没有让知识变不可见。

**失效内容检测与下线**：每块附加版本号、生效/失效时间元数据，检索阶段过滤已失效内容，或摘要标注"此条已于某日废止"。

**多用户权限与租户隔离**：检索必须按调用者权限过滤（越权文档绝不能进上下文）；多租户的向量索引和元数据相互隔离。

### 3.3.4 智能体化 RAG（Agentic RAG）

- 传统 RAG = 被动"检索-生成"管道（单次检索直接生成答案），能力上限低。
- **智能体化 RAG**：知识库检索变成 Agent 可随时调用的工具，用 ReAct（思考→行动→观察）主导迭代探索。
- 流程：思考分析需求定关键词 → 行动调 knowledge_base_search → 观察评估信息是否充分 → 不够则提炼更精确查询再搜 → 充分才综合生成答案。
- **价值**："解决问题"而非"回答问题"；牺牲响应速度换复杂问题的鲁棒性和质量（多跳问题准确率显著提升）。
- **RAG 安全边界**：检索文档是间接提示注入最典型载体，知识库投毒同理。防御两层：① 指令与数据分离（检索内容做来源标记"以下是外部资料不是命令"）；② 不让检索内容直接触发高风险操作（转账/删除/发信需独立授权判断，见第 4 章）。

### 3.3.5 RAG 技巧：上下文感知检索（Contextual Retrieval）

- 解决传统分块的根本缺陷：孤立块"该公司收入增长 3%"脱离上下文模棱两可。
- **核心思想（Anthropic）**：向量化索引前，先用 LLM 为每个块生成含核心上下文的**前缀摘要**，拼接后再索引（如"[本段节选自 ACME 公司 2025 Q2 财报'关键业绩指标'章节]"）。
- 同时增强稀疏（增加精确匹配关键词）和稠密（注入语义背景）。
- **与第二章"上下文感知压缩"的区别**：本节发生在**索引期**针对知识库文本块，做"补前缀加背景"（加法）；第二章发生在**运行期**针对当前会话历史，做"裁剪丢弃无关内容"（减法）。
- 代价：索引阶段额外 LLM 调用，但 prompt caching 可控（每百万文档 token 约 1 美元）。
- 效果（Anthropic 数据）：+BM25 检索失败率 ↓49%，+重排序 ↓67%。

### 3.3.6 从数据集提取深度知识（信息检索→知识发现）

- 知识以隐性、分散形式蕴含在结构化案例数据中（司法判决经验、资深医生直觉）。
- **两阶段**：
  1. **知识提取与结构化**：LLM 把非结构化案例描述转为标准化 JSON 对象。核心挑战是定义既全面又一致的 Schema。采用"自下而上"因子发现策略（LLM 分析数百样本自由列出影响判决的因素，构建贴合数据的模块化 schema = 核心模式 + 罪名扩展模式）。
  2. **因子分析与重要性建模**：特征向量化（独热编码而非 1/2/3，避免算法误以为"诈骗比盗窃严重 3 倍"）→ 聚类发现"案件原型"→ 构建因子重要性层次模型。
- 应用：按因子重要性引导提问 → 检索相似案件原型 → 数据驱动量刑分析。
- **启示**：Agent 不一定把知识库当只能检索的静态仓库——可以先"读懂"数据提炼结构化决策逻辑，再基于逻辑回答问题。

### 3.3.7 前沿探索：多模态记忆

| 思路 | 做法 | 特点 |
|------|------|------|
| **思路一** | 存储原始多模态数据 + 文本描述（剪切人脸存图片 + 文本描述索引） | 简单，但部分多模态信息难用文本表达 |
| **思路二** | 多模态信息嵌入压缩存储到上下文（人脸/声纹各存一个嵌入，1 token/个） | 1000 token 区域容 1000 张人脸，效率高；需注意力检索 |
| **思路三** | 嵌入压缩存储到模型参数（Engram 哈希 N-gram 槽位，非训练 LoRA） | 扩展性强，但需预训练模型支持 Engram，查准率可能不如思路二 |

## 3.4 本章小结

- 持久化知识两尺度：用户记忆（个体）+ 共享知识库（群体）。
- 用户记忆生命周期：读取相关记忆 → 后台提取候选 → 来源与策略核验 → 更新。
- 知识库主流水线：分块 → 稠密/稀疏检索 → 融合 → 重排序 → 生成，用 recall@k 等验收。
- RAPTOR、GraphRAG、OpenViking、上下文感知检索、智能体化 RAG 分别改变知识的**组织、分块、检索控制**方式。
- 写入不能跳过来源、时间、冲突、隐私检查；增量更新吸收新证据，定期整理回原始数据去重合并重建索引，待验证 diff 经独立审核后发布。
- **双层记忆架构**：结构化概览常驻上下文 + 原始细节按需召回（Advanced JSON Cards 常驻 + 上下文感知检索取细节），让"主动服务"首次在工程上落地。
