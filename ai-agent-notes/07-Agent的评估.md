# 07 · Agent 的评估

> 来源：《深入理解 AI Agent》第 7 章
> 核心问题：怎么判断 Agent 变好了还是变差了？评估把迭代从经验判断转化为可比较、可复现的工程过程。

---

## 7.0 总览

- **评估的对象不是模型，而是模型 + Harness 的组合体**（同一模型在不同 Harness 表现差异悬殊）。
- 区分"模型能力不足" vs "Harness 设计缺陷"：**模型替换实验（model swap）**——固定 Harness 只换模型，分数不涨说明瓶颈在 Harness；分数随模型大幅波动说明瓶颈在模型能力。
  - 注意区分：消融实验（关 Harness 组件看变化）定位 Harness 内部哪个部件重要；模型替换区分瓶颈在模型还是 Harness。
- 评估首要价值：**快速可靠地跟上模型演进**（数小时得出切换决策 vs 凭直觉等待）。

**三个层次**：
1. 评估设计（"什么算成功"+"在哪里测、测什么"）
2. 评估方法（"怎么判"）
3. 评估驱动决策（"测了干什么"）

---

## 7.1 评估指标口径（关键区分）

### Pass@k vs Pass^k（两个指标，结论可能相反）

- **Pass@k（技术奇观/能力上限）**：跑 k 次只要至少一次通过就算过（Best@k 取最好得分）。适合科研发现、漏洞挖掘、开放式创作（人类可从 k 条轨迹挑最好的）。
- **Pass^k（业务可靠性）**：同一任务连续 k 次每次都通过，且不能触发安全/合规/幻觉等一票否决项。适合支付、退款、权限变更、生产部署。
- 数学关系：Pass@k = 1−(1−p)^k，Pass^k = p^k。例 p=0.6, k=5：Pass@5≈99%，但 Pass consecutive@5≈7.8%。
- 评估报告必须写清 k 次尝试口径（k 次独立采样 vs 连续 k 个任务）；有副作用操作在沙盒/可回滚环境采样，每次失败都记入可靠性指标。

### 过程指标（从黑盒到白盒）

- 行动合法率（有效且合法操作比例，无效=调不存在工具/错误参数类型，越权=超权限）。
- 工具调用正确率（参数语义合理）。
- 路径效率（步数、冗余动作、回退次数；需建立人类专家/启发式基线）。
- 检索覆盖率（是否充分探索信息空间）。
- 成本与延迟（请求次数、token 花费区分输入/输出/缓存、墙钟时间追踪时间分布）。

### 安全、鲁棒性与轨迹覆盖

- 安全合规零容忍（敏感操作、数据外泄、违规内容），一次严重违规即否决整体评价。
- 鲁棒性：随机种子敏感性、页面变化适应性、API 抖动容忍度、长时记忆干扰。
- **轨迹（trajectory）与结果（outcome）双重覆盖**：Agent"说订票完成"是轨迹层面，数据库真生成订单才是结果层面；只看轨迹漏"说了没做到"，只看结果看不出中间走歪。两类都应覆盖。

### 人工抽检与对抗式评审

- 定期人工抽检覆盖不同任务类型、成败案例、边界模糊案例，审查评分理由合理性。
- **评判者校准**：先构建人工标注金标集（100-200 案例），测评判模型与人类一致率（Cohen's kappa，剔除随机猜中），达阈值（>0.7）才用于大规模评估；评判模型/Rubric 更新时重新校准。
- **对抗式评审（红队）**：构造表面完美但含隐蔽错误、关键词堆砌蒙混、利用评判偏见得高分的回答。

## 7.2 自动评估环境

### 五要素

1. **数据集（Dataset）**：任务集合（初始状态、目标描述、可选参考解）。
2. **环境状态（Environment State）**：维护可变信息，真实性与可控性平衡（状态变化符合业务逻辑 + 每次可重置相同初始状态）。
3. **工具接口（Tools）**：提供原子操作（查询订单、修改预订、发邮件），不用层级过高的抽象（"解决用户问题"），迫使 Agent 规划组合。
4. **评分标准（Rubric）**：二元/连续/多维。
5. **执行协议（Interaction Protocol）**：交互模式和终止条件。

### 工具调用型环境（Verifiers）

- 验证基于可执行标准（测试通过、答案匹配），不依赖人工/模型评判。
- 层次化：SingleTurnEnv（单轮问答）、ToolEnv（多轮工具调用）、StatefulToolEnv（有状态）、SandboxEnv（有状态+隔离，代码执行测试）。
- 支持并行采样和轨迹缓存；失败时提供清晰错误信息（而非简单失败标志）。

### 人机交互型环境（τ-bench / τ²-bench）

- 根本挑战：如何模拟真实用户。
- **渐进式信息透露（Progressive Information Disclosure）**：用户很少一上来清晰描述需求（"我的航班好像有问题"），Agent 需主动提问澄清。评估绝不能一开始把全部信息暴露。
- **用户模拟（User Simulation）**：另一个 LLM 扮演用户，按预定义指令对话，逐步透露必要信息，任务完成发终止信号。要求"不一次性透露所有信息""不编造指令未提供的信息"。真实性与可控性权衡（接近真实用户 + 遵循剧本保证可复现）。设置有限耐心（沟通低效就终止）。
- **双重验证**：① 数据库最终状态正确；② 对话中输出必要关键信息。任务层面汇总为二元奖励（全过 1 分，任一不过 0 分）——便于统计 Pass^k，代价是"漏一个非关键字段"与"完全失败"同分。
- **τ²-bench 增量**：① 双控环境（Dual-Control，用户模拟器也能操作共享环境，Agent 指导用户操作真正改变状态）；② 更精确任务规范 + 组合式任务生成。

## 7.3 评估数据集设计

### 五大核心挑战

1. **明确性与开放性张力**（GAIA：目标明确、路径开放）。
2. **真实性与可控性平衡**（SWE-Bench → Verified：人类专家筛选 500 高质量任务）。
3. **多样性与系统性协调**（AndroidWorld：116 任务横跨 20 应用，标注所需能力，参数化生成变体）。
4. **评估成本与覆盖范围**（SWE-Bench Verified 从 2294 筛到 500，成本降约 80%）。
5. **数据泄漏防范**（GAIA 靠答案独特性+专用附件；SWE-bench-Live 靠时间新鲜度；τ²-bench 动态生成参数；AndroidWorld 参数化抗泄漏；Terminal-Bench 金丝雀 GUID 使泄漏可检测）。

### 任务描述精确性设计

- GAIA：明确信息源约束、时间范围、主题、查询目标、严格输出格式（每个细节服务自动验证）。
- τ²-bench 情境化设计：表面问题 + 性能期望 + 约束条件 + 隐含情绪；"已知信息"与"任务指令"分离；事实锚定要求（必须基于工具实际返回回答，不能编造）。
- AndroidWorld 参数化模板：每次随机生成参数值（防记忆、增多样性、支持对比实验）；验证基于最终 UI 状态而非操作序列。

### 任务复杂度层次化设计

- GAIA 三级难度：Level 1（1-2 工具）、Level 2（多步思考）、Level 3（复杂组合）。诊断价值：不同层次对应不同改进方向（提示工程 vs 规划机制 vs 分层架构/后训练）。
- τ²-bench 业务复杂度分层（信息查询→多步流程→故障诊断→策略判断）。
- Terminal-Bench 技术领域 × 操作复杂度双维度分层。

### 可验证性与客观性

- SWE-Bench Verified：FAIL_TO_PASS（修复前失败后通过，证明解决）+ PASS_TO_PASS（前后都通过，证明没引入新 bug）双重验证；确保无 flaky tests。
- τ²-bench 多层检查：数据库状态、对话关键词、流程合规。
- OSWorld：134 个独立评估函数，深入检查文件系统/进程/网络/应用内部状态，发现"表面完成但实质错误"。
- Terminal-Bench：Docker 标准化 + 文件系统状态检查 + 程序执行功能验证。

### 数据质量控制与迭代改进

- SWE-Bench Verified：93 名开发者人工评估，多项检查（描述清晰、测试完整、测试稳定、patch 正确、难度合理），仅 29% 通过——高淘汰率是对评估质量的必要投资。
- OSWorld-Verified：15 个月暴露 300+ 问题（环境/描述/验证逻辑/初始状态四类），约 10 人小组两月系统性修复；评估基础设施本地 VM 迁 AWS，50 倍并行加速。
- **红线**：评估集具体题目必须与训练数据严格隔离；可复用的只是环境构造机制。

## 7.4 自动化评估方法

### 7.4.1 LLM-as-a-Judge

- 用于开放式任务（无标准答案）。已知局限：评判模型偏见（最典型**长度偏差**——倾向给更长回复打高分）、波动。
- 长度偏差防范：Rubric 显式惩罚冗长/规定长度上限；配对比较控制长度相近；定期审计评分与长度相关性。

**Rubric 四准则（Scale AI "Rubrics as Rewards"）**：
1. **基于专家指导**：反映领域知识，捕捉核心事实和推理步骤。
2. **全面覆盖**：事实准确性、逻辑连贯性、完整性、安全性 + 明确陷阱（Pitfall）。
3. **按重要性加权**：必要项（Essential）、重要项、可选项、陷阱项；支持**一票否决（Veto）**（幻觉是典型否决维度）。
4. **评价标准自包含**：每个评价项独立可操作，不依赖评价者领域知识（避免"展示了深刻理解"这种抽象标准，改为"引用了至少两个权威理论并准确解释"）。

- 每个维度定义客观可验证评分档 + 具体示例 + 边界案例。主动防范**奖励作弊（Reward Hacking）**（明确惩罚幻觉、讨好用户、关键词堆砌、回避棘手问题）。Rubric 不断迭代，从抽象准则演化成判例集。

### 7.4.2 失败归因（Failure Attribution）

- 端到端评估只给"成功/失败"，要驱动修复必须标出：主要错误类别、首次出现不可接受行为的步骤、对应工具调用/模型输出、可复核证据。
- **归因对象是轨迹中首个导致任务偏离的错误**（后续错误是连锁反应，不能把最后一个报错当根因）。
- 问题案例三类信号：用户明确纠正、用户点踩/负面反馈、事后状态检查/规则验证器/LLM 评审发现。
- Coding Agent 初始错误分类：流程与规范缺失、工具调用错误、作用域敏感的文档格式错误、精确复制错误、模型执行异常、任务完成度与逻辑判断问题。
- 归因记录需结构化（JSON/YAML），引用步骤号/工具名/观察证据，区分根因与后果，判断是否可恢复并给置信度（三次重试是后果不是三个独立根因）。保存时附带任务目标、环境状态、Agent 版本、工具集版本、完整轨迹。

**作用域敏感的文档格式错误**：区分 ASCII 直引号、中文弯引号、Markdown 反引号；同一字符在不同作用域（ZH_PROSE、EN_PROSE、CODE_BLOCK、JSON 等）语法角色不同，不能用同一条替换规则。

**精确复制错误**：保存原始字节哈希、Unicode code point 序列、tokenizer token ID 序列，沿"文件原始字节→工具返回→Harness 序列化→模型上下文→模型输出→解码→工具匹配"链路找首个差异；只有首个差异在模型输出才转训练数据，否则修复 tokenizer/序列化/Harness/工具协议。

### 7.4.3 端到端回归任务 vs 轨迹前缀回归任务

- **端到端回归**：从初始状态和用户请求开始完成整个任务，检查最终状态/必要输出/安全条件。验证完整工作流不退化。
- **轨迹前缀（trajectory prefix）回归**：冻结已有上下文/对话/工具返回/环境状态，只要求模型思考并执行下一步或下几步可观察动作。成本更低，隔离单个策略/工具问题。**对高可靠性生产级 Agent 往往更重要**。
- 答案定义为**可接受动作集合**（"先读规则""先询问用户""拒绝危险操作"）+ 禁止动作，而非唯一动作。

### 7.4.4 同源模型问题与多源评判

- 古德哈特定律：度量指标变成优化目标时就不再是好指标；Agent 会钻评分系统漏洞。
- **多源异构评判**：不同模型家族的多个 LLM 分别评判（Agent 用 Claude，评判用 GPT-5 和 Gemini），不同家族偏见正交，难同时"欺骗"所有评判者；相同 Rubric 确保同一目标；部署用单一模型快速评估，定期用完整多源评判质量审计。

### 7.4.5 多模态 LLM-as-a-Judge

- TTS 评估（准确性/自然度/音色一致度/情感表达）、ASR 评估（语义影响判断）、UI 评估（提议者-审核者模式检查溢出/对比度/按钮位置）、视频剪辑评估（关键帧验证）。
- **选什么参考答案/参考图片/参考音频本身就是评估设计**，不是无关紧要的准备。

### 7.4.6 配对比较与模型排名（Elo）

- Elo 评分：通过大量两两对决量化相对能力。统计基础 Bradley-Terry 模型（胜负概率由实力分差决定）。
- Chatbot Arena：匿名随机对决 + 用户盲选。局限：排名取决于用户问了什么问题。
- **位置偏差（Position Bias）**：评判模型系统性偏向某个位置（通常先出现）。缓解：交换顺序各评一次取平均；严格做法两次判决一致才计入，不一致记平局或人工复核。
- Elo 在线更新（受 K 因子和处理顺序影响）vs Bradley-Terry 极大似然拟合（一次性求解，与顺序无关）——总体排名应吻合，具体分值不精确一致。

## 7.5 评估驱动的模型选型

### 关键维度

- **Prefill vs Decode**：Prefill 一次性读入完整上下文（决定 TTFT 首字延迟，上下文越长越慢）；Decode 逐 token 生成（决定出字速度 tokens/s 和思考时长，50 tokens/s 生成 2000 思考 token 光思考就 40 秒）。
- 指标：输入/输出吞吐量、TTFT（排队+Prefill）、思考延迟（不同模型思考 token 数差异可达数倍且与效果不一定正相关）、**p95 尾部延迟**（比均值更反映真实体验）、成本（便宜但成功率低需频繁重试反而更贵）。
- 性能：日常看 Pass@1，关键操作看 Pass^k，探索性任务看 Pass@k/Best@k。
- 速率限制与可靠性（RPM/TPM、分布外数据、对抗输入、长时稳定性）。
- **预算—能力曲线**：不只报单点成功率，报性能随墙钟/token/工具调用/算力预算的变化曲线。RE-Bench：2 小时预算 Agent 约为人类专家 4 倍，但人类从增加预算收益更大（32 小时时约为 Agent 2 倍）——**短预算领先不能外推长时运行能力**。

### 模型行为策略（行动阈值）

- 模型默认"怎样做"也是选型维度：有的先广泛探索再改，有的凭局部证据快速定位先改再用测试反馈补齐。
- 来源：Harness 系统提示词 + 模型行为策略（后训练是关键来源——SFT 示范、过程奖励、结果奖励）。
- 实验测量：固定 Harness 换模型，GPT-5.6-sol 首次修改前平均调工具 6.89 次/读 4.67 文件 vs Claude Sonnet 5 的 4.56 次/3.56 文件——**行动策略随模型而变**，但"多读或早改"不一定更好（两模型最终测试都 100% 通过）。

### 成本分析（三层次）

1. **模型推理成本**：输入+输出 token。放大因素：**上下文累积效应**（每轮都发全部历史，无 KV Cache 时总量 1000+2000+3000=6000 而非 3000）+ 思考 token 成本（不展示但计费）。
2. **工具调用成本**：外部 API 费用、沙盒资源、**工具返回注入上下文的 token 费用**（一次搜索 2000-5000 token，后续每轮反复计费）。
3. **基础设施成本**：向量库、消息队列、关系库、日志追踪存储。

- 实测（八轮客服任务）：仅稳定前缀省 28.3%，仅压缩历史省 17.5%，两者合用只省 30%（**不是相加**，因为压缩历史同时缩短了可命中缓存的前缀）。**几项优化合用时必须在完整任务一起实测**。
- 成本优化：复用 KV Cache、压缩上下文、分层选择模型；这些能力最好**独立开关**（看清每项作用+检查合用是否抵消）；异步批处理（波谷折扣/GPU 利用率）；成本监控与预算控制（按任务类型/模型/用户追踪，设每任务成本上限防死循环/过度探索）。

## 7.6 评估结果的统计显著性

- 标准误 SE(p) ≈ √(p(1−p)/n)。100 用例 70% 成功率，95% 置信区间约 ±9 个百分点——"73% vs 70%"不足以支持切换。
- **配对分析优先**：逐题记录谁胜出，用 McNemar 检验或配对 bootstrap，而非直接相减两个独立成功率。
- 每个配置用多个随机种子（3-5 次），报告均值和波动范围；单次运行只筛选方向。
- 预期收益只有 2-3 个百分点且样本几十题时，先扩大样本（标准误按 1/√n 缩小）。
- 多重比较：收紧显著性阈值或独立复跑。实务标准：**分差超噪声、配对分析成立、能复现**，才值得切换。

## 7.7 Agent 的可观测性

- 概念：无法直接打开系统内部，只能通过日志/指标/追踪推断（医生靠体温血压影像诊断）。
- 价值：问题诊断（回放全过程）、持续优化基础（哪些任务多轮迭代、哪些工具成功率低）、成本管理、后训练数据积累。
- **数据基础是追踪（Trace）**，沿分布式系统 span 树模型：一次任务一条 trace，每个 LLM 调用/工具调用/检索是一个 span（输入输出、起止时间、token、错误），父子关系构成执行树。
- 标准协议：OpenTelemetry（通用分布式追踪）、OpenInference（LLM 特有语义约定）。**采集与分析解耦**，避免被单一平台锁定。
- LangSmith/Langfuse/Arize Phoenix：可观测性+评估+优化闭环，异步批量采集不影响延迟，支持 A/B 测试、提示词版本管理、协作开发。
- **闭环**：生产轨迹筛选失败/可疑案例 → 脱敏 → 沉淀为评估集新用例和回归测试。评估集从静态集合变成随产品演化的活资产。

## 7.8 从 Benchmark 报告到系统改进

**方法论：观察→假设→实验→决策→迭代（从炼金术到科学工程）**

- **先检查评测系统本身，再动 Agent**：看到分数下降先排查评测系统（资源不足、评分器 bug、测试用例与生产脱节），这些在结果数字上都跟模型退化一模一样，只有审查完整轨迹才能区分。

**AndroidWorld 调优案例（三轮）**：
- H1 增加导航提示 → 成功率不变（25%→25%），说明问题不在提示词。
- H5 accessibility feed 换 UIAutomator 元素树 → 25%→100% 但 token 2.498 倍。
- H5C 精简元素树（删不可见/无文字/不可操作容器节点）→ 成功率 100% 不变，token 降 0.506 倍。
- **结论**：① 提示写再详细补不回 Agent 根本没看到的信息，先检查输入而不是堆提示词；② 输入不是越多越好（删无语义节点后 token 减半）。

**决策原则**：低成本高收益优先部署，高成本限定关键场景；子集 4/4 不能写成系统整体 100%（需标准环境 116×5 完整复测）。

## 7.9 从外部评估到内部评估（生产级基础设施）

五个组件（OpenClaw 案例）：

1. **消融基础设施**：总开关同时禁用多个特性（思考/压缩/自动记忆/后台任务）创造"裸模型"基线。**消融开关必须在启动路径极早期注入**（在任何模块级常量捕获配置前），必须从架构设计之初就设计。定期运行发现"特性债务"（曾经有效但随模型进化已不再必要）。
2. **AB 测试方法论**：多臂而非二元（多个渐进变体揭示剂量-效应关系）；**区分机制指标和目标指标**（改变的 vs 真正关心的，以目标为准）；设置护栏指标（不能变差的底线）；记录基线统计。
3. **双层特性开关系统**：编译时开关（物理移除代码，逆向工程不可见，干净消融）+ 运行时开关（服务端下发+本地缓存，宁可读旧缓存不阻塞启动；曝光事件每会话最多记录一次）。特性开关是一等架构组件，非调试工具。
4. **提示词敏感性评估**：系统提示是 Agent 行为的"代码"，需版本控制和回归测试。实践：系统提示确定性渲染；版本化快照；每次变更跑评估集回归（像代码变更跑 CI）。
5. **隐私感知分析**：分析接口只接受特殊类型包装值（类型名是审计线索），隐私约束从文档规范变编译时强制。隐私和评估不对立，隐私感知设计催生更精准指标。

## 7.10 仿真环境（评估到后训练的桥梁）

- 区别：交互频率高得多（数百万 vs 数千）、需随机化（防死记硬背）、必须即时反馈。
- 评估资产转训练信号：Rubric/验证器本质就是 RLVR（可验证奖励）的奖励函数。
- 训练新要求：可靠的 **reset 语义**（每个 episode 重置到确定干净初始状态）；远高于评估的**吞吐**（百万次交互）。
- 数字环境：AWorld（GAIA 任务的 MCP 沙盒，26 服务器 126 工具，14.6 倍加速）。
- 具身环境：RoboTwin2（物理引擎双臂操作，随机化物体位置朝向外观，动作分块实时控制）。
- **保真度权衡与领域随机化**：高保真迁移好但计算开销大；适度随机化提升泛化，过度随机化让任务过难。领域随机化（物理参数/视觉/传感器噪声大范围随机）缩小 sim-to-real gap。

## 7.11 本章小结

- 完整闭环：评估环境 → 数据集 → 自动化评估方法 → Benchmark/问题案例 → 系统改进 → 更新环境数据集 → 新一轮迭代。
- 本章建的是第一章发现循环中的**证据段**：失败归因决定后续提案有没有可依之据。
- 获得一条信息 vs 正确用于当前决策是两种不同能力：端到端回归保证基本任务不退化，trajectory prefix 边界集直接检查作用域判断、当前指令覆盖、澄清、危险动作前确认。
