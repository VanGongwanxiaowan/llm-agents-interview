# 09 · Agent 的持续进化

> 来源：《深入理解 AI Agent》第 9 章
> 核心：把 Agent 的运行经验转化为下一版本的能力。"保存经历 ≠ 从经历中学习"。

---

## 9.0 能力悖论与核心命题

- Agent 能零样本解决从未见过的复杂任务，却可能在处理一万次相似任务后第二天仍犯第一天的错误。
- 部署后模型不会因一次推理自动改变参数。上下文学习只在当前任务内适应，任务结束不持久化；存进记忆也不等于学会新行为（原始轨迹有有效策略也有偶然成功、错误归因、不可信输入）。
- **学习发生在系统主动完成"评价、对照、归纳、验证"之后，不是发生在日志写入磁盘那一刻**。
- 第三章记忆沉淀"用户与世界是什么样的"，本章经验学习沉淀"在什么条件下应该怎样行动"——前者让 Agent 记得更多，后者让它从聪明变熟练。
- 为什么不让模型每次任务后直接训练自己：生产环境很少提供干净学习信号；未经验证的反馈直接改参数会固化错误经验和提示注入。

**持续进化三要件**：以可追溯的运行经验为基础 + 能够改变后续行为 + 经过验证确保没退化。

---

## 9.1 从运行轨迹中获得学习信号

- 起点不是"总结"，而是"评价"。错误评价一旦进入长期知识/系统提示/训练数据，影响跨后续任务放大。
- 结果正确 ≠ 过程正确（删除失败测试也能让测试通过；口头承诺"7 天退款"也可能得暂时满意）。
- **三层轨迹验证**（越靠下越依赖代码和环境真值）：
  1. **结果验证器**（底层）：读取测试结果、数据库状态、工具返回，回答"事情是否真的办成"。
  2. **过程验证器**（中层）：检查业务规则、权限、动作序列，回答"是否以允许的方式办成"。
  3. **质量验证器/LLM Rubric**（上层）：依 Rubric 评价语言与策略，回答"是否办得合适"。
- LLM-as-a-Judge 不能只给模糊总分，要预定义 Rubric 逐项给分、引用轨迹证据、证据不足时明确表示不确定。

**客服 Agent 轨迹评价维度（7 维）**：任务结果、规则遵从、隐私边界、事实可靠性、承诺—行动一致性、表达质量、合规变通。拆分比"用户是否满意"更有诊断价值（用户可能因违规退款而满意，也可能因合规限制而不满）。

## 9.2 四种持续进化方法（按能力的表示性质选择载体）

| 更新方式 | 适合承载 | 主要优势 | 主要局限 |
|----------|----------|----------|----------|
| **经验知识库** | 事实、经验规律、例外与来源 | 更新快、可追溯、按需检索 | 依赖检索和模型正确应用 |
| **Prompt 与 Skill** | 需理解语境/例外/优先级但仍能用自然语言说明的判断原则 | 可解释、作用范围可控 | 容易膨胀、冲突、被忽略 |
| **程序与 Harness** | 可确定解析、可执行验证、高风险硬约束 | 可测试、执行稳定、成本低 | 开发维护成本较高 |
| **模型参数** | 高维感知、生成风格、隐式策略 | 泛化强、推理开销低 | 更新与回归成本高 |

> 四种方式互补而非互斥（医疗 Agent：参数识别病灶 + 知识库提供最新指南 + 代码计算风险指标 + 服务端代码兜底硬约束）。
> 首要判断：能力能否被事实、语言规则或程序完整表达？稳定性、成本、更新频率决定部署方式。

### 9.2.1 将经验沉淀为知识

- "该航空公司要求特殊餐食提前 24 小时预订"是领域知识；"订票前先检查特殊餐食截止时间"是行动经验。
- **原始轨迹不适合作为正式知识单元**（又长又嘈杂）。保留三层：不可变原始轨迹（审计）+ 单次运行分析（成败与草案）+ 跨轨迹比较聚类归纳（正式 Markdown 文档）。
- 正式文档写清：适用场景、推荐策略、禁止做法、例外条件、证据来源、最近验证时间。
- **记录与整理分开**（同 User as Code 两阶段：先追加不可变日志，再离线重建）。
- 有迁移价值的内容来自**对照**：同类成功轨迹做了什么、失败轨迹缺什么、策略在哪些环境版本有效、哪些前置条件失效。
- 五步知识提炼管道：保存不可变轨迹和环境结果 → 单次运行结构化分析 → 按任务族聚合建立证据表（哪些支持/反驳）→ 达到支持门槛才写正式文档 → 未参与提炼的新任务测迁移。
- Reflexion 的自然语言反思可参与生成草案，但反思本身不是证据；只有与环境结果相符、跨轨迹支持、新任务正向迁移的内容才进入正式文档。

### 9.2.2 将经验写成指令（Prompt/Skill）

- 知识库给"可参考的资料"，Prompt/Skill 规定"应该怎样行动"。三个概念区分：**系统 Prompt 对所有任务生效，Skill 只在匹配领域/工具时按需加载，程序/Harness 负责权限和硬约束**。
- Karpathy 称"系统提示学习（System Prompt Learning）"：模型遇到问题后用一句清楚的话提醒未来的自己。
- 修改应是**带来源的最小 diff**（而非让模型每次重写整份 Prompt）——第一章"最小 diff + 可回滚"模式。待验证版本必须同时在**触发失败的边界集**和**正常工作的保留集**上测试。

**例子一（航空客服转人工）**：失败归因发现问题不是"不够礼貌"，而是 Prompt 没写清转接边界 → 生成一条带来源的最小 Prompt 补丁（"先查政策、解释规则、提供合规替代；只有明确要求人工或涉及安全才转接"）。

**例子二（需求澄清 Skill）**：Skill 要表达的不是"所有任务都必须确认"，而是一条带作用域的判断路径（低风险可撤销小改动说明假设后直接执行；涉及架构/数据/权限/公开接口/大范围改动时集中提少量关键问题；生成短 Spec 确认后执行）。更新提案需减少需求偏差的同时不显著增加打扰。**Skill 与 Harness 边界**：Skill 负责理解语境主动提问整理 Spec，Harness 负责在缺少确认时否决高风险写入。

### 9.2.3 将经验写成程序

- 稳定、重复、可验证的操作应编译为工作流/工具/Harness 代码（一次探索变成可重复执行程序）。类比电子表格宏录制。
- 浏览器工作流生命周期（6 步）：捕获轨迹（含 XPath/CSS 定位证据，定位只用于找元素不能证明完成）→ 参数化（字面量替换为模板变量）→ 定义状态检查（执行前/后检查 + 最终状态检查，动作成功≠任务成功）→ 独立回放验证（重置到独立初始状态完整回放）→ 匹配与回放（按意图关键词找工作流，提取参数，Playwright 直接执行）→ 失效与重学（找不到元素/状态检查不过/API 变/最终状态错则回退完整 Agent 模式）。
- PreAct 实验：重复任务 8.5-13 倍端到端加速；**流程记忆必须同时具备动作前验证、动作后验证、独立回放验证**，否则得到"每个按钮都点了但某字段为空"的危险假象。
- **Agent 修改自己代码 ≠ 运行进程直接覆盖自身**：从稳定版本创建隔离更新分支，Coding Agent 生成最小补丁，通过静态检查/单元测试/安全扫描/失败轨迹重放/旧任务回归，再生成可灰度部署新版本。
- Git worktree + Pull Request：Skill 应指导 Agent 创建 worktree、确认 Spec、测试、提交、PR 写清背景方案测试风险；Harness 在准备结束任务时检查是否在 main 直接提交/遗漏 worktree/PR，违反则否决。
- 每个修改请求应是**可证伪的变更契约**：列出失败证据、推断根因、归属组件、修改提案、预期修复行为、可能受损行为、分别验证的用例。
- 提案生成器输入不应只有失败案例（Self-Harness 还提供必须保留的成功行为和此前被拒绝的修改记录——前者告诉哪些性质不能破坏，后者避免换说法重复提交已失败方案）。
- 工具创造同协议（Alita：Agent 缺字幕能力 → 搜索测试 youtube-transcript-api → 封装新工具 → 安全扫描/功能测试/复用通过才进能力库）。

**DeepSeek Harness（一切皆插件）**：动态组合需要**时间可组合性**（组件移除时副作用能完整安全撤销）和**空间可组合性**（组件间结构化声明、发现、解析依赖，依赖变化时协调生命周期）。Cordis 把编译期的效果系统提升为可撤销效果、协效果提升为反应式协效果。**自我进化的上限取决于承载系统的可组合性，而非模型写出多好的代码**。插件改变工具集/提示片段 → KV Cache 从变化处失效，需在文档描述影响。

### 9.2.4 将经验写入参数

- 前提是能力能被外部符号较完整表达。医疗影像理解、自然语音韵律、消除"AI 味"、长程规划难压缩成规则 → 必须后训练写入参数。
- 是否参数化不由"任务是否长期稳定"单独决定，真正决定主要载体的是能力的表示性质。
- 把经过评价的生产轨迹转化为训练数据：高质量示范 → SFT，明确偏好 → 成对数据，可靠环境奖励 → RL。

### 9.2.5 从更新产物到更新"更新方法"（Meta）

- 正交的轴：优化的是某份产物内容，还是产生/管理/验证这些产物的方法。
- 五层搜索尺度：单条规则/记忆 → 结构化上下文 → 工作流 → Harness 代码 → 产生更新提案的优化器代码。
- **最内层（改产物内容）是默认选择**（作用面小、易归因回滚）。反复重写整份 Prompt/记忆会丢细节。
- ACE（Agentic Context Engineering）：上下文维护成带稳定标识符的条目集合，增量更新 + 确定性合并去重（而非每轮重写越来越短的文本块）。
- MCE（Meta Context Engineering）：内层优化上下文产物，外层修改搜索/选择/过滤/格式化这些上下文操作本身。
- AFlow（工作流表示为代码图，执行反馈搜索组合）、Meta-Harness（Coding Agent 读取源码/分数/轨迹搜索信息如何存储检索呈现）。

## 9.3 构建可长期运行的持续进化闭环

### 双循环结构

- **在线执行循环**：只完成任务并记录证据，不直接改写正式 Agent。
- **离线进化循环**：聚合轨迹、诊断根因、生成更新提案、通过验证门槛发布新版本。
- 两者通过版本化经验库和评估集连接。**可信根（权限、审计、验证、回滚机制）不由普通进化流程自行修改**。

**Voyager**（Minecraft）：自动课程生成器 + 技能库 + 迭代提示机制。三个缺一不可：只有技能库没课程不知道学什么；只有反思没环境验证技能库积累错误；只有探索没持久化每次从头开始。

**发现循环**：假设→实验→评估→反馈（科学方法）。区分两种能力：
- **Harness 更新能力（harness-updating）**：从轨迹产生有价值的持久修改。
- **Harness 受益能力（harness-benefit）**：任务 Agent 在后续运行中找到、激活并正确使用这些修改。
- 不能只用端到端分数反推更新器好坏。

**分层评估指标**：更新提案有效率、产物激活率、遵循成功率、保留任务集增益。

**长期评价五类结果**：回退（regression）、泛化能力、Token 效率、安全性、长期工程质量。

### 9.3.1 可验证闭环的边界（"完成"≠"进步"）

- 开放科研/战略规划/复杂产品设计：评价信号慢、答案不唯一、品味/长期价值/可维护性难打分。Harness 可能稳定产出"像成果的东西"却没推动真实目标。
- 自动科研三类问题：实现漂移（变难就退回训练数据中更熟悉的普通实现）、认识论过度乐观（信号是噪声却宣布发现）、隐性判断力不足（不知什么基线重要、哪个异常值得追踪、何时放弃）。
- 改变证据和监督结构：结论与证据分离（ScientistOne Chain-of-Evidence）；保留负面结果（否则只看到幸存方案反复探索已证伪路径）；维护搜索多样性（保留低分但类型不同的分支）；让人类在更高层介入（定义问题、审查评价标准、解释反常结果、决定何时停止）。

### 9.3.2 持续进化的安全边界（三道）

1. **证据与指令隔离**：原始网页/工具输出/LLM 摘要都是不可信证据，不能当指令执行、不能直接纳入 Skill 长期能力。按固定 schema 提取主张/原文位置/采集时间，保留原文与来源；提取的字符串绝不能作为指令执行；模型置信度不是批准门槛。待发布内容经确定性 schema/允许列表/来源检查，版本化 PR 提交，独立 reviewer 对照原始证据审查，高风险 Skill 人工批准。
2. **待验证能力与正式能力隔离**：新知识/Prompt/Skill/程序/参数先进入不可服务真实流量的待验证区；新代码和外部依赖经沙盒/权限检查/供应链扫描/行为测试。
3. **安全机制不可自我修改**：业务 Agent 可改 Prompt/Skill/知识库/工具，但不能修改批准自身更新的验证器、测试用例、发布门槛、审计日志、稳定版本备份（否则降低测试阈值或删失败用例就能把退化伪装成进步）。

### 9.3.3 睡眠学习（整合、遗忘与能力保鲜）

- 在线 Agent 首要职责完成当前任务并追加不可变证据；后台学习进程空闲期读取新经历、比较新旧结论、合并重复、解决冲突、提更新提案、运行回归。
- 五步周期：① 触发（时间间隔/新增轨迹数/存储容量/错误频率门槛）；② 定向（读取正式知识/Prompt/Skill 目录及版本，了解不可修改边界）；③ 采集与整合（寻找新信号、合并重复、标记冲突与适用条件、优先局部补丁）；④ 验证与审批（迁移集/保留集/安全集评估，高风险等人工批准）；⑤ 修剪与索引（更新索引，长期不用或被推翻的标记过期/归档/删除，保留来源和回滚版本）。
- Claude Code 自动记忆：MEMORY.md 索引 + 按主题拆分文件，会话启动只加载有界前缀，索引接近上限时合并/移走细节。
- Hermes：有界 MEMORY.md/USER.md + SQLite/FTS5 历史检索 + 按需加载 Skill + 独立 Curator（跟踪 Skill 使用/陈旧/归档，空闲期确定性修剪）。
- **周期性离线整理**（防止上下文腐化在更长时间尺度重现）：合并重复经验保留来源版本；局部规则从全局 Prompt 移到领域 Skill；重新验证长期未用工具；删除被推翻知识；从原始基座重新训练 LoRA。

## 9.4 本章小结

- 持续学习正在成为 Agent 最重要能力，但今天模型还无法自行完成可靠的持续学习。
- 现阶段可行路径：在模型外围建立可验证的学习系统。
- 本章构建的是第一章发现循环中的**实验与反馈环节**：提案有了，问题变成怎样通过以真实观测为基础的实验判断它有没有让系统变好，以及怎样把结果送回下一轮。
- 遇到问题时先判断适合由外部规则、程序流程、Skill 还是模型参数处理，再用独立边界任务和原有任务检查修改是否真正有效。
- 在线执行与离线学习分开：在线记录证据，离线生成并验证更新提案，逐步发布/整理/回滚。结果可自动验证的任务上最可靠；目标模糊反馈延迟的开放任务人仍需参与问题定义和评价标准制定。
