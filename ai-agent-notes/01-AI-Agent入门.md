# 01 · AI Agent 入门

> 来源：《深入理解 AI Agent》第 1 章
> 本章是全书的概念地图：核心公式、运行循环（ReAct）、工程框架（Harness）、设计模式。

---

## 1.1 现代 Agent = LLM + 上下文 + 工具

### 1.1.1 核心定义

- **LLM（大脑）**：不只是模型参数，而是整个决策内核——理解意图、思考规划、做出判断。能力来自两部分：预训练积累的世界知识与语言能力 + 后训练固化的决策策略。
- **上下文（眼睛）**：Agent 在每个决策点收到并保留的信息表示——环境观察、用户记忆、领域知识、自身状态、任务进展。
- **工具（手脚）**：Agent 用来感知或改变外部世界的接口，含工具定义、调用协议、适配器——从预定义工具调用到动态生成代码，从委托子 Agent 到主动与用户沟通。

### 1.1.2 观察空间与动作空间（最重要的能力杠杆）

> **核心洞察：模型固定时，提升 Agent 任务表现最主要的系统工程手段 = 重新定义或扩展观察空间与动作空间（即扩展上下文和工具）。**

- 没通过观察通道进入上下文的信息，对模型来说"像不存在"。
- 没被动作接口允许的操作，模型只能停留在文字建议。
- 许多看似需要"更聪明模型"的问题，其实只是接口问题：把任务数据纳入上下文、把操作封装成工具，原本不可解的任务就可能变可解。

**案例**：
- **Manus**：把 Deep Research、Coding、Computer Use 三条路线合并——虚拟浏览器扩大观察空间，文件系统/代码执行/命令行扩大动作空间。它没有靠更强模型，而是取三类 Agent 观察空间与动作空间的并集。
- **OpenClaw**：通过 WhatsApp/Telegram/Slack/Discord/iMessage 等消息渠道接收任务，用本地 Gateway 连接 Google Drive、Notion 等云应用 + 本地文件系统——把接口延伸到用户数字生活。

> **规律**：产品能力的演进往往就是观察空间和动作空间的演进。

**五类 Agent 产品对比（眼睛/手脚/策略）**：

| 产品 | 眼睛（感知） | 手脚（行动） | 策略 |
|------|-------------|-------------|------|
| Cursor 等 Coding Agent | 需求、代码片段、目录列表、终端输出 | 代码搜索、文件读写、执行命令 | 增量开发：理解→搜索→编辑→测试→调试 |
| Deep Research 搜索 Agent | 搜索结果、网页内容、论文摘要引用 | 搜索查询、网页读取、生成报告 | 迭代深化：调整搜索方向，综合报告 |
| Browser Use 电脑操控 Agent | 屏幕截图、DOM/无障碍树、操作结果 | 点击、输入、滚动、截图、执行代码 | 视觉感知+操作：观察→识别→执行→验证 |
| 豆包手机助手 Agent | 手机截图、App 界面状态、系统反馈 | 点击、滑动、输入、打开 App | 意图理解+App 操控 |
| Pine AI 个人办事 Agent | 授权账户记录、账单结果、服务商资料 | 打电话、发邮件、填表单、与用户确认 | 多步骤执行：收集→制定策略→联系→谈判→汇报 |

**共同特征**：开放式动作空间（能生成任意自然语言和代码）、内部思考（行动前先规划）、持续交互（根据环境反馈调整策略）。

## 1.2 工具：Agent 的手脚

### 1.2.1 五类工具（按与外界互动方向分类）

| 类别 | 作用 | 代表 |
|------|------|------|
| **感知工具** | 让 Agent 访问信息 | 搜索引擎、文件系统读取、API/数据库 |
| **执行工具** | 让 Agent 改变世界 | 代码执行、文件操作、系统命令、外部 API 调用 |
| **协作工具** | 与其他 Agent 分工 | 委托子 Agent、关键决策点请求人类确认、多 Agent 协调 |
| **事件触发工具** | 外部输入驱动 Agent（非主动调用） | 新邮件、定时、Webhook 回调 |
| **用户沟通工具** | 主动与用户建立连接传递信息 | 文字消息、语音通话、邮件 |

> 事件触发工具是外部驱动；用户沟通工具专注信息传递（区别于执行工具改变外部世界）。

### 1.2.2 工具调用（Tool Calling / Function Calling）四步流程

1. 在上下文声明可用工具（名称、用途、参数）。
2. 模型自主判断要不要调用、调哪个、传什么参数。
3. 工具执行完毕，结果追加到上下文。
4. 模型据此决定下一步行动。

> 开发者只负责定义工具和执行调用，模型自主完成"要不要调用、调哪个、传什么参数"的决策。

### 1.2.3 工具设计的核心原则

- **从最窄能力起步，随复杂度扩展**：四则运算→计算器；读表格/清洗/统计/绘图→受限 Python 代码解释器（比不断叠加专用工具更易组合探索）。
- **通用性扩大出错与攻击面**：代码必须在隔离沙盒运行，默认不能访问网络，不能读授权目录外文件，限制执行时间/CPU/内存/输出大小。
- **长程任务用受控虚拟工作目录**：同时保存计划、中间结果、运行日志、最终产物，让 Agent 多次执行间接续工作；限定可读写路径、容量、文件类型，防路径越界。
- **通用工具不总优于专用工具**：支付、删除数据、发邮件、生产部署等高风险/强业务约束操作，应封装为参数明确、权限受限、全程可审计的专用工具 + 预览 + 人工确认。

> **一句话原则**：通用基础能力用于组合与探索；专用工具用于约束高风险和强业务规则操作。

## 1.3 LLM：Agent 的大脑

### 1.3.1 关键能力

- 解析真实意图（用户说的往往不是真正想要的），拆解任务，执行中持续判断（下一步做什么、要不要调工具、调哪个、传什么参）。
- **内部思考**：行动前先规划推演，不改变外部环境，但显著提升后续行动质量。
- 与传统 RL Agent 不同：LLM Agent 不是盲目随机探索，而是在结构化知识体系上展开（预训练沉淀了数学定律、因果关系、问题分解策略等）。

### 1.3.2 模型即 Agent（Model as Agent）

- 先进模型通过后训练（尤其 RL）把工具调用能力内化为原生能力：何时调用、调哪个、传什么参都由模型决定，无需人工编排。
- **但框架层反而更重要**——Harness 原指马具（缰绳挽具），不是限制马，而是把力量引导到正确方向。模型是"强大但不可预测的马"，Harness 是"把能力引导成可靠任务执行的工程外壳"。
- 模型自主决策空间越大，出错影响面越大，越需要精细约束/验证/纠正。
- **模型厂商真正优势**：不是"让框架变薄"，而是能对模型与外围 Harness 协同优化。

### 1.3.3 苦涩的教训（The Bitter Lesson）与 Harness 的立场

- Sutton：研究者把领域理解编码进系统短期见效，长期输给随算力/数据扩展的通用方法（搜索与学习）。
- **本书立场：方向认同，节奏务实**。
  - 方向上不怀疑模型会持续"吃掉" Harness（工具调用、长程规划曾靠外部编排，如今已是模型原生能力）。
  - 节奏上这个"吃"的过程远慢于想象：训练以月计，模型无法一次内化所有业务约束与偏好。
  - **模型此刻的能力边界，就是 Harness 此刻的价值所在**。
  - 模型每内化一层，Harness 就卸下一层，转而兜底新的能力前沿。

### 1.3.4 Agent 学习机制的三条互补路径

| 路径 | 主要载体 | 更新特性 |
|------|----------|----------|
| **任务内上下文适应** | 当前上下文（示例、状态、检索结果） | 即时、低成本，任务结束不自动保留 |
| **跨任务外部产物更新** | 知识文档、Prompt/Skill、Harness 程序 | 跨任务持久、可审计，依赖检索或工具调用 |
| **训练周期参数更新** | 模型权重（SFT、偏好训练、RL） | 高维能力、广泛泛化，训练与回归成本高 |

> 三者协同：上下文负责**临场适应**，外部产物负责**可控积累**，参数负责**内化难以显式表达的能力**。
> 这三条也按"可回滚程度从高到低"排列（呼应最小 diff + 可回滚设计模式）。

## 1.4 上下文：Agent 的眼睛

### 1.4.1 上下文的五个组成部分（API 视角）

1. **系统提示词（System Prompt）**：开发者编写，全程不变，是"岗位说明书"（身份、权限、行为准则）。含跨会话用户记忆 + 动态注入环境状态。
2. **工具定义（Tool Definitions）**：声明可用工具的名称、功能描述、参数格式。没有它就无法调用任何工具。与系统提示词一起构成**静态前缀**。
3. **用户消息（User Messages）**：用户输入，可能含 RAG 动态检索引入的外部知识。
4. **模型回复（Assistant Messages）**：最多含三部分——reasoning（思考过程）、content（文本回复）、tool_calls（工具调用）。一次回复三者不一定同时出现。
5. **工具执行结果（Tool Results）**：框架执行工具后返回的结果，是下一步思考的直接依据。

> 前两项 = 静态前缀；后三项 = 动态消息历史（轨迹）。
> **Agent 的上下文 = 静态前缀 + 轨迹**。

### 1.4.2 消融实验（实验 1-1）结论

| 组件缺失 | 结果 |
|----------|------|
| 无工具定义 | ✗ 无法调用工具 |
| 无思考过程（reasoning） | △ 决策不连贯 |
| 无历史记录 | △ 重复操作 |
| 无工具结果 | ✗ 盲目循环（无限循环） |

> 核心洞察：**上下文决定 Agent 能看到什么，而 Agent 只能基于它看到的信息做决策。** 缺失任何一个组件，决策能力都严重退化。

## 1.5 ReAct 循环（核心运行机制）

### 1.5.1 定义

ReAct = **Reasoning + Acting**，实际含三个环节：**想 → 做 → 看**（思考 → 调用工具行动 → 观察结果 → 继续思考），循环直到任务完成。

### 1.5.2 最小运行骨架（伪代码）

```
trajectory = [user_request]
repeat:
    context = stable_prefix + trajectory
    decision = Model(context)
    trajectory.append(decision)
    if decision has no tool call:
        return decision.answer
    for call in decision.tool_calls:
        # independent calls may run in parallel
        validated_call = Harness.validate(call)
        observation = Environment.execute(validated_call)
        trajectory.append(observation)
```

**职责分工**：
- Model 只负责决定下一步。
- Harness 负责组装上下文、校验并执行工具。
- Environment 负责产生真实状态变化和观察。

### 1.5.3 轨迹（Trajectory）的关键特性

- 轨迹 = 用户消息 + 模型回复（reasoning + tool_calls）+ 工具执行结果的结构化消息历史。
- 每次 LLM 调用都看到完整轨迹 → 清楚任务进度、此前尝试、已有结果。
- 轨迹结构化的价值：易于解释调试、分析行为模式、优化决策路径、沉淀进知识库、用于 RL 训练。

## 1.6 Harness 工程：模型之外的竞争力

### 1.6.1 Harness 的完整定义

```
Agent = Model + Harness
Harness = 上下文管理 + 工具接口 + 约束 + 验证 + 纠正
Agent ↔ Environment
```

- 最小 Demo 只需 Model + 能构造上下文、暴露工具的 Harness。
- 生产系统还要加入**约束、验证、纠正**。
- Harness 是"Agent 边界内、模型之外"的运行与治理层，不包括环境本身。
- 物理部署位置不能决定概念归属（仿真环境与 Agent 同进程仍是 Environment）。

### 1.6.2 Harness 五要素

| 功能 | 职责与核心原则 | 实际例子 | 章节 |
|------|---------------|----------|------|
| **Context（上下文）** | 提供感知信息，信息要充分 | 系统提示词、知识库、Agent 状态栏、Sidecar 旁路查询 | 2、3 章 |
| **Tools（工具接口）** | 提供观察与行动手段，接口要清晰（命名直观、参数有例子、边界有说明） | MCP 工具、代码解释器、搜索工具 | 4 章 |
| **Constrain（约束）** | 设定行为边界；故障安全默认值，所有能力默认关闭、必须显式开放 | Claude Code 每个工具默认需用户授权 | 4 章 |
| **Verify（验证）** | 自动判断结果对错；只看结构化数据（JSON 字段）不看自由文本（防提示注入） | Linter、类型系统、工具调用结果校验 | 5、6 章 |
| **Correct（纠正）** | 发现问题自动修正或回退；确认无法恢复前不暴露中间态 | 静默重试、接续生成、连续失败回退人工（熔断） | 2、5 章 |

### 1.6.3 模型控制循环（伪代码）

```
observation = Environment.observe()
trajectory = [observation]
while true:
    actions = Model(Harness.build_context(trajectory))
    if len(actions) == 0:
        break
    allowed_actions = Harness.constrain(actions)
    observation = Environment.apply(allowed_actions)
    if not Harness.verify(Environment):
        observation = Harness.correct(Environment)
    trajectory.append(allowed_actions, observation)
```

> 五个功能构成闭环：上下文与工具让 Agent"能做事"；约束预防错误、验证发现偏差、纠正使闭环形成，三者共同让 Agent"不做错事"。

### 1.6.4 关键判断

- 早期框架关注"上下文与工具"（能做事）；生产级重心转向"约束、验证、纠正"（可靠做事）。
- **Claude Code 的 Harness 绝大部分代码是约束/验证/纠正**，工具本身只是一小部分。包括：流程状态管理、多层上下文压缩、权限分类、熔断器（Circuit Breaker）、错误恢复机制。
- 行业正从"能做事"向"可靠地做事"转变，Harness 工程成为核心竞争力。

### 1.6.5 工程范式演进（层层包含）

```
提示工程 ⊂ 上下文工程 ⊂ Harness 工程 ⊂ Loop 工程 ⊂ Graph 工程
```

| 阶段 | 关注点 |
|------|--------|
| 提示工程 | 优化输入给模型的自然语言指令 |
| 上下文工程 | 系统性管理模型能看到的所有信息 |
| Harness 工程 | Agent 如何组织模型运行并与环境交互（上下文+工具+约束+验证+纠正） |
| Loop 工程 | 跨轮次持续自主运转：谁发现下一件事、何时验证、何时真正完成 |
| Graph 工程 | 把 Agent 循环、确定性程序、人工审批组织成显式执行图（节点=能力，边=路由与依赖） |

> **当模型能力趋同时，竞争优势转移到模型之外的工程实践。**
> 例证：LangChain 在 Terminal Bench 2.0 上从 52.8% 提升到 66.5%（30 名外→前 5），改的不是模型而是 Harness（自动检查执行结果、检测重复循环、优化思考策略）。

### 1.6.6 构建有效 Agent 的三大核心原则（Anthropic 经验）

1. **保持简单**：从最简单方案开始，只在必要时增加复杂度。直接 API 调用优于复杂框架，清晰代码优于聪明抽象（每多一层抽象都是调试新盲区）。
2. **保持透明**：明确显示规划步骤、执行日志、决策轨迹（既为调试，也是用户建立信任的前提）。
3. **设计好工具接口（ACI，Agent-Computer Interface）**：从 Agent 视角设计接口（让 Agent 易理解使用），而非从程序员视角。命名参数直观，用设计消除误用（防呆 Poka-yoke，如 SIM 卡缺角、微波炉门未关不加热）。

## 1.7 如何选择模型

- **闭源模型**（OpenAI GPT/o 系列、Anthropic Claude 系列）：能力领先，成本高，受 API 策略限制。不要只看排行榜，要在自己任务上评估（第 7 章）。
- **开源模型**：与闭源差距约 6 个月内，成本显著低，可私有化部署、支持微调。国内 Agent 能力较强：DeepSeek、Kimi、GLM。不同模型工具调用能力差异大，务必场景实测。
- **策略边界**：模型具备能力 ≠ 产品允许调用（网络安全、蒸馏、隐私、高风险操作策略不同）；同一任务在聊天产品/Coding Agent/API 结果可能不同。业务关键任务需备人工接管或合规模型替代路径。
- **绝大多数 Agent 需要支持思考（Reasoning）的模型**：多步思考、工具选择等复杂决策，不带思考的模型表现差。例外：单步简单任务、Computer Use 中仅点击固定位置的简单 GUI 操作。
- **关注输出速度**：Agent 多轮推理，每轮等待输出，输出速度直接决定端到端延迟（20 轮 × 每轮慢 2 秒 = 多等 40 秒）。
- **关注多模态支持**：需理解图片/音频/视频时是硬性要求。

## 1.8 编排模式：工作流与自主 Agent

> **从简单到复杂的原则**：先考虑单个 LLM 调用 → 能清晰分解为固定子任务用工作流 → 需要动态决策才用自主 Agent。
> **记住**：Agent 系统通常用延迟和成本换任务性能，应谨慎权衡。

### 1.8.1 工作流（Workflow）：确定性编排

- 预定义代码路径，节点间流转顺序代码固定，LLM 只在节点内部负责理解与生成。
- 例（订机票四节点）：核实身份 → 搜索航班 → 完成付款 → 确认预订。
- **两大优势**：① 严格流程控制（"付款前不能预订"等规则由代码强制，不依赖 LLM）；② 安全性（提示注入/模型犯错最多影响当前节点，无法跳到不该执行的分支）。
- **局限**：缺乏变通性，预设流程未覆盖的情况只能走异常分支或交还人类。

### 1.8.2 自主 Agent（Autonomous Agent）：动态决策

- 执行路径由 Agent 根据环境反馈实时决定。
- 本质 = 在循环中使用工具的 LLM（ReAct 循环）。
- **必须设计明确停止条件**，否则陷入死循环或过度执行。

**常见退出条件（任一满足）**：
1. 任务完成
2. 调用 final_answer（最终输出工具）
3. 无工具调用返回
4. 错误次数超限
5. 达到最大轮次

- 适用：开放式问题（Coding Agent 解 SWE-bench、Computer Use、迭代搜索研究）。
- 风险：更高成本、复合错误；需沙盒充分测试、护栏监控、关键决策点人机协作。

### 1.8.3 混合模式

关键合规流程用工作流保证可靠性，灵活决策部分切自主模式（如 n8n 可视化框架可同时用工作流节点和自主 Agent 节点）。

## 1.9 护栏与安全性

### 1.9.1 三层护栏（按被绕过难度排序，越靠下越不依赖模型判断）

| 层 | 管什么 | 时机 | 核心机制 |
|----|--------|------|----------|
| **上下文层** | 模型能看到什么 | 内容进入上下文前拦截 | 相关性分类器、安全分类器（越狱/提示注入）、内容审核、基于规则的过滤 |
| **执行层** | 模型能做什么 | 动作生效前验证 | 工具风险评级（低/中/高）、独立审查进程、最小权限凭证、沙盒隔离、人在回路、输出检查（PII 过滤器） |
| **数据层** | 世界最终能被改成什么样 | 稳定机制强制执行 | 数据库行级安全、约束与校验器、受控视图、存储过程、不可伪造的访问上下文 |

**关键区分**：
- **越狱（Jailbreak）**：用户自己试图绕过模型安全限制。
- **提示注入（Prompt Injection）**：攻击者通过外部数据（网页、文档）间接操纵模型行为。

**上下文层结构性上限**：处在同一上下文的 Agent 很难判断自己是否已被注入，所以上下文层只能降低攻击成功率、给不出保证——这正是需要下面两层的原因。

**数据层价值**：不依赖上面两层是否正确——即使提示注入得手、生成代码漏写权限判断，越权操作仍会在数据层被拒绝。

**代表性工业实践（Anthropic Constitutional Classifiers）**：
1. 规则驱动——用自然语言规则生成合成数据训练输入输出分类器。
2. 上下文联合判断——用户提问 + 模型回答放一起检查（有些回答单独看无害，对照提问才发现暗语）。
3. 两级筛查——先极轻量探针（读模型内部激活，几乎零成本）检查所有对话，可疑再交强分类器复审（而非直接拒绝）。

### 1.9.2 护栏的误拒绝问题

- 评估护栏不能只测"应拒绝的是否拦截"，还要测"明确允许的请求能否正常完成"（否则误拒绝合法敏感任务，如授权安全测试、模型蒸馏研究）。

### 1.9.3 人工干预（Human in the loop）

- 让 Agent 在不损害体验下提升性能；部署早期尤为重要（识别失败模式、发现边缘情况、建立评估周期）。
- 两种触发情况：
  1. **超过失败阈值**（重试次数/操作次数超限）。
  2. **高风险操作**（敏感、不可逆、高风险，如授权大额退款/付款）。

## 1.10 贯穿全书的设计模式（一次性命名）

| 模式 | 定义 | 应用场景 |
|------|------|----------|
| **提议者—审核者（Proposer-Reviewer）** | 产出与评判由两个不共享上下文的角色分别承担；评判方看产物本身（渲染结果、测试输出、结构化参数）而非产出方推理过程 | 第 3 章更新知识、第 4 章工具审批/验证、第 5 章 PPT/视频/日志实验、第 7 章评估 UI、第 9 章审核更新、第 10 章对等协作 |
| **渐进式披露（Progressive Disclosure）** | 不把全部信息一次性放进上下文，先给可检索目录，再按需加载细节；同时优化上下文预算与选择精度 | 第 2 章 Skills（元数据常驻、正文按需）、第 3 章分层检索、第 4 章主动工具发现、第 10 章 Agent 发现 |
| **只增不改（Append-only）** | 状态以追加方式演进，已写内容不再回头修改；换来可缓存、可重放、可审计 | 第 2 章 KV Cache 前缀稳定性、第 3 章事件式记忆、第 4 章新工具 schema 追加到轨迹末尾 |
| **边界集 + 保留集（Boundary Set + Retention Set）** | 任何修改都要在"应改变的样本"和"不应影响的样本"上同时验证；只测前者会过拟合，只测后者会把无效当安全 | 第 7 章回归任务、第 8 章训练/评估隔离、第 9 章更新提案验证 |
| **最小 diff + 可回滚** | 每次修改尽量小、带来源、可单独回滚（而非整体重写），让归因成为可能 | 第 3 章知识更新、第 5 章代码补丁、第 9 章 Prompt/程序更新 |

> **提议者—审核者成立的前提**：自审不可靠——同一上下文中的模型难以发现自己的认知盲区，也难以判断自己是否已被注入。

## 1.11 本章小结（要点速记）

1. **Agent = 大脑 + 眼睛 + 手脚**（LLM + 上下文 + 工具），三者缺一不可。
2. **扩展眼睛和手脚是最主要的能力杠杆**：模型固定时，重新定义/扩展观察与动作空间，常能把不可解任务变可解。
3. **眼睛（上下文）是决定性因素**：上下文 = 静态前缀 + 轨迹；消融任一组件系统显著退化。
4. **Harness 是竞争力所在**：模型商品化，差异在 Harness（约束/验证/纠正）。
5. **编排顺序**：先优化提示词 → 工作流 → 自主 Agent，降低意外风险。
6. **五个设计模式**：提议者—审核者、渐进式披露、只增不改、边界集+保留集、最小 diff+可回滚。
7. **安全是架构问题**：从第一行代码考虑，护栏分上下文层/执行层/数据层三层。
