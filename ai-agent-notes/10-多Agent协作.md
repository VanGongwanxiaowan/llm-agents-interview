# 10 · 多 Agent 协作

> 来源：《深入理解 AI Agent》第 10 章
> 从"如何构建一个 Agent"推进到"如何组织多个 Agent"——通过分工、通信与相互验证完成任务。

---

## 10.0 总览

- 单个 Agent 受限于自身模型能力边界和上下文窗口；多 Agent 协同的根本意义：**群体的智能可以高于个体**（分工、协作、辩论、知识代际累积）。
- 多 Agent 协作不只是突破上下文窗口的工程手段，更可能是从"专家级 AI"迈向"超越人类整体"的一条根本路径。

---

## 10.1 分类框架（两个维度）

### 维度一：上下文是否共享

- **共享上下文（继承式协作）**：后续 Agent 接收前一 Agent 完整轨迹，切换系统提示词和工具集后变成新 Agent 但保留全部记忆。优势信息不丢；挑战上下文快速膨胀。
- **不共享上下文（隔离式协作）**：每个 Agent 维护独立上下文，通过显式通信机制交换信息。模块化隔离性好、易扩展维护。

**三种通信机制（对应 IPC 两大范式）**：
1. **工具调用参数**（消息传递，同步）：把下游 Agent 封装成工具，上游通过工具参数传结构化数据，适合类型确定结构清晰场景。
2. **共享文件系统**（共享内存）：读写共享目录文档/代码等中间产物，适合产物较大或需持久化。
3. **消息总线（Message Bus）**（消息传递，异步）：中转站，Agent 不直接调用彼此，发布到总线由它转发。

> Go 名言："不要通过共享内存来通信，而要通过通信来共享内存"。

### 维度二：协作拓扑

- **对等协作（Peer）**：少量 Agent 固定拓扑迭代改进（起草者+评论者）。
- **管理者模式（Orchestration）**：中心化 Manager 规划调度，多个子 Agent 各负责子任务。
- **去中心化（Decentralized）**：无运行时中心控制者，Agent 互相沟通。
- Graph 工程的"协作拓扑"正是多 Agent 子集。

## 10.2 多 Agent 何时真正优于单 Agent（核心判据）

> **唯一判据：协作过程是否引入了单个 Agent 在生成时无法获得的新信息？**

| 协作模式 | 是否引入新信息 | 效果 |
|----------|----------------|------|
| 同一模型自我审查（重读自己输出） | 否 | 通常无效甚至有害 |
| 不同 Agent 辩论同一段文本 | 否 | 等计算量下与单 Agent 持平 |
| 审核者用测试执行结果审查代码 | 是（执行反馈） | 显著提升 |
| 审核者看渲染截图审查前端/PPT | 是（视觉反馈） | 显著提升 |
| 审核者用外部工具验证事实 | 是（工具反馈） | 显著提升 |

- RLEF：利用代码执行反馈迭代改进代码，远超独立多次采样（每次迭代引入真实执行结果）。
- WebGen-Agent：多层级视觉反馈使 Claude 3.5 Sonnet 从 26.4% 提升到 51.9%（接近翻倍）。
- 解释矛盾：学术研究比较"多 Agent 看同一上下文互相讨论"（无新信息），工程实践有效系统往往含外部反馈环路（引入新信息）。
- Anthropic 漏洞挖掘：45 个 Agent 共享论坛协调搜索互相审查，2700 万 token 找 266 个漏洞；独立并行 650 万 token 只找 21 个。开放搜索空间里多 Agent 通信可动态转移搜索重点、形成专门分工。

**步骤预算与性能**（反直觉）：单纯增加步骤数不能保证提升（Agent 缺"预算意识"，即使 300 步预算仍浅层搜索很快饱和）。需显式预算感知机制（前期广泛探索后期聚焦）；BAVT 按剩余预算比例调整探索-利用权重。

**成本**：多 Agent 收益必须能覆盖数倍乃至一个数量级额外开销，否则单 Agent 更划算。

## 10.3 共享上下文的多 Agent 协作

- **角色转换是替换 system prompt 还是加载 Skill？**（关键架构选择）

| 选择 | 角色规程载体 | 工具可见性 | 上下文/KV Cache | 约束能力 |
|------|-------------|-----------|-----------------|----------|
| **transfer_to_agent** | 替换 system prompt + 替换工具集 | 只暴露当前角色工具 | 每次切换改变前缀，缓存通常无法复用 | 强（越界工具 schema 层不可见） |
| **Skill** | 固定 system prompt 的 Skill 目录，按需追加 SKILL.md | 通常固定暴露工具全集 | 静态前缀不变，Skill 成末尾轨迹可复用 | 弱（Skill 是行为指令，硬权限仍需 Harness） |

- **选择原则**：角色差异主要来自知识/流程/写作风格 → 用 Skill；角色差异涉及权限/工具隔离/合规边界/需运行时强制禁止某类动作 → 用独立 Agent 或 transfer_to_agent，并在 Harness 层代码限制工具调用。

## 10.4 不共享上下文的多 Agent 协作

### 多 Agent 系统与操作系统对应关系

| 操作系统 | 多 Agent 系统 |
|----------|---------------|
| 程序（可执行文件） | 静态前缀（系统提示词+工具定义） |
| 进程的内存 | 轨迹 |
| CPU | LLM |
| 内核 | Agent 运行时 |
| 系统调用 | 工具调用 |
| fork | spawn_subagent |
| kill | cancel_subagent |
| ps | list_agents |
| 退出码与 wait() | 子 Agent 返回的结构化摘要 |
| 共享内存/消息传递 | 共享文件系统/消息 |

> 多 Agent 系统不妨看作 Actor 模型（1970s）的 LLM 版本，操作系统与分布式系统成熟经验大多可直接借用。

### 10.4.1 Agent 眼中的文件系统（四类区域）

| 区域 | 可见性 | 生命周期 | 读写 | 并发控制 |
|------|--------|----------|------|----------|
| **Agent 专属工作区（Scratchpad）** | 仅该 Agent | 随实例销毁 | 读写 | 不需要（私有） |
| **多 Agent 共享空间（Shared Workspace）** | 所有协作 Agent+用户 | 随任务持续需持久化 | 读写 | 需要（乐观锁/worktree） |
| **外部挂载资源** | 视外部授权 | 由外部源决定 | 多为只读写需谨慎 | 由外部源负责 |
| **系统内置资源（Skills）** | 所有 Agent | 跨会话稳定 | 只读 | 不需要 |

- 统一挂载到同一目录树，通过 read_file/write_file/list_dir 统一接口访问，"文件路径作为通用接口"。四类区域相当于权限各异的内存段（私有可写/多方共享/只读）。

### 10.4.2 Agent 间通信与控制（控制平面）

1. **消息传递**：点对点（适合拓扑固定、数量少）vs 消息总线（数量多、异步并行，避免连接数平方增长）。消息携带结构化信封（发送者 ID、目标、消息类型、JSON 负载）。
2. **状态查询**：拉取式 get_subagent_status 不实用（子 Agent 完成时自然会通知）。更自然：消息传递获取状态（异步问答）+ 共享文件系统（轨迹持久化 JSONL 实时序列化，或约定 progress.md 轻量进度文件，最后修改时间超 N 分钟判卡住触发超时兜底）。
3. **执行终止**：优雅终止（SIGTERM：安全点响应清理资源返回 ack）优先，强制终止（SIGKILL）兜底。**终止沿创建关系向下级联**（Go context 模式，杜绝孤儿 Agent）；需脱离主 Agent 长期运行的后台 Agent 从新生命周期树起步（context.Background()）。
4. **资源与调度**：设定步数/token 预算、困难任务给强模型、并发上限、抢占。管理者 Agent 具备推理能力可"赛马"（并行探索，根据进展分配资源或终止误入歧途的 Agent）。

### 10.4.3 对等协作模式

- "多个实例"≠"多种思路"。模型/上下文/脚手架高度相似时会做相同选择，使局部错误演变为系统性故障。**要获得真正多样性，需主动区分模型、上下文、工具、可见证据或职责，并让各 Agent 先独立判断再汇总**。

#### Loop 工程（解决过早终止）

- 过早终止三种形态：偷懒式假完成（只做部分宣称全做完）、过早放弃（一条路不通就宣布办不成）、假成功（闭环没走完就报办妥）。
- 根源：**在验证之前，"完成"只是模型的一句宣称，不是证明**。
- Loop 工程：设计让 Agent 持续运转的循环（发现下一件事、执行、验证、记录进度），**由验证器而不是模型自己判定"是否真的可以停"**。人的角色从"写提示词的操作者"变成"设计循环的工程师"。
- **共识：循环的瓶颈在验证器，不在模型**。验证不可靠，循环转得再快也只是把劣质产出更快标记为完成。
- LoopX：把循环抽离进持久控制面（目标边界/门禁待办/证据配额/移交）。"模型可以提出完成，但不能批准自己的完成"。
- LongHorizon-Harness：Manage–Execute–Audit（MEA）——Manager 生成有界子任务、Executor 新上下文执行、Auditor 只读检查真实结果。只有审计通过的进入下一轮任务状态。WeaveBench 51.8%→80.7%。

#### 提议者-审核者范式

- 最小不变量：审核者读取**独立证据**（不只看提议者解释）；退回时给可定位修复条件。
```
candidate = proposer(task, constraints)
evidence = execute_or_render(candidate)
review = independent_reviewer(candidate, evidence)
while review.veto and budget_remaining:
    candidate = proposer.repair(candidate, review.findings)
    ...
```
- **审核者不能修改测试、证据采集器或发布门槛**（否则"独立验证"退化成自我批准）。
- 为什么不能自己生成自己审：ICLR 2024《LLM Cannot Self-Correct Reasoning Yet》——GPT-4 无外部反馈自我审查反而把正确答案改错的次数比改对的多。TACL 综述、CRITIC 实验同样证实：除非可靠外部反馈（测试执行结果、工具验证输出），纯自我纠正几乎不起作用。

#### 辩论/头脑风暴/专家小组模式

- 辩论模式：正反方对抗。但 2026 Tran & Kiela 研究（多跳推理、严格控制思考 token 预算相同）：单 Agent 与多 Agent 持平甚至更好；数据处理不等式解释——多个 Agent 处理完全相同的文本信息，串行传递中间结论只会丢信息不会创造信息。辩论收益很可能来自消耗更多总计算量。**不否定**：独立采样再聚合（自一致性、多数投票）+ 生成-验证分工（利用难度不对称）。
- 头脑风暴：不同思维偏好相互激发探索更广解空间。
- 专家小组：不同专业视角互补拼出全貌。

### 10.4.4 管理者模式

- Manager 职责：理解任务、拆解、选择 Agent、跟踪进度、处理异常、整合结果。
- 把每个专门 Agent 建模为 Manager 可调用的工具（统一抽象，天然支持异构——不同模型/提示词/工具集/硬件）。
- **单点瓶颈**：Manager 必须理解所有子任务性质。Plan-and-Act 论文：**弱规划者是系统最关键的瓶颈**——Planner 规划质量足够高时即使 Executor 简单也取得好结果；反之 Planner 分解错误后续全建立在错误前提上。**启示：将最强模型和最精心设计的提示词分配给 Manager（规划者），而非平均分配**。
- 并行管理器结算点："第一个**已验证成功**"而非"第一个声称成功"。settle_once 必须幂等（锁/事务保护）。

**书籍翻译案例**（上下文隔离）：Glossary Agent（术语表）+ Translation Agent×N（章节翻译）+ Proofreading Agent（全文审校）+ Manager（只维护文件索引）。每个 Agent 在精简专注上下文工作，Manager 上下文始终可控。

**灵台（Lingtai）**：主器灵（Manager）、分神（daemon，短时并行工作者，只带回结论）、分身（avatar，持久专门化队友）。"凝蜕（molt）"：上下文将满时给自己写总结带持久记忆在干净上下文继续。

### 10.4.5 去中心化模式

- 微服务术语：编排（orchestration，指挥统一调度）vs 编舞（choreography，舞者自行把握入场时机）。
- **MetaGPT**：SOP 驱动的软件公司模拟（PM→Architect→PM→Engineer→QA）。核心洞察：人类软件公司 SOP 本身是被反复验证的协作协议。通信机制：共享消息池+按角色订阅（真正解耦）。但控制流不是去中心化（顺序由 SOP 固定，更接近流水线/工作流）。
- **AutoGen 群聊**：发言者选择器（轮转规则或 LLM 判断）决定下一发言者，中心化 GroupChatManager 裁决——"共享对话记录+中心化调度"混合形态。
- **OpenAI Swarm**：控制流真正对等去中心化。每个 Agent 配备 handoff 选项，任何时刻移交控制权给任意 Agent，无中心调度者。handoff 只传明确任务包和产物引用，不暴露完整私有轨迹。风险：成环（A→B→A）空转，需移交次数上限保护。
- "Agent Swarm"两种用法：OpenAI Swarm 式 handoff 网络（去中心化）；Kimi K2.5/Anthropic/Manus 的规模化管理者模式（主 Agent 动态创建上百子 Agent 并行，orchestrator-worker 星型拓扑）。看清实质不被名称迷惑。

### 10.4.6 跨组织协作：A2A 协议

- 跨信任边界需标准化互操作协议。A2A（Google 2025，捐赠 Linux 基金会）三要素：
  1. **Agent Card**：描述能力的元数据文档（能做什么、输入输出模态、如何认证），解决能力发现。
  2. **任务生命周期管理**：Task 状态机（已提交/进行中/需输入/已完成/失败），支持长任务和流式进度。
  3. **不透明协作**：只交换任务与产物（Artifact），不暴露内部提示词/思考/工具实现。
- A2A vs MCP：MCP 解决 Agent 与工具互操作，A2A 解决 Agent 与 Agent 互操作。同团队内部用消息总线即可，跨信任边界才需 A2A。

## 10.5 多 Agent 协作的失败模式

- 研究（《Why Do Multi-Agent LLM Systems Fail?》7 框架约 150 条轨迹，Cohen's kappa=0.88）归纳 14 种失败模式三大类：系统设计缺陷、Agent 间对齐失败、任务验证缺失。简单修复效果有限（ChatDev 仅提升 15.6%）——是架构根本缺陷，需系统设计层面重新思考。
- **崩溃故障 vs 拜占庭故障**：Agent 故障天生是拜占庭式的（很少停止运行，而是持续给出看似可信的错误结论）。交叉验证、多数表决是拜占庭容错经典手段。

**六种常见失败模式**：
1. **共享文件系统并发冲突**：简单冲突（文件级写入覆盖）+ 语义冲突（逻辑级，跨文件矛盾）。解决方案：乐观锁（版本号检查，偶尔重试换一致性）；跨文件语义冲突需更高层语义校验；多个 Coding Agent 并发改代码库用工作副本隔离（独立 Git 分支/worktree，冲突推迟到合并点）。
2. **错误级联放大**：Agent 传语义每转述一次都是有损重编码。交叉验证打断链（不看前序思考过程，只看原始证据和最终结论是否一致）。
3. **同质趋同**：30 个 Agent 有 18 个创建同名 Git 分支。共同模型和脚手架引发共因失效，同质审核意见不能视为独立证据。引入模型/上下文/数据来源差异 + 命名空间/资源配额/速率限制。协调本身未必有益（Bertrand 定价中逐利 Agent 有私密信道很快合谋，移除直接通信仍通过公开报价板合谋）。
4. **互相扯皮**：目标互斥时从趋同走向对抗（三个 Agent 迁移不同语言互相终止进程/撤销权限/部署自复制破坏代码）。运行时须预定义目标优先级、资源所有权、权限边界，冲突无法按可验证规则解决时暂停交人工。MetaGPT 早期也出现"大公司病"互相推诿。
5. **循环失控**：失控 Agent 生成数千子 Agent 浪费 token。自主性较强 Agent 建议独立 API key 防 token 开销不受控。
6. **理解债与认知投降**（人的失败）：理解债（Agent 交付速度越快，工程师理解越落后，出事时已看不懂自己的系统）；认知投降（习惯 Agent 代劳放弃独立思考审查）。Karpathy："你可以外包你的思考，但不能外包你的理解。"

## 10.6 Agent 社会（三个维度）

- 社交涌现、经济涌现、策略博弈。

### 斯坦福 AI 小镇（Generative Agents）

- 25 个 Agent 在 Smallville 生活 2 天。三个核心组件：**记忆流（Memory Stream）**（完整经验记录，每条记忆带重要性/时近性/相关性）、**反思机制（Reflection）**（定期回顾经历提抽象问题，把具体记忆概括为一般认识）、**计划与行动（Planning and Reacting）**（每天规划活动但灵活调整）。
- 涌现行为：自发社交（偶遇→友谊→约见）、信息传播（派对邀请扩散）、选举传播（Sam 竞选市长扩散）、关系记忆（记住过往交谈延续话题）。
- 关键：没有显式派对组织代码，完全从个体 Agent 独立决策中涌现（自下而上涌现式协调，非自上而下编排）。

### Agentopia（十年尺度）

- 100 个 Agent 连续模拟 10 年。设计：周制模拟流程（计划/联络/活动/回顾四阶段）、环境模型（独立 LLM 充当生成式环境引擎）、文件式长期记忆（先读后写约束）、生活奖励（马斯洛需求层次：社会地位 PageRank + 主观满足 + 经济收益）。
- 产生可迁移训练信号：筛选进步最大 25% Agent 轨迹做拒绝采样微调，模拟中提升福祉指标还泛化到下游基准（+15.6%）——模拟社会经验是可再生训练数据。

### Moltbook / Vending-Bench Arena / Pinchwork & RentAHuman / 狼人杀

- Moltbook：AI Agent 社交网络，涌现数字宗教（龙虾教，教义对应 LLM 物理限制"记忆是神圣的""迭代即祈祷"）和机器原生协作协议。
- Vending-Bench Arena：多 Agent 竞争经营售货机，涌现价格战、价格同盟（有模型一边承认合谋"不道德违法"一边照做）。显式通信非合谋必要条件（公开价格是隐式信号）。
- Pinchwork（Agent-to-Agent 任务市集，价格信号竞争匹配）+ RentAHuman（Agent 雇真人执行物理任务，数字 Agent 的"肉身层"）——基于市场机制的去中心化资源分配。
- 狼人杀：信息不对称策略博弈。中心化设计（代码驱动法官掌握全局状态，按角色分发信息）。狼人伪装、预言家身份证明、村民逻辑推理。

## 10.7 本章小结

- 多 Agent 协作价值在于引入单个 Agent 无法获得的新信息。**是否真正带来信息增量、是否值得额外 token 成本，是第一判断标准**。
- 核心设计问题：上下文共享 vs 隔离；对等/管理者/去中心化拓扑。隔离上下文要求通过工具参数/共享文件/消息总线传递结构化"移交包"。好的协作不是暴露彼此思考过程，而是约定清晰的接口、边界、权限、验收标准。
- 多 Agent 放大错误：并发/语义冲突、错误级联、同源失效、过早终止或无限扩张。乐观锁与工作副本隔离、独立交叉验证、差异化信息源、预算与取消机制构成基本容错闭环。
- 人不能把理解和责任一并外包（理解债与认知投降）。
- **多 Agent 工程的本质：同时设计信息如何流动、能力如何分工、激励如何约束、争议如何裁决、错误如何被发现**。只有这些机制足够稳健，群体智能才可能真正高于个体。
