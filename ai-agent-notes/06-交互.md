# 06 · 交互：观察与动作空间的扩展

> 来源：《深入理解 AI Agent》第 6 章
> 前五章默认 Agent 与世界"轮流行动"；本章挑战这个前提——扩展观察/动作空间的**模态**与**时机**。

---

## 6.1 模态与触发时机的扩展

- **模态**决定观察/动作的形式（文本、声音、屏幕、力矩、发声、点击、关节）。
- **触发时机**决定观察/动作的节奏（Agent 主动去取 vs 世界主动推来；回合内做完 vs 跨回合可打断可抢占）。
- **回合制是训练留下的假设，不是环境的性质**：模型训练语料几乎全是回合制，学到的策略默认世界会等它；但真实世界不会等。

| 尺度 | 场景 | 观察侧变化 | 动作侧变化 |
|------|------|-----------|-----------|
| 秒—天 | 异步与事件驱动 | 被外部事件主动唤醒 | 跨回合：先发起，后续靠事件收尾 |
| 10ms—1s | 语音 | 边说边听，不等说完 | 边想边说，可被打断 |
| 亚秒—秒 | Computer Use | 屏幕两帧间持续变化 | 动作后必须重新确认现实 |
| 毫秒 | 机器人 | 传感器连续回流 | 动作分块：一次规划一小段，可被抢占 |

## 6.2 异步与事件驱动：当世界主动找上门

### 6.2.1 为什么需要异步

- 同步 = "做完一件才能做下一件"；异步 = "多件可同时进行"。
- 真实助理三项核心能力：异步执行是常态、事件优先级动态判断、中断恢复流畅性。
- **根本矛盾：训练同步 / 部署异步**——LLM 训练范式假设"发出工具调用后下一条必须是工具结果"，真实部署要求"用户随时打断、多任务并发、外部事件在工具未返回时抵达"。
- 事件驱动 = 系统不轮询，新消息到达自动触发处理；所有输入/输出/思考/外部交互统一建模为事件流。

### 6.2.2 OpenClaw 事件驱动机制

- **Hooks（事件钩子）**：响应 Agent 生命周期事件（会话创建、重置）。
- **Cron（定时调度）**：按 cron 表达式执行周期任务。
- **Heartbeat（心跳守护）**：每隔 N 分钟唤醒 Agent 检查。
- 真正让 Agent "自己动起来"的只有 Cron 和 Heartbeat（时间驱动）；Hooks 事件源是框架内部。
- **短板**：第三方事件源（新邮件、API 回调、紧急通知）缺乏即时接入通道，只能等下一周期。
- **PineClaw Channel 机制**：在 Gateway 和 Pine API 间建立实时事件通道（电话接通/需验证码/结束等关键事件即时推送），解决 Heartbeat 轮询延迟（客服等验证码时用户收不到通知→挂断）。
- **核心价值**：真正"主动服务"不仅需要 Agent 定时检查世界，更需要世界主动通知 Agent。

### 6.2.3 事件触发工具（三类）

1. **定时器（set_timer）**：一次性（明确时间点任务，如"下周一 10:00 致电银行"）与循环（周期性任务、外部服务不支持推送时反复查询）。
2. **后台任务监控（monitor_shell）**：监控命令行新增输出或含特定关键词的输出（不断查询浪费 token，等结束再处理无法及时发现严重问题）。
3. **外部事件通道（connect_channel）**：新邮件/API 回调/IM 消息实时推送。

- 设计：定义清晰触发条件和过滤规则（避免无关事件唤醒浪费算力）；事件载荷含足够上下文（减少唤醒后额外查询）。

### 6.2.4 用户沟通工具

- 原生 ReAct 循环中 assistant 消息直接发给用户；OpenClaw 打破——用专门工具发消息，用户和 Agent 可随时互相发消息（"活人感"）。
- 支持异步消息模式（用户不一定在线）、已读/未读状态跟踪、多渠道一致性。
- 多渠道用户沟通与召回：根据紧急程度、用户状态、内容性质、偏好综合选渠道；长时间任务完成时主动通知召回注意力。

### 6.2.5 虚拟身份与隔离执行环境

- **架构选择**：直接管理用户账号（一旦出错/被攻破全部数字身份暴露）vs 独立虚拟身份（专属通讯账号、存储、计算环境，透明代表用户工作）。
- **隔离执行环境**：虚拟电脑（VM/容器）+ 虚拟手机（Android 模拟器），提供 OS 级隔离；全天候运行、错误最多崩溃虚拟环境、防止访问用户本地文件。
- **两个现实挑战**：反机器人机制（CAPTCHA/IP 信誉，数据中心 IP 易识别，需住宅代理）；访问用户真实账号用 Human-in-the-Loop 认证（VNC/RDP 远程桌面让用户亲自登录，会话令牌有效期复用）。
- **数据交换**：共享文件系统卷挂载（/workspace/shared），传递文件路径引用而非内容拷贝，避免占用上下文。

### 6.2.6 事件处理机制

- **事件循环（event loop）**骨架：每轮从队列取事件→追加轨迹→调一次 LLM→执行工具→回到循环头。
- **关键性质**：事件只在每轮循环边界被消费（LLM 推理/工具执行时不插入，等到安全点统一处理）；取消也在安全点检查。

**事件结构化建模**（来源/渠道/内容/上下文）：
```json
{"source": {"type": "email", "sender": "client@example.com"},
 "channel": "gmail_webhook",
 "content": {"subject": "退款请求", "body": "..."},
 "context": {"priority": "high", "customer_tier": "vip", "related_orders": ["#12345"]}}
```
> 只有清晰建模才能避免把用户输入误当工具结果、把藏有指令的工具结果误认用户指令（提示注入）。

**三种处理策略（区别在于对待安全点的方式）**：
| 策略 | 适用 | 机制 |
|------|------|------|
| **取消式（Cancellation）** | 紧急事件 | 主动中断当前步骤制造安全点：停止当前操作→清空队列→事件+紧急事件一起追加→立即重新调 LLM |
| **队列式（Queued）** | 常规事件 | 入队不打断→等当前操作完成→工具返回时检查队列非空则一次性追加→LLM 综合处理 |
| **并行式（Parallel）** | 独立轻量查询 | 判断独立性/复杂度→并行推理会话独立执行→结果标记"与主任务并行" |

**紧急度判定**：
- 紧急：user.interrupt、supervisor.instruction、agent.interrupt、标记紧急的外部触发器（系统告警、支付失败）。
- 非紧急：常规 user.input、agent.input、tool.result、timer.trigger、常规外部触发器。
- 硬编码规则有局限，建议用**轻量分类 LLM 作为事件路由器**。
- 取消点必须是工具/推理能安全收尾的位置；未完成工具结果用显式占位符表示，**不能伪造成功**。

### 6.2.7 如何让同步模型支持异步打断（五条规则）

1. LLM 输出后立即记录 assistant message（含 thinking/content/tool call）。
2. 工具调用完成时才记录 tool result（执行中轨迹"部分完成"）。
3. 工具执行中的打断需占位符：为未完成工具生成占位符响应（"工具正在后台执行，请优先处理新事件"），追加打断事件重新调 LLM。
4. LLM 思考中的打断直接丢弃当前思考（不写入轨迹）。
5. 非打断事件入队等待批处理。

- 核心优势：常态下 LLM 看到完美同步轨迹（assistant 与 tool result 严格配对），最友好；只在真正需要打断时引入占位符。
- **风险（加剧幻觉）**：模型可能"编造"工具结果误以为已返回有效数据（训练时从未学会"结果还没回来"）。因此**只在真正紧急时打断，非紧急入队批量处理**。

**适合现有模型的异步工具接口**：把"启动"和"完成"解耦——`initiate_phone_call`（立即返回任务 ID，进展靠事件通知）而非 `phone_call`（暗示调用即完成）。工具名和描述本身要传达异步语义。

**队列式处理的注意力分散问题**：模型倾向于只关注最后一个事件。两个干预：
- 提示词层面告知"收到多个连续事件时全面考虑所有信息"。
- Agent 状态栏标记：`[未处理事件 1/4] Tool result...`，末尾汇总"上面有 4 个未处理事件（1 工具结果 + 2 用户消息 + 1 系统提醒），请确保回应涵盖所有信息"。

### 6.2.8 深层矛盾与未来方向

- 占位符/异步工具接口/状态栏标记都是在用提示工程弥补"训练同步/部署异步"矛盾，是过渡期权宜之计。
- **根本解法**：下一代模型通过异步环境中的强化学习获得三种核心能力：
  1. 理解轨迹中事件的异步穿插（乱序轨迹中保持清晰认知）。
  2. 恢复被打断的任务和思考（回答后自然等待原工具结果，避免幻觉误以为完成）。
  3. 批量事件综合处理（不只关注最后一个）。
- 需要新基础设施：异步环境模拟器（工具延迟返回、用户随机打断）+ 专项奖励机制。
- **持续思考（continuous-time）**：用约 200 行编排逻辑让现成文本思考模型变成持续思考 Agent——把整个交互建成不间断思维流，随时合上正在写的 `<think>` 块，把新观察作为普通消息注入再接着解码。利用常被浪费的资源（模型每秒生成上百 token，工具调用/用户说话要好秒），产生"边等边想"和"边做边想"两种行为。

## 6.3 语音：最自然的人机接口

### 6.3.1 三种交互范式

| 范式 | 核心结构 | 优势 | 限制 |
|------|----------|------|------|
| **级联（Cascading）** | VAD→ASR→LLM→TTS | 模块清晰、易替换易调试 | 延迟累积、副语言信息丢失 |
| **端到端 Omni** | 原生音频输入输出，按轮次 | 延迟较低、保留语气情绪环境声 | 仍依赖轮次、训练调试成本高 |
| **全双工** | 原生音频输入输出，持续听说决策 | 支持重叠说话、自然打断、连续流 | 训练控制评估更复杂 |

> 主线：如何摆脱"轮流说话"和 VAD 对发言权的猜测。

### 6.3.2 级联流水线

- 四模块延迟：VAD 500-800ms、ASR 50-200ms、LLM 100-500ms、TTS 200-500ms，串行累积最优 ~0.9s、最差 ~2.3s。
- 生产排队放大：总延迟 = S/(1-ρ)，ρ=0.5→2s（用户忍受上限），ρ=0.8→5s（不可接受）。
- **从串行到流式感知**：ASR 边听边转（临时转录+最终确认）、LLM 分段输出、TTS 增量合成。真正的"抢跑"需提交/失效/回滚机制，非开 stream 开关即可。
- **传统 VAD+ASR 三问题**：延迟累积（等静音确认说完）、信息丢失（有声/无声二值无法表达犹豫/情绪/环境声）、上下文切断（邮箱/人名/专有名词分片识别出错）。
- 基于 LLM 的流式听觉模型：从连续音频输出文本和语义事件（speak_start/end、interrupt、emotion、laugh/sigh/noise），把"识别"和部分"理解"放同一模型。

### 6.3.3 端到端全模态模型（Omni）

- 级联即使流式感知，听/想/说仍通过离散接口交接，情绪/语调/环境声在转文本时丢失。Omni 同一模型直接听音频生成回复输出语音。
- 端到端优势主要体现在延迟和非文字信息，**不必然转化为更高准确率**。关键不在于是否有中间表示，而在于中间表示承载了什么信息。
- Omni 仍假设轮流说话，靠 VAD 或语义端点划分发言权。
- 代表：OpenAI Realtime（gpt-realtime，服务端 VAD+轮次检测+异步函数调用+打断）、Gemini Live（VAD 敏感度可配置）、Qwen3-Omni（Thinker-Talker MoE，首包延迟 234ms）、Step-Audio 2（潜在音频编码+RL，副语言理解 83.09%）。
- 共同局限：仍依赖轮次检测机制；VAD 基于声学信号无法捕捉语义（用户停顿≠说完、"嗯""对"是附和不是打断）。

### 6.3.4 全双工交互模型

- 同声传译等任务要求"用户说"和"模型说"重叠。全双工不再预设轮次，持续听、持续说，不断决定继续/停顿/打断/调用工具。
- Moshi（Kyutai 2024）：并行建模用户和模型音频流。
- **交互模型（Interaction Model）**：交互性内建在模型而非外部 harness；微轮次机制以短音频块持续推进，静音/重叠/打断作为连续上下文保留；可把完整对话委派给后台推理模型。
- GPT-Live：把全双工带到生产规模。

### 6.3.5 认知时序：实时交互与深度思考（三种方案）

| 方案 | 机制 | 问题 |
|------|------|------|
| **一：快思考回应，慢思考回答** | 快模型几百毫秒即时回应，慢模型后台深推 | 简单问题过度思考；快慢不一致（两个实例各自独立思考，前后矛盾） |
| **二：快思考交互，慢思考提醒** | 后台通过状态栏/接口向前台建议，前台维持话头 | 通信间接（前台可能误解建议）、看不到后台中间思考 |
| **三：端到端思考与表达统一** | Step-Audio R1：MGRD（模态锚定思考蒸馏）+ MPS（双脑并行构思与表达） | 思考和实时表达需一起重新训练 |

- **快慢分离的工程优势**：直接承接慢模型迭代红利——更强思考模型发布后只需替换后台，不必重训整套实时语音系统。是"让交互能力与智能上限分别演进的模块化选择"。
- 两个"端到端"含义澄清：① 语音通路端到端（Omni/交互模型）；② 认知架构端到端（实时交互与深度思考同一模型 vs 前后台分离）。两条轴独立。

### 6.3.6 更像人的语音合成

- 传统 TTS 过于流畅零停顿暴露机器身份；停顿、填充词、偶尔重复是人类表达不确定性的信号。
- 让主 LLM 输出控制标记（THINKING、EMO:happy、SPEED:0.8x），TTS 映射为停顿/韵律/语速/笑声/叹气。

## 6.4 Computer Use：GUI 自动化 Agent

### 6.4.1 感知-思考-行动循环

1. 截取当前屏幕 → 2. 多模态模型输出思考+动作 → 3. 执行层执行（鼠标/键盘）→ 4. 等待界面响应再截图。
- 区分"看懂界面"（一次截图问答）和"完成任务"（把理解和动作放进闭环，处理页面加载/状态变化/误操作/不可逆后果）。
- **难点**：每步之后重新确认现实是否仍符合计划。

### 6.4.2 动作空间设计（三类工具）

1. **GUI 操作工具（computer）**：鼠标（move/click/drag/down/up）、键盘（type 逐字符 12ms 间隔、key 组合键、hold_key）、滚动（四方向+修饰键）、感知（screenshot、cursor_position、wait）。
2. **命令执行工具（bash）**：持久 bash 会话、120s 超时、哨兵字符串检测完成、保持环境状态。
3. **文件编辑工具（str_replace_editor）**：字符串匹配安全编辑（view/create/str_replace/insert/undo）。

- **坐标缩放机制**：实际分辨率 ↔ 训练分辨率（XGA/WXGA/FWXGA），截图缩小→推理→坐标放大→执行。

### 6.4.3 视觉定位（Grounding）三条路线

| 路线 | 做法 | 特点 |
|------|------|------|
| **Set-of-Mark（纯视觉标注）** | 分割模型切候选区域+叠加编号，模型报编号 | 不需 DOM，原生桌面/游戏适用；对未专门训练模型友好 |
| **DOM/Accessibility Tree（结构化元素索引）** | 枚举可交互元素编号（CDP 获取 DOM/A11y） | 定位最精确稳定；不省 token；browser-use 代表 |
| **纯坐标预测** | 直接训练模型输出坐标（SeeClick、Claude computer use） | 省标注步骤；对做过 GUI 定位训练的模型直接 |

- **选择逻辑**：结构化信息可得优先 DOM/A11y；不可得（原生桌面、Canvas/WebGL、游戏）用视觉标注或坐标预测。
- **坐标预测的分辨率依赖**：模型对坐标理解高度依赖训练分辨率，需双向坐标缩放，且**按宽高比选目标分辨率**（非等比拉伸会把画面压变形、坐标判断带偏）。

### 6.4.4 能看动画、能听声音的 Computer Use Agent（AOI）

- 传统感知假设屏幕静止（每 3-5 秒睁一次眼、没耳朵），对"两帧之间发生的事"看不见听不到。
- **重新设计观察接口（AOI，Agent-Computer Observation Interface）**：把连续环境观察转成离散事件。
  1. 帧间关键帧捕获（跳过没变化的画面，小模型判断是否发生有意义变化，变化时才截帧）。
  2. 音量门控的语音转写（有声音才调语音识别）。
  3. 文字描述画面（帧描述成一句话，原图清理后文字留记忆，实现多模态交互历史压缩）。

### 6.4.5 Computer Use 的世界模型

- 观察接口不消除规划延迟（仍是串行"截图-思考-点击"）。人类是"先预测动作后果，实际变化与预期一致就沿计划执行，偏离才停下来重新观察"。
- **世界模型**：让 Agent 行动前预测桌面接下来可能变什么，实现"推测执行"。
- 桌面状态不只是像素图（窗口、焦点、滚动位置、输入框内容、加载状态、权限、网络返回）；世界模型至少编码当前状态、预测候选动作的状态变化、交给规划器决策。
- 重点不是生成逼真未来截图，而是预测完成任务所需的**可检查的状态差异**。
- Photon-1（Induction Labs 2026.7）：每帧压缩为离散潜在 token，自回归预测动作后下一状态表示（不逐像素生成截图）。

### 6.4.6 移动端：生态壁垒比技术更难

- 技术差异：接入无障碍服务 API（AccessibilityService）、触摸手势（坐标语义改变需额外手势类型）。
- **真正卡点是生态壁垒**：商业模式冲突——传统应用靠流量与注意力变现（广告、推荐、冲动消费），Agent 代操作绕过变现链路（不关注广告、不冲动消费、直奔目标）。是**结构性利益冲突**，比纯技术问题更棘手。

## 6.5 机器人操作（XLeRobot 整理桌面）

### 6.5.1 硬件与算法分工

- 诊断方法：保持硬件不变，先让人接管闭环（遥操作）。几百美元机械臂通过遥操作已能完成连续多步任务 → **硬件不是瓶颈，算法才是**。
- 遥操作不只是收集演示数据，也是"固定硬件、替换操作者"的诊断实验。

### 6.5.2 机器人控制基本结构（分层）

| 层级 | 核心问题 | 输出 | 时间尺度 |
|------|----------|------|----------|
| 任务目标 | 人想完成什么 | "把杯子和废纸归位" | 分钟级 |
| 长程规划 | 先做什么后做什么 | 先杯子再废纸最后检查 | 秒到分钟 |
| 基本技能 | 当前完成哪个状态变化 | pick(red_cup)、place(red_cup, tray) | 1-3 秒 |
| VLA/技能策略 | 技能具体怎么动 | 夹爪一段动作或连续轨迹 | 1-10 Hz |
| 底层控制与安全 | 稳定及时执行 | 关节/末端控制量、限速急停 | 50-1000 Hz |

- **必须把"任务顺序"和"眼前动作"分开**（否则高层推理延迟拖慢底层、底层高频让高层处理大量无关细节）。
- 模型不直接输出任意关节角，只选择 pick/place/verify_state/stop 等有边界技能，经标定/限速/超时的执行器变成真实动作。

### 6.5.3 长程规划与任务分解

- 规划器先列物体和目标、决定先后顺序、写清开始/完成条件和风险限制。
- 每完成一个技能得到可检查节点；抓取失败只重试当前步；物体被挪动只需重新规划受影响步骤。
- **工具设计**：一次调用只做一件事、动作范围固定、超时限制、执行后立即重新观察。

### 6.5.4 VLA 控制（Vision-Language-Action）

- VLA 接收当前画面 + 技能指令 → 输出动作。工具调用定义期望的状态变化，VLA 定义如何通过连续动作实现。
- RT-2/OpenVLA：连续动作切离散 token 逐个输出；π₀：直接生成连续平滑轨迹。
- **动作分块（action chunking）**：模型一次生成一小段未来动作，控制线程高频执行，模型后台准备下一段（把推理等待藏在执行时间里）。代价：动作段越长运动越平滑但看到的新画面越少 → 在平滑性和反应速度间取舍。

### 6.5.5 VLA 局限

1. 训练数据有限（机器人演示远少于互联网数据）。
2. 只学会模仿，不一定懂后果（行为克隆没明确要求回答"动作造成什么结果"）。
3. 机器人各不相同（自由度/坐标系/夹爪/执行器延迟不同）。
4. 观察可能过时（动作块执行后物体可能被移动，模型仍据上一帧决定）。

### 6.5.6 世界模型

- 世界模型 = "动作结果预测器"：当前状态 + 候选动作 → 预测下一状态 → 比较候选结果 → 选择/重规划/安全停止。
- 三件事：看懂当前状态、预测不同动作结果、交给规划器选择。
- 只会描述视频的 VLM 或生成画面的模型不会自动成为可靠世界模型，必须知道动作是什么并能预测动作影响。
- 三种用法：动手前（比较候选动作选风险小的）、执行时（真实观察与预测对照，偏差则缩短/停止/重规划）、训练时（利用视频/仿真/失败轨迹学习状态变化）。
- 世界模型给出的是"如果这样做可能发生什么"的可比较预测，不是确定答案；真实摄像头观察仍是最终事实。

### 6.5.7 从仿真到真实机器人（Sim2Real）

- 模拟稳定不代表真机成功，需处理两个环境差异（背景、光照、相机位置、遮挡、摩擦、传感器噪声、执行器延迟）。
- 实验验证：训练时主动扩大画面变化范围（改变背景/外观/光照/噪声）有助于适应新摄像头画面；真机部署仍需真实相机标定、执行器测试、完整安全闭环。

## 6.6 本章小结

- 四节共享同一控制骨架：**持续感知 → 判断当前状态与时机 → 选择回复或动作 → 让输出进入环境 → 观察反馈 → 继续/修正/重试/停止/重新规划**。
- 共享同一组原语：**唤醒、安全点、取消、抢占、快慢分离**。
- 完成"构建 Agent"最后一块：观察与动作空间在**内容、模态、时机**三个方向展开。
