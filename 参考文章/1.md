# OpenClaw：架构深度解析（2026年2月，Opus 4.6版本）
### 面向软件架构师——AI智能体系统底层工作原理

---

## 1. 执行摘要
OpenClaw 是一个开源的自托管式AI智能体框架，可将大型语言模型转化为具备持久性、能使用工具且支持真实世界集成的助手。与仅作为API调用代理的聊天机器人封装器不同，OpenClaw 实现了完整的智能体运行时环境，包含会话管理、内存持久化、上下文窗口优化、多渠道消息传递、沙箱化工具执行以及事件驱动的可扩展性。

本文档从技术层面深度剖析 OpenClaw 的工作机制——不仅涵盖其运行的AWS基础设施，还包括使无状态LLM（大语言模型）表现得如同有状态、持续可用助手的软件架构决策。

## 3. 网关——系统的中枢神经系统
网关是一个长期运行的单例Node.js守护进程，掌管所有状态和连接。可将其视为**应用服务器**——所有数据流转均通过它完成。

### 3.1 优先采用WebSocket协议
网关在可配置端口（默认`127.0.0.1:18789`）上暴露类型化的WebSocket API。所有客户端（macOS应用、命令行工具、网页UI、移动节点、自动化程序）均通过这一单一WebSocket连接。

**传输协议细节：**
- 传输层：WebSocket，基于文本帧传输JSON载荷
- 首个帧**必须**是`connect`握手请求
- 请求格式：`{type:"req", id, method, params}` → 响应格式：`{type:"res", id, ok, payload|error}`
- 事件格式：`{type:"event", event, payload, seq?, stateVersion?}`
- 产生副作用的方法（如`send`、`agent`）需携带幂等键，以支持安全重试

**连接生命周期：**
```
客户端                    网关
  |---- 请求:connect -------->|
  |<------ 响应 (成功) ---------|  （返回在线状态 + 健康快照）
  |<------ 事件:presence（在线状态）---|
  |<------ 事件:tick（心跳）-------|
  |------- 请求:agent（调用智能体） ------->|
  |<------ 响应:agent --------|  （确认：运行ID、状态：已接受）
  |<------ 事件:agent ------|  （流式返回内容增量）
  |<------ 响应:agent --------|  （最终结果：运行ID、状态、摘要）
```

### 3.2 设备配对与信任模型
所有WebSocket客户端在连接时需声明**设备身份**。网关实现了如下信任模型：
- **本地连接**（回环地址/同主机Tailnet网络）可自动通过认证
- **非本地连接**需签署挑战随机数，并经显式审批
- 配对后会颁发设备令牌，用于后续重连
- 网关认证令牌（`OPENCLAW_GATEWAY_TOKEN`）适用于所有连接

### 3.3 渠道桥接
网关维持与各类消息平台的持久连接：
- **WhatsApp**：基于Baileys（网页协议）
- **Telegram**：基于grammY框架
- **Discord**、**Slack**、**Signal**、**iMessage**：基于各平台官方SDK
- **网页聊天（WebChat）**：基于网关WS API的静态UI

每个桥接组件将平台特定事件转换为标准化的内部消息包。核心架构设计要点：**网关是唯一持有消息会话的进程**——每台主机仅维护一个WhatsApp会话、一个Telegram机器人连接，以此类推。

## 4. 智能体循环——消息如何转化为行动
当收到入站消息时，完整生命周期如下：

### 4.1 接收与路由
```
入站消息 → 渠道桥接 → 会话解析 → 命令队列 → 智能体运行时
```
1. **渠道桥接**：标准化消息（发送者、内容、附件、线程上下文）
2. **会话管理器**：根据`dmScope`规则解析会话密钥：
   - `main`：所有私信共享一个会话（跨设备/渠道保持连续性）
   - `per-peer`：按发送者ID隔离会话
   - `per-channel-peer`：按渠道+发送者隔离（推荐多用户场景使用）
3. **命令队列**：序列化智能体运行请求

### 4.2 命令队列
这是一个支持通道隔离的先进先出（FIFO）队列，可防止并发智能体运行产生冲突：
```
┌─────────────────────────────────────────┐
│           全局通道（main）               │
│  最大并发数: 4（可配置）                 │
│  ┌─────────────────────────────────┐    │
│  │ 会话通道（按会话密钥隔离）      │    │
│  │ 并发数: 1（严格串行执行）       │    │
│  └─────────────────────────────────┘    │
│  ┌─────────────────────────────────┐    │
│  │ 子智能体通道                    │    │
│  │ 并发数: 8                       │    │
│  └─────────────────────────────────┘    │
│  ┌─────────────────────────────────┐    │
│  │ 定时任务通道                    │    │
│  │ 与主通道并行执行                │    │
│  └─────────────────────────────────┘    │
└─────────────────────────────────────────┘
```

**队列模式**控制入站消息与活跃运行任务的交互方式：
- **`collect`**（默认）：将排队消息合并为单个后续对话轮次
- **`steer`**：注入当前运行任务，在下一个边界点取消待处理工具调用
- **`followup`**：等待当前运行结束后启动新轮次
- **`steer-backlog`**：立即注入并保留消息作为后续轮次

### 4.3 提示组装
OpenClaw为每次智能体运行构建**自定义系统提示**。这并非静态字符串——而是从多个来源组装而成：
```
系统提示 = 
    工具信息（可用工具+描述）
  + 安全规则（防护边界）
  + 技能列表（含文件路径的可用技能）
  + 自更新指令
  + 工作区信息
  + 文档索引
  + 当前日期时间（时区感知）
  + 回复标签
  + 心跳协议
  + 运行时元数据（主机/操作系统/模型/思考等级）
  + ── 项目上下文 ──
  + AGENTS.md（操作指令）
  + SOUL.md（人格/语气）
  + TOOLS.md（本地工具说明）
  + IDENTITY.md（智能体名称/风格）
  + USER.md（用户档案）
  + HEARTBEAT.md（周期性任务清单）
```

**核心设计决策：**
- 引导文件（Bootstrap files）会被截断至`bootstrapMaxChars`（默认20,000字符），以精简提示内容
- 技能仅以元数据形式列出（名称+描述+文件路径）——模型按需`读取`完整的SKILL.md文件
- 工具模式（JSON格式）随提示发送，但会占用上下文空间（即使不可见）
- 时间仅保留时区信息（无动态时钟），确保提示在多轮对话中**缓存稳定**

### 4.4 模型推理与流式传输
嵌入式运行时（`pi-mono`）处理实际的LLM交互：
1. 解析模型+认证配置
2. 通过会话级+全局队列序列化运行请求
3. 将助手回复增量以`event:agent`帧流式返回
4. 工具调用在推理轮次间执行（智能体循环）
5. 强制执行超时限制（默认600秒）

**流式架构：**
- 助手文本增量实时流式传输
- 工具启动/更新/结束事件在独立`tool`流中发送
- 块流式传输可在块完成后立即输出（可配置800-1200字符的分块大小，优先按段落分隔）
- `NO_REPLY`是特殊标记，会从输出载荷中过滤（支持静默轮次）

### 4.5 工具执行
工具是智能体的“手脚”。核心工具始终可用（受策略管控）：
- `read`/`write`/`edit` — 文件操作
- `exec`/`process` — Shell命令执行+后台进程管理
- `browser` — 浏览器自动化（基于CDP协议）
- `web_search`/`web_fetch` — 网络访问
- `message` — 跨渠道消息发送
- `cron` — 定时任务管理
- `memory_search`/`memory_get` — 语义内存检索
- `sessions_spawn`/`sessions_send` — 子智能体编排
- `nodes` — 配对设备控制（摄像头、屏幕、位置、运行命令）
- `canvas` — UI画布控制
- `tts` — 文本转语音
- `gateway` — 自管理（重启、配置、更新）

**工具策略**是分层的允许/拒绝体系：
```
全局拒绝 → 智能体专属拒绝 → 全局允许 → 智能体专属允许 → 默认规则
```

## 5. 内存架构——无状态模型如何“记忆”
这或许是架构上最具特色的部分。LLM本身无持久化内存——每个会话均从零开始。OpenClaw通过分层内存系统解决该问题：

### 5.1 内存栈
```
┌─────────────────────────────────────────┐
│ 第4层：语义向量检索                     │  ← "即使表述不同，也能找到相关笔记"
│ （SQLite + 嵌入向量）                   │
├─────────────────────────────────────────┤
│ 第3层：长期内存（MEMORY.md）            │  ← 精选见解、决策、偏好
│ （手动维护）                            │
├─────────────────────────────────────────┤
│ 第2层：每日日志（memory/YYYY-MM-DD）    │  ← 原始每日笔记，仅追加写入
│ （自动+手动）                            │
├─────────────────────────────────────────┤
│ 第1层：会话上下文                       │  ← 模型上下文窗口中的当前对话
│ （JSONL格式对话记录）                    │
└─────────────────────────────────────────┘
```

### 5.2 作为内存的工作区文件
内存以**纯Markdown文件**形式存储在智能体工作区。文件是唯一可信数据源；模型仅“记住”写入磁盘的内容。
- **`memory/YYYY-MM-DD.md`**：每日日志文件（仅追加）。会话启动时读取当日+前日日志
- **`MEMORY.md`**：精选长期内存。仅在主私有会话中加载（群组上下文绝不加载——安全边界）
- **`AGENTS.md`**：操作指令，每次会话均注入
- **`SOUL.md`**：人格与边界规则，每次会话均注入

**核心设计思路**：智能体被设定为每当学到值得记忆的内容时，就写入这些文件。“心理笔记”无法跨会话保留——唯有文件可以。

### 5.3 向量内存检索（语义召回）
OpenClaw为内存文件构建向量索引，支持语义检索：

**索引流水线：**
```
Markdown文件 → 分块（约400令牌，80令牌重叠）
    → 嵌入向量生成（OpenAI / Gemini / 本地GGUF模型）
    → SQLite存储（可选sqlite-vec加速）
    → 文件监视器（1.5秒防抖）实现增量更新
```

**混合检索（BM25 + 向量）：**
- **向量相似度**：语义匹配（如“Mac Studio网关主机”匹配“运行网关的机器”）
- **BM25关键词相关性**：精确令牌匹配（ID、代码符号、错误字符串）
- 分数融合公式：`最终分数 = 向量权重 × 向量分数 + 文本权重 × 文本分数`
- 默认权重：70%向量 + 30%BM25

**嵌入向量提供商**（自动选择，带降级策略）：
1. 基于node-llama-cpp的本地GGUF模型（约0.6GB）
2. OpenAI `text-embedding-3-small`
3. Google Gemini `gemini-embedding-001`

**重建索引触发条件**：索引存储嵌入向量提供商/模型 + 端点指纹 + 分块参数。任一参数变化，OpenClaw自动重置并重建索引。

**暴露给智能体的工具：**
- `memory_search` — 语义检索，返回带文件+行号范围的片段
- `memory_get` — 按路径读取指定内存文件内容

### 5.4 压缩前内存刷写
当会话接近自动压缩阈值（上下文窗口即将占满），OpenClaw触发**静默智能体轮次**，提醒模型在上下文被总结前将重要内容写入磁盘：
```
会话接近上下文限制
    → 触发静默内存刷写轮次
    → 模型将重要上下文写入memory/YYYY-MM-DD.md
    → 模型回复NO_REPLY（用户无感知）
    → 自动压缩安全执行
```

该机制由软阈值令牌数控制，每个压缩周期最多执行一次。

## 6. 会话管理——跨对话的连续性

### 6.1 会话密钥与路由
每个对话映射到唯一会话密钥：
```
私信：  agent:<agentId>:<mainKey>         (dmScope: "main")
        agent:<agentId>:dm:<peerId>       (dmScope: "per-peer")
        agent:<agentId>:<channel>:dm:<peerId>  (dmScope: "per-channel-peer")

群组聊天：agent:<agentId>:<channel>:group:<id>
Telegram主题：agent:<agentId>:<channel>:group:<id>:topic:<threadId>
定时任务：cron:<job.id>
Web钩子：hook:<uuid>
子智能体：agent:<agentId>:subagent:<uuid>
```

### 6.2 会话生命周期
```
┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│ 会话启动     │───▶│ 活跃使用     │───▶│ 过期         │
│ （首次消息触发）│    │ （消息+工具调用）│    │ （每日4点或闲置）│
└──────────────┘    └──────┬───────┘    └──────────────┘
                           │
                    ┌──────▼───────┐
                    │  压缩        │
                    │  （上下文窗口│
                    │   管理）      │
                    └──────────────┘
```
- **每日重置**：默认本地时间凌晨4:00
- **闲置重置**：可选滑动窗口（`idleMinutes`配置项）
- **手动重置**：`/new`或`/reset`命令启动全新会话

### 6.3 持久化
- **对话记录**：JSONL文件存储路径 `~/.openclaw/agents/<agentId>/sessions/<SessionId>.jsonl`
- **存储索引**：`sessions.json` — 映射关系 `会话密钥 → {会话ID, 更新时间, ...}`
- **来源元数据**：每个会话记录来源信息（渠道、发送者、线程等）

### 6.4 上下文窗口与压缩
所有模型的上下文窗口容量有限。当占满时：
```
完整对话历史
    → 旧消息总结为压缩条目
    → 近期消息完整保留
    → 总结内容持久化到JSONL
    → 后续请求使用：[总结内容] + [近期消息]
```

**压缩 vs 修剪：**
- **压缩**：总结并**持久化**到对话记录（永久保存）
- **会话修剪**：仅在内存中修剪旧**工具结果**，按请求执行（非破坏性）

## 7. 技能系统——为智能体赋予新能力
技能是智能体的习得能力——针对特定工具和任务的结构化指令集。

### 7.1 架构
```
┌─────────────────────────────────────────┐
│          技能解析                       │
│                                         │
│ 工作区技能（最高优先级）                │
│  └── <workspace>/skills/                │
│ 托管技能                                │
│  └── ~/.openclaw/skills/                │
│ 内置技能（最低优先级）                  │
│  └── <install>/skills/                  │
└─────────────────────────────────────────┘
```

### 7.2 懒加载模式
技能**不会**注入提示词中，仅注入精简的元数据列表：
```xml
<available_skills>
  <skill>
    <name>weather</name>
    <description>获取实时天气和预报</description>
    <location>/path/to/weather/SKILL.md</location>
  </skill>
</available_skills>
```

模型仅在任务匹配时才被指令`读取`SKILL.md文件。这使提示词开销最小化（每个技能约97字符+字段长度），同时仍能实现精准的工具调用。

### 7.3 准入控制（加载时过滤）
技能可在YAML前置元数据中声明依赖要求：
- **`requires.bins`**：必须存在于PATH中的二进制文件
- **`requires.env`**：必须设置的环境变量
- **`requires.config`**：必须存在的配置路径
- **`os`**：平台限制（darwin、linux、win32）

会话启动时会快照技能列表，后续轮次复用（文件系统变更时热重载）。

## 8. 子智能体架构——并行工作
子智能体支持后台并行执行任务，不阻塞主对话流程。

### 8.1 设计
```
主智能体运行
    │
    ├── sessions_spawn("研究X")  → 立即返回
    │       │
    │       ▼
    │   子智能体会话（隔离）
    │       │
    │       ├── 独立上下文窗口
    │       ├── 独立工具执行
    │       ├── 受限工具集（无会话类工具）
    │       └── 结果推送至请求方聊天窗口
    │
    ├── sessions_spawn("分析Y")  → 立即返回
    │       │
    │       ▼
    │   子智能体会话（隔离）
    │       └── ...
    │
    └── 主对话继续进行
```

### 8.2 核心设计决策
- **会话隔离**：每个子智能体分配独立密钥 `agent:<agentId>:subagent:<uuid>`
- **禁止嵌套**：子智能体无法生成新的子智能体（防止无限扩展）
- **工具限制**：默认禁用 `sessions_list`、`sessions_history`、`sessions_send`、`sessions_spawn`
- **结果推送模式**：结果附带状态、运行时长、令牌用量、成本信息，推送至请求方聊天窗口
- **自动归档**：会话在可配置超时后归档（默认60分钟）
- **并发控制**：专用通道，可配置最大并发数（默认8）
- **成本控制**：子智能体可通过`agents.defaults.subagents.model`配置使用更经济的模型

## 9. 心跳与定时任务——主动行为
### 9.1 心跳机制
心跳是主会话中的周期性智能体轮次。网关每隔N分钟（默认30分钟）触发一次心跳，附带可配置提示词。
```
┌──────────┐    ┌──────────┐    ┌──────────────────┐
│ 定时器   │───▶│ 智能体   │───▶│ HEARTBEAT_OK     │──▶ 静默处理
│ (30分钟) │    │ 轮次     │    │ （无紧急事项）   │
└──────────┘    └────┬─────┘    └──────────────────┘
                     │
                     ├──────────▶ 告警文本 ──▶ 推送至聊天窗口
                     │
                     └──────────▶ 后台工作（内存维护、
                                  文件整理等）
```

**响应协议：**
- `HEARTBEAT_OK` = 无需要关注的事项（静默处理，不推送）
- 其他内容 = 告警信息（推送至配置的渠道）
- `HEARTBEAT.MD`是可选的工作区清单，智能体每次心跳时读取

### 9.2 定时任务（Cron）
适用于需精确计时或隔离执行的任务：
- **调度类型**：一次性（`at`）、周期性（`every`）、Cron表达式（`cron`）
- **载荷类型**：`systemEvent`（注入主会话）或`agentTurn`（隔离会话）
- **结果推送**：将结果通知指定渠道/接收方
- 隔离的定时任务每次运行生成全新会话

**使用场景对比：**

| 心跳机制                  | 定时任务                  |
| ------------------------- | ------------------------- |
| 批量执行多项检查          | 需精确计时                |
| 依赖主会话上下文          | 需隔离执行                |
| 时间允许小幅偏差          | 可使用不同模型/思考等级    |
| 减少API调用次数           | 一次性提醒类任务          |

## 10. 沙箱化——降低风险影响范围
OpenClaw可在Docker容器内执行工具，限制潜在损害。

### 10.1 运行模式
- **`off`**：工具直接在主机运行
- **`non-main`**：仅为非主会话（群组聊天、子智能体）启用沙箱
- **`all`**：所有会话均在沙箱中运行

### 10.2 作用范围
- **`session`**：每个会话对应一个容器
- **`agent`**：每个智能体对应一个容器
- **`shared`**：所有沙箱化会话共享一个容器

### 10.3 工作区访问权限
- **`none`**：工具仅能访问沙箱工作区（无主机访问权限）
- **`ro`**：主机工作区只读挂载
- **`rw`**：主机工作区可读写挂载

### 10.4 例外机制
- **`tools.elevated`**：显式绕过沙箱，直接在主机执行（仅限授权发送者）
- **工具策略**：沙箱规则生效前，仍需通过允许/拒绝规则检查
- **自定义绑定挂载**：暴露主机特定目录

### 13.2 系统提示安全规则
系统提示包含指导性安全规则：
- 无独立目标（无自我保护、复制、资源获取行为）
- 优先保障安全和人工监督，而非任务完成

- 不通过操纵手段扩大访问权限

## 14. 该架构的核心设计亮点（面向架构师）
### 14.1 有状态性难题
LLM本质是无状态函数：`f(prompt) → response`。OpenClaw通过以下方式实现“有状态”体验：
- **基于文件的内存**：跨进程重启持久化
- **会话对话记录**（JSONL）：重现对话历史
- **压缩前内存刷写**：在上下文丢失前提取持久化知识
- **向量检索**：跨会话语义召回

### 14.2 上下文窗口作为核心资源
上下文窗口是智能体的“工作内存”——容量有限且成本高昂。OpenClaw将其视为缓存管理：
- **压缩** = 带总结的内容淘汰
- **修剪** = 剔除低价值数据（旧工具结果）
- **技能懒加载** = 指令的按需分页
- **引导文件截断** = 注入文件的大小限制

### 14.3 单写入者架构
网关对每个会话采用单写入者模式。命令队列确保：
- 每个会话同时仅运行一个智能体任务
- 会话对话记录无并发写入
- 多渠道消息的确定性排序

### 14.4 工作区作为唯一可信数据源
智能体工作区是**可Git版本控制**的纯Markdown文件目录。这意味着：
- 内存内容人类可读、可编辑
- 版本控制提供完整审计轨迹
- 无需管理数据库（仅向量检索使用SQLite）
- 迁移仅需`git clone` + 配置更新

### 14.5 技能作为按需加载的指令
不同于将所有工具指令嵌入每次提示（令牌成本高），OpenClaw仅列出技能元数据，让模型按需`读取`详细指令。这类似于开发者使用带文档的IDE：无需启动时阅读所有文档，仅在需要时查阅。
